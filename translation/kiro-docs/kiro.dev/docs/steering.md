## ステアリングとは何ですか？

ステアリングは、マークダウンファイルを通じて、Kiroにプロジェクトに関する一貫した知識を提供します。チャットごとに規約を説明する代わりに、ステアリングファイルによって、Kiroが確立されたパターン、ライブラリ、および標準を一貫して遵守できるようになります。

| 機能 | IDE | CLI | Web | モバイル |
| --- | --- | --- | --- | --- |
| ワークスペースのステアリング (`.kiro/steering/`) | ✓ | ✓ | ✓ | ✓ |
| グローバル・ステアリング (`~/.kiro/steering/`) | ✓ | ✓ | — | — |
| Web設定で管理されるクラウドステアリング | — | — | ✓ | — |
| UI 経由での基盤ファイルの生成 | ✓ | — | — | — |
| インクルードモード（always、fileMatch、manual） | ✓ | ✓ | ✓ | ✓ |
| AGENTS.md のサポート | ✓ | ✓ | ✓ | ✓ |

Web上での「グローバル・ステアリング」とは、ローカルの`~/.kiro/steering/`ディレクトリを指しますが、クラウドサンドボックスからは読み取ることができません。クラウドセッション間で個人用ステアリングを再利用するには、[Configuration](https://kiro.dev/docs/web/cloud-configuration/) Syncを通じてアップロードしてください。そうすることで、クラウド上のコピーがすべてのクラウドセッションに適用されます。

## 主な利点

**一貫性のあるコード生成** - すべてのコンポーネント、APIエンドポイント、テストが、チームで確立されたパターンや規約に従います。

**反復作業の削減** - 会話のたびにプロジェクトの標準について説明する必要がありません。Kiroは設定を記憶します。

**チームの足並みを揃える** - プロジェクトに新しく参加した開発者でも、ベテランの貢献者でも、すべての開発者が同じ基準で作業します。

**拡張可能なプロジェクト知識** — コードベースの成長に合わせてドキュメントも拡大し、プロジェクトの進化に伴う決定事項やパターンを記録します。

## ステアリングファイルのスコープ

ステアリングファイルは、ワークスペーススコープまたはグローバルスコープで作成できます。

### ワークスペースのステアリング

ワークスペース・ステアリング・ファイルは、プロジェクトのルートフォルダ内の ``.kiro/steering/`` ディレクトリに配置され、その特定のワークスペースにのみ適用されます。ワークスペース・ステアリング・ファイルを使用すると、個々のワークスペースに適用されるパターン、ライブラリ、および標準を Kiro に通知することができます。

### グローバル・ステアリング

グローバル・ステアリング・ファイルは、ホームディレクトリの ``~/.kiro/steering/`` 配下に配置され、すべてのワークスペースに適用されます。グローバル・ステアリング・ファイルを使用すると、すべてのワークスペースに適用される規約を Kiro に通知できます。

グローバルステアリングとワークスペースステアリングの指示が競合する場合、Kiroはワークスペースステアリングの指示を優先します。これにより、すべてのワークスペースに一般的に適用されるグローバルな指示を指定しつつ、特定のワークスペースではそれらの指示を上書きする柔軟性を維持できます。

### チーム・ステアリング

グローバル・ステアリング機能を使用すると、チーム全体に適用される一元化されたステアリングファイルを定義できます。チーム・ステアリングファイルは、MDMソリューションやグループポリシーを介してユーザーのPCにプッシュするか、ユーザー自身が中央リポジトリから自身のPCにダウンロードし、`~/.kiro/steering`フォルダに配置することができます。

## プロジェクト・ステアリング・ファイル

Kiroは、プロジェクトの中核となるコンテキストを確立するためのプロジェクト・ステアリング・ファイルを提供します：

**製品概要** (`product.md`) - 製品の目的、ターゲットユーザー、主要機能、およびビジネス目標を定義します。これにより、Kiroは技術的な決定の背景にある「理由」を理解し、製品の目標に沿ったソリューションを提案できるようになります。

**技術スタック**（`tech.md`） - 選択したフレームワーク、ライブラリ、開発ツール、および技術的な制約を文書化します。Kiroが実装を提案する際、代替案よりもお客様が確立したスタックを優先して提案します。

**プロジェクト構造** (`structure.md`) - ファイルの構成、命名規則、インポートパターン、およびアーキテクチャ上の決定事項の概要を記載します。これにより、生成されたコードが既存のコードベースに適合しやすくなります。

これらの基盤ファイルは、デフォルトですべての操作に含まれており、Kiroによるプロジェクト理解の基盤を形成します。

IDEでプロジェクト・ステアリング・ファイルを生成するには：

1. Kiro パネルの [**Steering]** セクションに移動します
2. 「**Steering Docsを生成**」ボタンをクリックするか、+ボタンをクリックして「**Foundationステアリングファイル**」オプションを選択します
3. Kiroは、`.kiro/steering/` ディレクトリ内に3つのプロジェクト・ステアリング・ファイルを作成します

## カスタムステアリングファイルの作成

プロジェクト固有のニーズに合わせた専門的なガイダンスにより、Kiroの理解の幅を広げます。

1. Kiroパネルの「**Steering」**セクションに移動します
2. **「+」**ボタンをクリックします
3. ステアリング ファイルの適用範囲（ワークスペースまたはグローバル）を選択します
4. わかりやすいファイル名を選択します（例：`api-standards.md`）
5. 標準のマークダウン構文を使用してガイダンスを記述してください
6. 要件を自然な言葉で記述してください
7. 必要に応じて、「**Refine」**ボタンを使用して、Kiroに要件を精緻化させることができます

作成されたステアリングファイルは、すべての Kiro とのやり取りですぐに利用可能になります。

## カスタムエージェントを使用したステアリング

[カスタムエージェント](https://kiro.dev/docs/custom-agents/creating/)を使用する場合、ステアリングファイルは自動的に組み込まれません。ステアリングコンテキストを読み込むには、エージェントの`resources`設定に明示的に追加する必要があります。

カスタムエージェントにすべてのステアリングファイルを含めるには、エージェントの設定に以下を追加してください：

json

```json
{
  "resources": ["file://.kiro/steering/**/*.md"]
}
```

このグロブパターンにより、エージェント使用時にステアリングディレクトリ内のすべてのマークダウンファイルが読み込まれます。完全な設定例については、[カスタムエージェントのドキュメント](https://kiro.dev/docs/custom-agents/creating/)を参照してください。

## Agents.md

Kiroは、[AGENTS.](https://agents.md/)md標準によるステアリングディレクティブの提供をサポートしています。AGENTS.mdファイルは、Kiroのステアリングファイルと同様にマークダウン形式ですが、AGENTS.mdファイルは[インクルードモード](https://kiro.dev/docs/steering/#inclusion-modes)をサポートしておらず、常に読み込まれます。

AGENTS.md ファイルは、グローバルなステアリングファイルの配置場所（`~/.kiro/steering/`）またはワークスペースのルートフォルダに追加すると、Kiro によって自動的に検出されます。

また、AGENTS.md ファイルはワークスペース内のサブディレクトリからも検出されます。これにより、AGENTS.md ファイルを、そのファイルが記述するコードの隣に配置することができます（たとえば、1 つは `services/api/` に、もう 1 つは `packages/ui/` に配置するなど）。それぞれのファイルは、他のステアリングファイルと同様に、ステアリングコンテキストとして読み込まれます。

## インクルードモード

ステアリングファイルは、必要に応じて異なるタイミングで読み込まれるように設定できます。この柔軟性により、パフォーマンスを最適化し、必要なときに適切なコンテキストが利用可能になります。

インクルードモードは、ステアリングファイルの先頭にフロントマターを追加することで設定します。フロントマターは YAML 構文を使用し、ファイルの先頭、3 つのダッシュ（`---`）で囲まれた場所に配置する必要があります。

### 常に読み込む（デフォルト）

yaml

```yaml
---
inclusion: always
---
```

これらのファイルは、すべての Kiro インタラクションに自動的に読み込まれます。すべてのコード生成や提案に影響を与えるべき中核的な標準については、このモードを使用してください。例としては、技術スタック、コーディング規約、基本的なアーキテクチャの原則などが挙げられます。

**最適な用途**：ワークスペース全体に適用される標準、技術的な選定基準、セキュリティポリシー、および普遍的に適用されるコーディング規約。

### 条件付き読み込み

yaml

```yaml
---
inclusion: fileMatch
fileMatchPattern: "components/**/*.tsx"
---
```

指定されたパターンに一致するファイルを扱う場合にのみ、ファイルが自動的に組み込まれます。これにより、文脈に沿った状態を維持し、必要な場合にのみ専門的なガイダンスを読み込むことで、不要な情報を減らすことができます。

配列を使用して複数のパターンを指定することもできます：

yaml

```yaml
---
inclusion: fileMatch
fileMatchPattern: ["**/*.ts", "**/*.tsx", "**/tsconfig.*.json"]
---
```

**一般的なパターン**：

- `"*.tsx"` - ReactコンポーネントおよびJSXファイル
- `"app/api/**/*"` - APIルートおよびバックエンドロジック
- `"**/*.test.*"` - テストファイルおよびテスト用ユーティリティ
- `"src/components/**/*"` - コンポーネント固有のガイドライン
- `"*.md"` - ドキュメントファイル
- `["**/*.ts", "**/*.tsx"]` - すべての TypeScript ファイル
- `["*.js", "*.jsx", "*.ts", "*.tsx"]` - すべてのJavaScriptおよびTypeScriptファイル

**最適な用途**：特定のファイルタイプにのみ適用される、コンポーネントパターン、API設計ルール、テスト手法、デプロイ手順などのドメイン固有の標準。

### 手動での組み込み

yaml

```yaml
---
inclusion: manual
---
```

チャットメッセージ内で ``#steering-file-name`` と指定することで、必要に応じてファイルを利用できます。これにより、すべてのやり取りを煩雑にすることなく、特定のコンテキストが必要なタイミングを細かく制御できます。

**使用方法**：チャットで `#troubleshooting-guide` または `#performance-optimization` と入力すると、そのステアリングファイルが現在の会話に組み込まれます。手動のステアリングファイルはスラッシュコマンドとしても表示されます。チャットで `/` と入力すると、それらを確認・選択できます。

**最適な用途**：特殊なワークフロー、トラブルシューティングガイド、移行手順、またはたまにしか必要とされないコンテキストの多いドキュメント。

### 自動組み込み

yaml

```yaml
---
inclusion: auto
name: api-design
description: REST API design patterns and conventions. Use when creating or modifying API endpoints.
---
```

リクエストが説明文と一致すると、ファイルが自動的に組み込まれます。[これはスキルと同様の仕組みで](https://kiro.dev/docs/skills/)、Kiroは説明文に基づいて、どのタイミングでステアリングファイルが関連性を持つかを判断します。

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| `name` | はい | ステアリングファイルの識別子。表示および照合に使用されます。 |
| `description` | はい | このファイルをいつ読み込むか。Kiroはこれとリクエストを照合します。 |

自動読み込みされるステアリングファイルは、チャット内でスラッシュコマンドとしても表示されます。説明文との一致に基づく自動起動に加え、`/` の後にステアリングファイル名を入力することで、明示的に読み込むことも可能です。

**最適な用途**：関連性がある場合にのみ読み込むべき、文脈に依存するガイダンス。たとえば、専門的なドメイン知識、複雑なワークフロー、あるいは常に有効なステアリングでは情報過多になりがちな詳細な参考資料など。

## ファイルの参照

ステアリングを最新の状態に保つために、ライブワークスペースのファイルへのリンクを指定します：

markdown

```markdown
#[[file:<relative_file_name>]]
```

例：

- API仕様：`#[[file:api/openapi.yaml]]`
- コンポーネントパターン: `#[[file:components/ui/button.tsx]]`
- 設定テンプレート: `#[[file:.env.example]]`

## セッション中の操作

永続的なステアリングファイルに加え、チャットで指示を与えることで、どのセッション中でもKiroをリアルタイムでステアリングすることができます:

- 「リポジトリの既存のエラー処理パターンを使用する」
- 「UserService クラスと同じアプローチに従う」
- 「単体テストだけでなく、統合テストも必ず追加するように」

## コードレビューを通じた指導

Kiro Webでは、プルリクエストにフィードバックを残すことでエージェントを誘導できます。「常に当社の標準的なエラー処理を使用してください」や「命名規則に従ってください」といった指導をPRにコメントすると、エージェントはそれを学習し、すべてのリポジトリにおける今後の作業にそれらのパターンを適用します。

エージェントの学習に影響を与えるのは、あなた（タスクを作成したユーザー）のフィードバックのみです。他のレビュアーのコメントは、エージェントの学習内容には影響しません。

## ベストプラクティス

**ファイルの内容を絞り込む** - 1つのファイルに1つのドメインを**限定する** - API設計、テスト、またはデプロイ手順など。

**明確な名前を使用する**：

- `api-rest-conventions.md` - REST APIの標準
- `testing-unit-patterns.md` - 単体テストの手法
- `components-form-validation.md` - フォームコンポーネントの標準

**文脈を含める** - 単に標準が何であるかだけでなく、その決定に至った理由を説明する。

**例を示す** - コードスニペットや「変更前／変更後」の比較を用いて、標準を実証する。

**セキュリティ最優先** - APIキー、パスワード、機密データを絶対に含めないでください。ステアリングファイルはコードベースの一部です。

**定期的なメンテナンス**：

- スプリント計画やアーキテクチャ変更の際にレビューを行う
- リファクタリング後はファイル参照をテストする
- ステアリングファイルの変更をコードの変更と同様に扱い、レビューを義務付ける

## 一般的なステアリングファイルの戦略

**API標準** (`api-standards.md`) — RESTの規約、エラー応答形式、認証フロー、バージョン管理戦略を定義する。エンドポイントの命名規則、HTTPステータスコードの使用方法、リクエスト/レスポンスの例を含める。

**テストアプローチ**（`testing-standards.md`） - ユニットテストのパターン、統合テストの戦略、モックの使用方法、およびカバレッジの目標を確立します。推奨されるテストライブラリ、アサーションのスタイル、およびテストファイルの構成を文書化します。

**コードスタイル** (`code-conventions.md`) - 命名規則、ファイル構成、インポート順序、およびアーキテクチャ上の決定事項を規定します。推奨されるコード構造、コンポーネントパターン、および避けるべきアンチパターンの例を含めます。

**セキュリティガイドライン** (`security-policies.md`) - 認証要件、データ検証ルール、入力のサニタイズ基準、および脆弱性防止策を文書化する。アプリケーション固有のセキュアコーディングの実践例を含める。

**デプロイメントプロセス** (`deployment-workflow.md`) - ビルド手順、環境設定、デプロイメントの手順、およびロールバック戦略の概要を記載します。CI/CDパイプラインの詳細や、環境固有の要件を含めます。
