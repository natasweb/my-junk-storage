ワークフローの実行では進行状況が保持されるため、一度離れても、完了済みの作業を再実行することなく再開できます。 IDE、CLI、Webのいずれの環境においても、Kiroがノードの状態、出力、アーティファクト、繰り返し進捗、カーソルの監視、およびセッションのステップ実行を永続的な境界でチェックポイントとして保存する間、実行は親の会話と接続されたまま維持されます。表示される経過時間は、アクティブな実行時間をカウントし、実行が一時停止していた時間は除外されます。

## 親チャットから進行状況を追跡

バックグラウンドで実行されるワークフローは、メインの会話の進行を妨げません。Kiroは、ワークフローの起動を確認し、ステップの実行中に進捗状況を報告し、完了した実行とその成果物を確認し、親チャットで結果をまとめて表示することができます。「[ワークフロー](https://kiro.dev/docs/workflows/)」の[概要](https://kiro.dev/docs/workflows/)では、そのような実行の全過程を追跡できます。

Kiro Webでは、親セッションと実行の詳細が併せて表示されます：

- **「ワークフロー」**には、実行、ネストされたノード、ステータス、経過時間、エージェント、モデル、工数、およびステップのアクティビティが表示されます。
- **「概要」には、**セッションの結果がまとめられて表示されます。
- **「ファイル」では、**実行中に生成または変更されたワークスペースのファイルを確認できます。
- **「成果物」では、**ワークフローによって明示的に公開された出力が表示されます。

親チャットでの進捗報告と、選択したステップへのダイレクトメッセージは、それぞれ異なる目的を持ちます。進捗の解釈、より広範な問題の解決、または次の対応の決定については、メインのエージェントに依頼してください。そのエージェントの現在のタスクに直接関係するガイダンスが必要な場合は、ステップにメッセージを送信してください。

親チャットとステップ間のチャネルは、実行中のどの時点でも双方向で機能します。ステップは、`send_message`シグナルを通じて外部に報告を行います。ガイダンスは、次のいずれかの経路でステップに届きます。クライアント上で選択したステップに直接メッセージを送るか、親チャット内のメインエージェントにステップが何をすべきかを伝え、メインエージェントがそのガイダンスをステップのセッションに配信します。 実行中のステップは、次のターンでガイダンスを受け取ります。一時停止中のステップは、それを待っていた返信として扱います。

## 実行の検索と確認

親チャットの上部にある**「ワークフロー」**を開きます。このエリアには、セッションの実行一覧が表示されます。実行を展開してステップツリーとステータスを確認し、ステップを選択すると、専用の「**ワークフローステップ」**タブが開きます。このタブにはステップとエージェントの情報が表示され、ステップ独自のメッセージ履歴が保持されます。また、実行が継続している間、親チャットの横に表示されたままにしておくことができます。

親の実行カードには、処理がアクティブな間、**「一時停止」**と**「停止」**が表示されます。展開されたステップの詳細には、選択されたエージェント、モデル、労力、およびアクティビティが表示されます。親チャットでの開始および完了の更新情報には、利用可能な場合、実行名、ID、タスク、出力成果物、経過時間、および推定使用量も表示されることがあります。

入力を必要とする実行では、「**あなたの対応が必要です」**というステータスが表示される場合があります。実行画面に戻り、一時停止中のステップを選択して直接回答するか、親チャット内のメインエージェントに依頼して、そのステップへ回答を転送してもらうことができます。

## 実行ステータスの理解

実行には5つのステータスのいずれかが報告され、`paused`では、それぞれ異なる対応が必要な3つの状況に対応しています。クライアントが提供する操作は画面によって異なりますが、ステータスおよび実行がステータス間を移行する条件は、すべての画面で共通しています。

| ステータス | 意味 | 次の操作が可能です | 以下の操作が可能です |
| --- | --- | --- | --- |
| `running` | Kiroがノードを実行中、またはスケジューリング中 | **一時停止**（次のノード境界で有効になります。それまではステータスは「`running`」のままです）または**停止** | ステップが入力を要求した場合（`paused`）、必要なトップレベルノードがすべて完了した場合（`completed`）、またはノードが失敗した場合（`failed`） |
| `paused` ・入力が必要 | 「`send_message`」というステップが、深刻度「`warning`」で呼び出されており、あなたの操作を待っている | **一時停止中のステップで応答する**（そのターンが実行されている間、実行状態は「`paused`」のままとなる）、または**停止する** | ステップを停止すると、「`success`」（`running`）または「`error`」（`failed`）のシグナルが送信されるか、再度要求が行われます（`paused`のままになります） |
| `paused` ・境界で | 要求された一時停止が、安全なノード境界で有効になった | 永続化された状態から**再開するか**、**停止する** | 再開する（`running`） |
| `paused` ・反復回数の上限 | 繰り返し処理が、`onMaxIterations: "pause"` により `maxIterations` に到達しました | **再開**（）を選択すると、反復回数は増加しないため、繰り返しは同じ上限に達して再び一時停止します。あるいは、**停止するか**、残りの計画を見直してください | 停止するか、修正された計画が残りの作業に取って代わる |
| `completed` | 必要なすべてのトップレベルノードが完了した | 実行とその成果物を検査する | ターミナル |
| `failed` | ノードが失敗し、その失敗が実行に波及した | 失敗したノードが再試行可能な場合は**再試行する**：失敗したターゲットはリセットされ、完了した兄弟ノードは保持される | 再試行（`running`）を行う。そうでない場合は終了 |
| `aborted` | 実行が停止されたか、`onMaxIterations: "abort"` が使用された | 再試行可能な作業が残っている場合は**再試行する** | 再試行（`running`）を行う。そうでない場合は終了する実行が停止されたか、 が使用された再試行可能な作業が残っている場合は再試行する |

ノードは、`pending` または `skipped` である場合もあります。各リピート反復では、その本体に対して新しい状態エントリのセットが作成されるため、同じ静的ノード ID が反復ごとに 1 回ずつ出現する可能性があります。各クライアントが公開するこれらの制御のどれが該当するかは、[「適切な実行制御の選択」](https://kiro.dev/docs/workflows/manage/#choose-the-right-run-control)に記載されています。

## ステップが入力を必要とする場合の応答

ステップは、セッションのコンテキストを失うことなく、情報を要求して一時停止することができます。ステップエージェントは、重大度を`warning`に設定して`send_message`を呼び出すことでこれを通知します。Kiroは、返信があるまでステップと実行を一時停止します。

返信は、一時停止中のステップのセッションに届く必要があります。最も直接的な方法は、クライアントでそのステップを開き、そこで回答することです。以下のタブにその場所が示されています。 また、親チャットを通じて回答することも可能です。その場合は、メインエージェントに回答を一時停止中のステップへ転送するよう依頼すると、メインエージェントが代わりにそのステップのセッションへ回答を届けてくれます。その指示なしに親チャットに入力された通常のメッセージは、ステップへの回答ではなく、メインエージェントとの会話となります。

1. 親チャットの上部にある「**ワークフロー」**を開きます。
2. 実行を展開します。
3. 一時停止中のステップを選択します。Kiroがその**ステップ**専用の「**ワークフローステップ」**タブを開きます。
4. **「このステップのエージェントにメッセージを送信**」で通常のテキスト返信を送信します。

Kiroはメッセージを保留中のステップを経由してルーティングし、同じバックグラウンドセッションで別のターンを実行します。ステップが完了するか失敗するまで、実行は保留されたままになります。

どちらのルートを選択しても、返信は一時停止中のステップ自身のセッションに届きます。親チャットは、せいぜいその返信を入力した場所にとどまります。 次に何が起こるかは 3 つの要素によって決まります。下の図は、1 つの返信がこれらすべてを経由する流れを示しています。ステップは履歴をそのまま維持して継続し、次の「`send_message`」シグナルが分岐を選択し、「`success`」のみが実行を新しいセッション内の次のノードへと進めます。「`warning`」は同じセッションを再び一時停止させ、「`error`」は実行を終了させます。

1/6・send_message・警告

一時停止中。6ステップ中の1ステップ目。

ノードを選択するか、実行を再開してください。

一時停止中のステップ · セッション 7f2

次へ send_message

重大度？

警告↺ 7f2のままで、再び一時停止

エラー終了：実行に失敗しました

`triage`セッション 7f2 · 一時停止中 · 入力待ち

Send_message · 警告。

triageが入力を求め、実行が一時停止する

行き先：セッション 7f2。そこで入力されたか、メインエージェントによって中継されたもの。親は、ステップがシグナルを送ったときにのみ結果を把握します。

あなたの返信は、一時停止中のステップ自身のセッションに届きます。その次のシグナルが分岐を選択し、成功した場合のみ新しいセッションへと進みます

上記の流れは、ステップが入力を要求した際の Kiro の組み込みの一時停止機能です。レシピ作成者は、`completion` を使用してステップを明示的に対話型にすることもできます。これにより、条件が満たされるまで、各返信の後もステップが開いたままになります：

json

```json
{
  "type": "step",
  "id": "triage",
  "agent": "wf-planner",
  "prompt": "Investigate the flaky test and refine a fix plan with the user.",
  "completion": {
    "completionSignal": "success"
  }
}
```

各ターン終了後、Kiroは`completion`を評価します。これがfalseのままである場合、ステップはそのセッション内で次のメッセージを待ちます。

Kiroでは、兄弟ステップが実行を継続している間に、ある分岐のみを入力待ちの状態に留めておくことができないため、対話型ステップは`parallel`内部では実行できません。

## 適切な実行制御を選択する

| アクション | 意味 |
| --- | --- |
| 一時停止 | アクティブなエージェントを完了状態にし、安全なノード境界で一時停止します。 |
| 再開 | 一時停止した実行を、永続化された状態から継続する |
| 停止 / キャンセル | アクティブな処理を中断し、ファイルの変更を元に戻さずに実行を`aborted`としてマークする |
| 再試行 | 再試行可能な失敗した処理を、完了済みの兄弟ノードを保持したまま「`pending`」の状態にリセットします。CLIおよびWebターミナル上で、失敗したノードを含む実行時に利用可能です。 |

**「ワークフロー」**で実行を開き、実行コントロールを使用します：

- **「一時停止」は、**次のノード境界で協調的な一時停止を要求します。
- **「再開」は、**一時停止中の実行を続行します。
- **「停止」は、**アクティブな処理を中断し、実行を`aborted`としてマークします。

現在の IDE UI には「再試行」機能は提供されていません。完了または失敗後にレシピを繰り返し実行するには、ワークスペースを確認した後、新しい実行として開始してください。

### 安全な一時停止

「一時停止」は協調的です。一時停止要求が受け入れられたからといって、実行がすでに停止したわけではありません。Kiro が次のノード境界に到達するまでは、アクティブなエージェントのターンが継続する可能性があります。エージェントによる処理がもう行われていないとみなす前に、実行のステータスが「`paused`」になるまで実行状況を点検してください。

### 再開

「`onMaxIterations: "pause"`」によって一時停止されたリピートは、固定された予算を使い果たしています。「再開」を行っても反復回数は増えず、リピートは同じ上限に達して再び一時停止します。残りの計画を見直すか、実行を停止して修正したレシピを新しい実行として開始してください。

### 停止またはキャンセル

**「Stop**」、「`/workflow cancel`」、または「`Ctrl+X`」は、作業を直ちに停止する必要がある場合にのみ使用してください。キャンセル操作は、ファイル操作の途中のステップを中断する可能性があります。すでに変更されたファイルは、変更されたままになります。ワークスペースを確認し、バージョン管理機能を使用して不要な部分的な編集を破棄してから、再実行してください。

### 再試行

CLI では、失敗したすべての処理、または選択した失敗／中止されたノードを再試行できます:

bash

```bash
/workflow retry <workflowId>
/workflow retry <workflowId> <nodeId>
```

Kiroは、再試行対象をそれぞれ`pending`にリセットし、そのステップセッション、タイムスタンプ、キャプチャされた出力、ノードアーティファクト、失敗メタデータ、完了メタデータ、対話状態、およびウォッチ状態をクリアします。また、完了済みの兄弟作業を保持したまま、実行が対象に到達できるよう、ターミナルの親プロセスを再オープンします。

再試行では、ワークスペースのファイルは元に戻りません。再試行する前に、未完了の編集内容を確認してください。完了した実行は、現在のCLI UIでは再試行できません。レシピを再度起動して、新しい実行を作成してください。

## 複数の実行を管理する

各実行には、独自のワークフロー ID と状態ツリーがあります。レシピファイルは出力パス、Git ブランチ、またはワークツリーを分離しないため、2 つの実行が同じチェックアウトを編集したり、同じアーティファクトを上書きしたりする可能性があります。

- IDE では、親セッションの詳細にある [**Workflows]** の下にある実行リストを使用します。
- CLI では、``/workflow`history` または ``/workflow list`` を使用し、ワークフロー ID を選択または指定してください。
- Web では、親の会話の横にある [**ワークフロー]** を開き、実行リストから実行を選択します。
- 並行して実行される実行には、異なる`run_dir`とアーティファクトパスを指定してください。
- 実行間で同じファイルを編集する可能性がある場合は、別々のワークツリーまたはワークスペースを使用してください。

## 実行が終了したら

完了は単なるステータスの変更ではなく、引き継ぎです。メインエージェントは、実行内容を検査し、宣言された成果物や関連ファイルを読み取り、要求された証拠を検証し、親の会話で結果を要約することができます。

有用な完了要約には、以下の項目を記載します：

- 結果とワークフロー ID;
- 完了したステップ、および実行されたループやレビュー；
- 作成または変更されたファイル；
- 成果物と機械可読な判定結果；
- 実行された検証および未検証のまま残っている項目。

Kiro Webでは、**「Summary」**、「**Files**」、「**Artifacts**」を使用して、その証拠を直接確認できます。レシピまたはステップエージェントは、アーティファクトを生成し、公開する必要があります。実行中に作成されたすべてのファイルが、自動的に宣言されたアーティファクトになるわけではありません。

## まだ開始されていない作業を修正する

実行中または一時停止中のワークフローは、すでに実行されたノードを維持したまま、残りのトップレベル計画を置き換えることができます。

- 完了した作業および現在実行中の作業は変更できません。
- ステップがアクティブな場合、Kiro は次のステップ境界まで置換をキューに入れます。
- 実行中のステップがない場合（実行が一時停止している場合を含む）、Kiro は置換を直ちに適用できます。
- 修正後のツリー全体は、スキーマ、ID、ネスト、ステップ数、テンプレート、エージェント、およびウォッチの検証に合格している必要があります。
- キューに入れられた置換が検証に失敗した場合、Kiro はその置換を拒否し、元のプランを続行します。

プランを修正できるユーザーは、実行構造によって決まります。

| 呼び出し元 | 現在のステップを更新する | 残りのプランを置換する |
| --- | --- | --- |
| ルートレベルにある、またはルートレベルのコンテナ内にネストされたステップエージェント | はい | はい |
| 実行を開始した親セッション | 現在のステップがない | はい |
| ステップ内で生成されたサブエージェント | いいえ | いいえ |

エージェントは、どちらのアクションにも`update_workflow`を使用します。通常の結果については、ステップは引き続き`send_message`を通じてシグナルを送信する必要があります。`update_status`は、意図的なオーバーライドのためのものです。プランの修正はエージェント／ランタイムの機能であり、すべてのクライアントが手動による修正制御を公開することを意味するものではありません。

## 監視の挙動を理解する

`watch` ノードは、リソースがアイドル状態である間、モデルのターンを消費することなく外部リソースをポーリングします。そのハンドラは、以下の3つの結果のいずれかを返します：

| 結果 | 効果 |
| --- | --- |
| `idle` | 次のポーリングを待機 |
| `new-activity` | このウォッチインスタンスを終了し、JSONペイロードを出力として公開する |
| `terminal-state` | ウォッチを終了し、リピートの`stopWhen`条件用にそのターミナルフラグをラッチする |

Kiroはウォッチカーソルとターミナル状態を実行とともに永続化するため、新規性追跡は再起動後も維持されます。中断と回復を経ても、配信は少なくとも1回行われるため、レスポンダーは重複する項目を許容する必要があります。`idleTimeoutSec`が設定されている場合、アイドル状態のウォッチはその期間経過後にターミナルアウトカムで終了します。設定されていない場合、ウォッチは無期限に待機し続けることができます。

2つのハンドラが組み込まれています。「`github-pr`」は、自身がすでに報告した内容を追跡します。「`command`」は、ポーリングごとに1回、ユーザーが記述したプログラムを実行し、そのプログラムが返すカーソルを保存します。したがって、何が「新規」とみなされるかはプログラム側で決定します。[「`command`」を使用して他のものを監視する方法については](https://kiro.dev/docs/workflows/authoring/#watch-anything-else-with-command)、[そちら](https://kiro.dev/docs/workflows/authoring/#watch-anything-else-with-command)を参照してください。

`publish-pr` パターンでは、`github-pr` ウォッチと、repeat ブロック内のレスポンダーを組み合わせます。「[パブリッシュとレスポンス」](https://kiro.dev/docs/workflows/patterns/#publish-and-respond)を参照してください。

## 中断後の復旧

Kiroは、ノード遷移後もワークフローの状態を完全に保持します。完了したステップ、記録されたターミナル出力、入力待ちの状態、キャプチャされた出力、アーティファクト、およびウォッチカーソルは、最後の永続化境界で維持されます。最終シグナルがないまま中断されたステップは、新しいステップとして初期プロンプトを再実行するのではなく、既存のステップセッション内で継続されます。 Kiroが再起動した後、一時停止中のステップに回答すると、同じステップセッションが再開され、その進行状況および完了シグナルによって実行ライフサイクルが継続します。

1. 実行を所有する親チャットセッションを再度開きます。
2. 親チャットの上部にある「**ワークフロー」**を開きます。
3. 実行を展開し、アクションを実行する前にそのステータスを確認してください。
4. 実行が「`paused`」の場合は、必要に応じて**「Resume」**を使用するか、一時停止中のステップに返信してください。
5. 「`failed`」または「`aborted`」の場合は、ワークスペースを確認し、修正したレシピを新しい実行として起動してください。現在の IDE には「Retry」コントロールはありません。

依然として「`running`」と報告されている実行では、「Resume」は受け付けられません。その親セッションまたはモニターを再度開き、アクティブなステップを確認してください。新しい出力がないまま「`running`」の状態が続く場合は、ワークフロー ID を記録し、クライアントの診断情報を収集してから、重複実行を開始してください。クライアントには、個別の手動による「リクレイム」制御機能はありません。

接続エラーの場合、ワークフローは最大24時間にわたり、その場で同じステップセッションを再試行し、最後の試行も失敗した場合に実行を一時停止します。最初の5分間は1分間に1回程度の頻度で再試行が行われ、それ以降の試行では、ジッターを伴いながら約2分間の待機時間が設けられます。 ターンが成功した場合、または明示的に再開された場合は、新しい再試行ウィンドウが開始されます。サービス5xxエラー、スロットリング、およびストリームの停止については、それぞれ独自の、より短い再試行動作が適用されます。

正確なストレージレイアウトおよびプロセス所有権の記録は、実装の詳細であり、レシピAPIの一部ではありません。

## トラブルシューティング

| 症状 | 確認項目 |
| --- | --- |
| IDEのワークフロー画面が表示されない | ワークスペースでワークフローを有効にしてから、新しいチャットセッションを開始してください |
| CLIのワークフローコマンドが表示されない | `/settings` → **Features** でワークフローを有効にし、Kiro CLI を再起動してください |
| レシピが表示されない | そのソースと優先順位を確認してください。プロジェクトファイルは、`.kiro/workflows/` 配下にあり、サポートされている拡張子が付いている必要があります |
| 実行がリテラル「`{{name}}`」で始まる | 起動時にベア入力が宣言または指定されていません |
| 出力またはアーティファクトテンプレートでステップが失敗する | プロデューサーが先に実行され、値をキャプチャまたは宣言していることを確認してください |
| 繰り返しの上限に達しました | 停止ファイル、JSONパス、期待値、および生成ステップを確認してください |
| 「再開」直後に「繰り返し」が一時停止する | 「再開」ではそれ以上の反復は許可されません。「[再開」](https://kiro.dev/docs/workflows/manage/#resume)を参照してください |
| ファイル条件が一致しない | 有効な JSON、正確な JSON パス/値、および許可されたワークスペースパスを確認してください |
| 検証は通過したが、実行の作成に失敗した | エージェント名、モデルへのアクセス権、およびウォッチハンドラーの設定を確認してください。スタンドアロンの検証では、ランタイムレジストリを完全にチェックすることはできません |
| `command` watchが即座に失敗する | プログラムが 2、126、または 127 で終了したか、JSON の形式が不正であるか、`cursor` が存在しない状態で 0 で終了しました。保存された stdin オブジェクトを使用して手動で実行し、stdout に JSON オブジェクトが正確に 1 つ含まれていることを確認してください |
| `command` watchが決して起動しない | `commandTimeoutSec`による強制終了を含め、それ以外のゼロ以外の終了コードはアイドル状態とみなされ、再試行されます。stderrで繰り返し発生するエラーを確認し、プログラムが単にカーソルを前進させるだけでなく、`new-activity`を報告していることを確認してください |
| 並列処理は高速化につながらない | Kiroはブランチを並行して開始しますが、速度向上ではなく、分離とjoinのセマンティクスのために`parallel`を使用してください |
| キャンセルされた実行では編集内容が保持されたままになる | キャンセルしてもファイルの変更は元に戻りません。ワークスペースを確認するか、元に戻してください |
| 一時停止されたステップは返信を無視します | テキストは、添付ファイルや親チャットだけでなく、そのステップ独自のセッションで送信してください |

## 運用上の制限

- レシピは、最大 8 レベルのネストと 50 個の静的 `step` ノードをサポートしています。
- すべての`repeat`には、正の`maxIterations`が設定されています。
- 繰り返し条件は反復の後に実行されるため、すべての繰り返しは少なくとも 1 回は実行されます。
- `parallel` 各ブランチに独自のコンテキストと結合ポリシー（`all`、`allSettled`、または `any`）を割り当てます。Kiro はブランチを並行して開始します。実測時間が短縮されると想定するのではなく、分離および結合のセマンティクスのためにこれを使用してください。
- ワークフローは、Gitブランチを分離したり、ワークツリーを作成したりすることはありません。
- クライアントのクローズおよびクライアント間のアタッチメントの挙動は、ここで文書化されているレシピ契約の一部ではありません。
