親チャットから始めましょう。期待される成果、制約条件、エージェント、および必要なレビューの深さを記述してください。Kiroが、そのタスクに合わせたワークフローを生成します。グラフを「レシピ」として保存しておけば、繰り返し利用したり、確認したり、共有したりする際に役立ちます。

ワークフローレシピとは、入力とノードのツリーを定義したJSONまたはYAMLファイルのことです。プロジェクトのレシピは、以下のいずれかの拡張子をつけて`.kiro/workflows/`に保存してください：

- `*.workflow.json`
- `*.workflow.yaml`
- `*.workflow.yml`

Kiroは実行時にこれらのファイルを検出します。同じファイル名（語幹）を持つファイルが、サポートされている複数の拡張子を使用している場合、JSONファイルが優先され、Kiroは他のファイルを競合として報告します。

ワークスペース間で利用可能にする必要がある個人用レシピは、`~/.kiro/workflows/`に保存してください。レシピ名の優先順位は、プロジェクト、ユーザー、同期されたアカウントのレシピ、そしてバンドルされたレシピの順です。無効な高優先度のレシピがあっても、有効な低優先度のレシピは非表示になりません。利用可能な同期済みおよびバンドルされたレシピは、アカウントやクライアントのバージョンによって異なる場合があります。

Kiro Webでは、**[設定] → [ワークフロー]** から、サポートされているレシピを1つアップロードしてください。`.kiro/workflows/`フォルダ全体をインポートするには、[[設定の同期]](https://kiro.dev/docs/web/cloud-configuration/) を使用してください。

## 2ステップのレシピを作成する

`.kiro/workflows/plan-and-implement.workflow.json` を作成する:

json

```json
{
  "name": "plan-and-implement",
  "description": "Plan a change, then implement it",
  "inputs": {
    "task": "prompt"
  },
  "steps": [
    {
      "type": "step",
      "id": "plan",
      "agent": "wf-planner",
      "prompt": "Create an implementation plan for: {{task}}. Do not edit files."
    },
    {
      "type": "step",
      "id": "implement",
      "agent": "wf-coder",
      "prompt": "Implement this plan, then run relevant tests:\n\n{{previous.output}}"
    }
  ]
}
```

「`plan`」ステップの最終出力は、`implement` の場合、「`{{previous.output}}`」となります。実行する前に、Kiro に保存されたレシピの検証を依頼してください：

```text
Run `validate_workflow` on `.kiro/workflows/plan-and-implement.workflow.json`. Report every error and warning, and do not launch the Workflow.
```

報告されたエラーを修正し、クライアントからレシピを実行します。 IDEでは、親チャットでKiroに保存されたレシピの実行を依頼し、タスクの説明を行ってください。その後、親チャットの上部にある**「Workflows」**を開き、「`plan`」ステップを選択して、専用の**「Workflowステップ」**タブを開きます。CLIでは、`/workflow run plan-and-implement --task "Describe the change"`を実行します。宣言された入力を省略した場合、Kiroが入力収集用のフォームを開きます。モニターで「`plan`」ステップを選択し、そのセッションを追跡してください。 Kiro Webでは、**[設定] → [ワークフロー]** でレシピをアップロードし、クラウドセッションでKiroにその実行を依頼してタスクの説明を行った後、**[ワークフロー]** を開き、[`plan`] ステップを選択して追跡したり、メッセージを送信したりします。

これらのエージェントは、レシピで使用するためにKiroに同梱されています。これらはワークフローが有効になっている間のみステップで使用可能であり、「`/agent`」ピッカーには表示されません。クライアントが提供する正確なリストは、Kiroが「`run_workflow`」を説明する際に表示されるものです：

| エージェント | 役割 |
| --- | --- |
| `wf-planner` | 読み取り専用の調査および計画；レポートや計画の作成 |
| `wf-coder` | 変更を実装し、テストを実行し、コミットする |
| `wf-design` | 技術設計を作成する |
| `wf-design-reviewer` | 要件に基づいて設計をレビューする |
| `wf-review-aggregator` | 複数のレビューレポートを1つに統合する |
| `wf-pr-submitter` | プルリクエストを開く、または既存のものを再利用し、そのURLを記録する |
| `wf-pr-responder` | プルリクエストへのフィードバックに対応する |
| `wf-auto-researcher` | イテレーションごとに1つの実験を提案、実施、評価する |
| `wf-workflow-creator` | タスクの説明に基づいてレシピの草案を作成する。これはオーケストレーターによって使用され、ステップ内では使用されない |
| `semantic_reviewer` | 行動ベースのコードレビュー。ワークフローステップエージェントおよび汎用サブエージェントの両方として登録される |

ステップのツールへのアクセス権は、`tools`および`excludedTools`の設定を含むエージェント定義に基づきます。無人ステップには範囲を限定したエージェントを使用し、レシピを実行する前に各エージェントが持つ権限を確認してください。

## ルートフィールド

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| `name` | はい | 安定したレシピ名 |
| `description` | いいえ | レシピセレクタに表示される目的 |
| `inputs` | いいえ | `prompt`、`file`、`string` などの自由形式の型ヒントへの入力名のマッピング。デフォルトは `{}` です。 |
| `modelId` | なし | ステップのデフォルトモデル。`auto` または省略の場合、親セッションから継承される |
| `effortLevel` | いいえ | ステップのデフォルトの推論負荷 |
| `steps` | はい | ワークフローノードの配列。最上位のノードは順に実行される |

入力型のヒントは、起動インターフェースが値を収集するのに役立ちますが、Kiroは実行時にそれらを強制しません。すべての裸のテンプレート変数を`inputs`で定義し、起動時にすべての値を指定してください。

## ノードの型

レシピはツリー構造です。ルートとなる ``steps`` 配列は暗黙のシーケンスであり、コンテナがネストされて制御フローを構成し、``step`` および ``watch`` ノードが処理を行う葉となります。

| 型 | 目的 | 必須フィールド |
| --- | --- | --- |
| `step` | 指定されたエージェントを独自のセッションで1つ実行する | `id`, `agent`, `prompt` |
| `sequence` | 子ノードを順序通りに実行する | `id`, `steps` |
| `repeat` | 条件に一致するか、上限に達するまで子ノードを実行する | `id`, `steps`, `maxIterations`, `onMaxIterations` |
| `parallel` | 独立した分岐をスケジュールし、その結果を結合する | `id`, `branches`, `joinPolicy` |
| `watch` | アイドル時にモデルターンを使わずに、ハンドラーを介して外部システムをポーリングする | `id`, `handler`, `config` |

以下のツリーは、小さな汎用レシピに各ノードタイプを1つずつ配置したものです。任意の行を選択すると、そのタイプが実行時にどのように動作するかを確認できます。バッジは、以降のすべての図で使用されているものと同じです。「`gate`」バッジはノードタイプではなく、「`stopCondition`」を示すものです。これは、「[停止条件の定義](https://kiro.dev/docs/workflows/authoring/#define-stop-conditions)」で説明されている、各反復後にリピートが評価するチェックです。

インデントと幹線は親子関係を表現します。バッジは、実行可能な末端ノード、再帰的なコンテナ、およびリピートの終了やステップの完了を許可する条件を識別します。詳細ペインは選択された行に追従します

すべてのノード `id` は、静的レシピ全体で一意でなければなりません。1つのレシピには、最大50個の **`step` ノード**を含めることができ、ノードは最大深度8までネスト可能です。リピートの反復は、追加の静的ステップスロットを消費しません。

## ステップの設定

`step`は、`id`、`agent`、`prompt`に加え、以下のオプションフィールドをサポートしています：

| フィールド | 動作 |
| --- | --- |
| `artifacts` | ステップによって生成されるファイルに論理名をマッピングします |
| `captureOutput` | 後のテンプレートで使用するために、ステップの最終アシスタントメッセージをキャプチャします。デフォルトは`true`です |
| `completion` | 停止条件が一致するまで、ステップを対話モードのまま維持します |
| `modelId` | ワークフローおよび親セッションのモデルを上書きします |
| `effortLevel` | ワークフローおよび親セッションの推論処理を上書きする |

要求された成果物を、ステップの最終応答とします。その応答は、`{{step-id.output}}` および `{{previous.output}}` が下流に渡すものです。

### `send_message` を使用して結果を通知する

ステップエージェントは、`send_message` ツールを呼び出すことで結果を通知します。このツールは親セッションに短いメモを投稿し、その `severity` はステップのライフサイクル信号としても機能します：

| `severity` | 記録されたシグナル | ステップへの影響 |
| --- | --- | --- |
| `success` | `success` | ステップが完了し、出力が取得され、ワークフローが進行する |
| `warning` | `need_input` | ステップと実行がユーザー入力を待つために一時停止する。ステップは、各ターン終了後も「`success`」または「`error`」を通知するまで一時停止状態を維持する |
| `error` | `error` | ステップが失敗する。失敗はツリー上へ伝播する |
| `info` | なし | 進捗の記録のみ。ライフサイクルへの影響なし |

Kiroはこのプロトコルをすべてのステップセッションに自動的に組み込むため、プロンプト内で説明する必要はありません。ただし、エージェントにシグナルを送る*タイミング*を伝えることは役立ちます。例えば、「テストに合格したら、`send_message`の深刻度で`success`を返して終了してください」といった具合です。`send_message`の呼び出しがなく、かつ`completion`の条件が満たされていない状態で終了するターンでは、ステップが完了します。

`send_message` これは双方向チャネルの「送信側」に相当します。ステップの実行中や待機中にも、ガイダンスがステップに届くことがあります。ステップが無人状態で実行されると仮定するのではなく、そのガイダンスを受け入れる余地を残したプロンプトを作成してください。[「ステップが入力を必要とする際の応答」](https://kiro.dev/docs/workflows/manage/#respond-when-a-step-needs-input)を参照してください。

## テンプレート変数の使用

ステップが読み取れるすべての値は、`{{...}}` テンプレートを介して渡されます。入力は起動時（launch）から、キャプチャされた出力は前のステップの最後のメッセージまたはウォッチ（watch）の JSON ペイロードから、アーティファクトは前のステップで宣言されたファイルから取得されます。テンプレートは、ステップのプロンプト、アーティファクトパス、停止条件のファイルパス、および「`watch`」ノードの「`config`」内の文字列値で機能します。

プロンプトは配線そのものです。以下のステップのいずれかを選択すると、そのステップが読み取るすべての値、各値の生成元となるステップ、および後続のステップに向けて公開する値を確認できます。トランスポートを使用して実行を遡ると、生成元がまだ完了していない値は琥珀色に変わります。これが、このセクションの残りの部分で詳述する順序付けのルールです：

| --- | --- |

| `{{input-name}}` | `inputs`で宣言された起動入力 |

構造化参照は、コンシューマよりも前に実行されるプロデューサーを指す必要があります。Kiroがそれらを解決できない場合、コンシューマステップは失敗します。特に：

- コンテナの最初のノードで `{{previous.output}}` を使用しないでください。
- 並列ブランチ内で`{{previous.output}}`を使用しないでください。ブランチの順序は保証されません。
- 後続の兄弟ノードや別の並列ブランチからの出力やアーティファクトを参照しないでください。

## 制御フローの構成

### シーケンス

`sequence` を使用して、順序通りに実行する必要があるノードに名前を付け、グループ化します。ルート `steps` 配列はすでに暗黙のシーケンスであるため、ネストによって実行計画が明確になる場合にのみ、明示的な `sequence` を追加してください。

### 繰り返し

repeatは常にその本体を少なくとも1回実行します。各反復が完了した後、Kiroは停止条件を評価します。条件に一致した場合、次の反復が始まる前にrepeatは完了します。`fileCheck`の場合、Kiroは`path`にあるJSONファイルを読み取り、`jsonPath`の値を`value`と比較します。 相対パスはプライマリワークスペースのルートから解決されます。ファイルが存在しない、または読み取れない場合、JSONが無効な場合、JSONパスが存在しない場合、あるいは値が一致しない場合は一致とみなされないため、繰り返し処理は継続されます。

json

```json
{
  "type": "repeat",
  "id": "implementation-loop",
  "maxIterations": 10,
  "onMaxIterations": "pause",
  "stopCondition": {
    "fileCheck": {
      "path": ".kiro/workflow-output/status.json",
      "jsonPath": "complete",
      "value": true
    }
  },
  "steps": [
    {
      "type": "step",
      "id": "implement-next-item",
      "agent": "wf-coder",
      "prompt": "Implement the next incomplete item and update .kiro/workflow-output/status.json."
    }
  ]
}
```

リピートでは、`stopCondition`と`stopWhen`の両方を省略できる。その場合、`maxIterations`まで処理が実行される。

終了時の動作を選択してください：

| `onMaxIterations` | 結果 |
| --- | --- |
| `abort` | リピートを中止し、実行を終了します |
| `continue` | リピートを完了し、その次の兄弟要素へ移動する |
| `pause` | 人間の判断を待つために一時停止する |

キャップで一時停止されたリピートを再開しても、反復回数は増加しません。すぐに再び一時停止されます。残りのプランを修正するか、実行を停止して、修正した定義を新しい実行として開始してください。

### 並列

並列ノードは、各分岐を独立してスケジューリングします：

json

```json
{
  "type": "parallel",
  "id": "reviews",
  "joinPolicy": "allSettled",
  "branches": [
    {
      "type": "step",
      "id": "security-review",
      "agent": "semantic_reviewer",
      "prompt": "Review the current changes for security issues."
    },
    {
      "type": "step",
      "id": "test-review",
      "agent": "semantic_reviewer",
      "prompt": "Review the current changes for missing tests."
    }
  ]
}
```

並列ノードがいつ確定するか、またある分岐の失敗によってその兄弟分岐がキャンセルされるかどうかを決定する3つのポリシーがあります：`all`、`allSettled`、および`any`です。一時停止された分岐は決してその兄弟分岐をキャンセルしません。例えば、ネストされたリピートが`onMaxIterations: "pause"`に達した場合などに、分岐は一時停止することがあります。以下の状況から1つ選び、各ポリシーがそれをどのように解決するかを確認してください。違いはタイミングとキャンセルの有無にあります。

図1.5: 並列結合 · 1つの状況、3つの答え

2つの分岐。親はどのような場合にどうすべきか…

ブランチ1が失敗し、ブランチ2が実行中の場合

- `all`直ちに失敗を報告し、ブランチ2をキャンセルする
- `allSettled`まだ実行中：ブランチ2が完了するまで待機し、その後「失敗」と報告するが、すべての結果は保持される
- `any`まだ実行中：ブランチ2はまだ完了可能であり、親を救うことができる

1つの失敗で残りが無意味になる場合は**「all」**を使用します。独立したレビューなど、すべてのブランチの証拠が必要な場合は**「allSettled」**を使用します。最初の有効な結果で十分な場合は**「any」**を使用します。

2つのブランチに何が起きたかを選択してください。各行には、1つのjoinPolicyがそれをどのように解決するか（どの兄弟ブランチをキャンセルするかも含めて）が表示されています

`completion` を使用した対話型ステップは、`parallel` 内にネストすることはできません。

### ウォッチ

A ``watch`` ノードは、変化がない間はモデルターンを消費することなく、ハンドラーを介して外部システムをポーリングします。ハンドラーが新しいアクティビティを報告すると、その JSON ペイロードが次のステップの ``{{watch-id.output}}`` となります。終端結果は ``stopWhen: "watch-id.terminal"`` として保持されます。2 つのハンドラーが組み込まれています：``github-pr`` はプルリクエストを監視し、``command`` はユーザーが記述したプログラムを実行するため、ワークフローはスクリプトや CLI が読み取れるあらゆるものを待機できます。

`idleTimeoutSec` この設定は、`config` ではなく、watch ノード自体に設定され、どちらのハンドラーにも適用されます。設定すると、その秒数だけアイドル状態が続いたウォッチは終端結果となり、その出力が `{"outcome": "idle-timeout", "idleTimeoutSec": <seconds>}` となるため、`stopWhen: "watch-id.terminal"` が発火し、後続のステップは引き続き実行されます。タイムアウトと実際のアクティビティの両方に対応できるよう、そのステップのプロンプトを記述してください。 アイドルクロックは、リピートがウォッチに再進入するたびに再起動され、リピートの`maxIterations`は、1回のエントリ内でのアイドルポーリングを制限しません。設定されていない場合は、ウォッチは無期限に待機します。

#### `github-pr` を使用してプルリクエストを監視する

ハンドラーを URL、または最上位の ``url`` フィールドにプルリクエストの URL が含まれるワークスペースの JSON ファイルに向けるように設定します。ファイル形式は、前のステップでプルリクエストを開き、その URL を記録する場合によく使われるパターンです：

json

```json
{
  "type": "watch",
  "id": "wait-for-pr",
  "handler": "github-pr",
  "config": {
    "prRef": ".kiro/workflow-output/pr.json",
    "pollIntervalSec": 60
  },
  "idleTimeoutSec": 3600
}
```

| `config` フィールド | 目的 |
| --- | --- |
| `prRef` または `url` | 次のいずれかが必要です：最上位に`url`を持つワークスペースのJSONファイル、またはPRのURLそのもの |
| `pollIntervalSec` | ポーリング間隔。デフォルトは 60、最小値は 30 |
| `includeOwnActivity` | 認証済みの `gh` アカウントによるコメントでウォッチを起動させるかどうか。デフォルトは `false` |
| `ignoreAuthors` | マーカーコメントを書き換えるボットなど、そのアクティビティによってウォッチが決して起動しないログイン |
| `commandTimeoutSec` | 各`gh`呼び出しに対するオプションのタイムアウト |

PRがマージまたはクローズされた際、ウォッチは`terminal-state`を報告します。新しいアクティビティが発生した際、`{{wait-for-pr.output}}`はレスポンダーのプロンプトが参照できるJSONオブジェクトとなります。すべてのキーが常に存在します：

json

```json
{
  "url": "https://github.com/org/repo/pull/42",
  "state": "OPEN",
  "newComments": [],
  "newReviews": [],
  "inlineComments": [],
  "excludedComments": [],
  "excludedReviews": [],
  "excludedInlineComments": [],
  "inlineCommentsFetch": "ok",
  "backlog": { "remaining": 0 },
  "headSha": "4b715b8b",
  "newFailedChecks": [],
  "passingCheckCount": 12,
  "pendingCheckCount": 3
}
```

`state` は、`OPEN`、`MERGED`、または`CLOSED`のいずれかです。`new*`配列には、ウォッチを起動させた未確認のアクティビティが格納され、`excluded*`配列には、無視された作成者による未確認のアクティビティが（コンテキスト情報としてのみ）格納されます。各アイテムはウォッチを最大1回のみ起動させます。編集や削除ではウォッチは起動しません。 配信の予算は、1回のポーリングにつきウォッチの起動に関連する項目10件（古い順）と設定されています。これを超える分は後のポーリングで処理され、「`backlog.remaining`」にカウントされます。最終ペイロードは予算の対象外であり、残りのすべての項目を伝送します。

CIチェックの失敗もウォッチを起動させます。`headSha`はチェックが実行された先頭のコミットであり、不明な場合は`null`となります。 各`newFailedChecks`エントリには、`name`、`workflowName`、`conclusion`、`detailsUrl`、`runId`、`startedAt`、および`completedAt`が含まれます。また、失敗はヘッドコミット、チェック名、詳細URL、完了時間ごとに1回報告されるため、赤色のままのチェックは毎回のポーリングで再起動されることはありませんが、新しいヘッドコミットや再実行の際は再起動されます。 失敗したチェックは決して予算に計上されず、失敗した Actions チェックはその実行が完了するまで保留されるため、1回のウェイクでその実行のすべての失敗が処理されます。`passingCheckCount` および `pendingCheckCount` にはその他の概要が記載されています。スキップされた、キャンセルされた、中立、および期限切れのチェックは、いずれもカウントされません。レスポンダーがチェックの詳細情報を必要とする場合は、`gh pr view <url> --json statusCheckRollup` を実行させてください。

中断と復旧をまたいだ場合でも、配信は少なくとも1回行われるため、レスポンダーのプロンプトは、項目が重複しても許容されるように記述してください。

`prRef` パスは、`fileCheck`のパスと同様に、ワークスペースのルートに限定されます。Kiroは実行が作成された際にハンドラーの設定を検証しますが、スタンドアロンの`validate_workflow`ツールでは、レジストリに依存するこのチェックを実行できません。

#### `command` でその他を監視する

スクリプトやCLIで変更の有無を確認できる場合（イシュートラッカーのチケット、デプロイ、別のCIシステムでのビルド、組み込みハンドラーのないツールでのレビューなど）は、`handler: "command"`を使用してください。Kiroはポーリングごとに1回プログラムを起動します。プログラムは変更の有無を確認し、結果を1つ出力して終了します。 「アイドル」の結果が返されると、エージェントのターンが回ってこない状態でウォッチのポーリングが継続されます。「新規アクティビティ」または「ターミナル状態」の結果が返されると、そのウォッチエントリが完了し、次のステップで `{{watch-id.output}}` からペイロードが読み込まれます。

json

```json
{
  "type": "watch",
  "id": "review",
  "handler": "command",
  "config": {
    "command": "node watch-review.mjs",
    "reviewFile": "mock-review.json",
    "pollIntervalSec": 10,
    "commandTimeoutSec": 5
  }
}
```

| `config` フィールド | 目的 |
| --- | --- |
| `command` | 必須。実行のワークスペース内で、セッションのデフォルトシェルによって実行される 1 つの静的なコマンドライン |
| `pollIntervalSec` | ポーリング間隔。デフォルトは 60、最小値は 10 |
| `commandTimeoutSec` | ポーリングごとのタイムアウト（秒単位）。オプション。正の値で、下限なし |
| その他 | 独自のキー。データとしてプログラムに渡される |

これらのフィールドに適用されるルール：

- シェルは、Windows では PowerShell、それ以外の環境では `$SHELL` です。
- 固定引数は`command`文字列内に記述してください。`args`キーは存在せず、これを含む`config`は拒否されます。`command`内のどこにあっても、`{{...}}`テンプレートは送信時に拒否されます。
- `commandTimeoutSec`が設定されていない場合、ポーリングは無限に待機し続けます。タイムアウトが発生すると、コマンドのプロセスツリー全体が終了し、古いカーソルを使用したアイドル状態のポーリングとして扱われるため、1回のポーリング処理が完了するのに十分な長さに設定してください。ノードの`idleTimeoutSec`はポーリングの合間にチェックされますが、ハングしたコマンドを中断することはありません。
- 独自のキーに含まれる最上位の文字列値はテンプレートをサポートしており、ウォッチが開始された際に展開されます。ネストされたオブジェクトや配列は展開されずにそのまま渡されます。これらをプログラム内のデータとして扱い、決してシェルテキストとして扱わないでください。

各ポーリングでは、1つのJSONオブジェクトがプログラムの標準入力に書き込まれた後、標準入力が閉じられます。`config`には、`command`を除くすべてのウォッチ設定キーが含まれています。`workspacePath`はプライマリワークスペースであり、プロセスの作業ディレクトリです。`additionalDirectories`には、その他のワークスペースのルートが一覧表示されています。実行の最初のポーリングでは、`cursor: null`が設定されます。

json

```json
{
  "cursor": null,
  "config": {
    "reviewFile": "mock-review.json",
    "pollIntervalSec": 10,
    "commandTimeoutSec": 5
  },
  "workspacePath": "/path/to/project",
  "additionalDirectories": []
}
```

このプログラムは、標準出力に JSON オブジェクトを正確に 1 つ書き出し、終了コード 0 で終了します:

json

```json
{
  "outcome": "new-activity",
  "cursor": { "revision": 1 },
  "payload": "{\"state\":\"OPEN\",\"summary\":\"Please add a test.\"}"
}
```

- `outcome` は、`idle`、`new-activity`、または `terminal-state` のいずれかです。
- `cursor` は必須であり、明示的な ``null`` を含め、任意の JSON 値にできます。決して省略してはなりません。Kiro はこれを不透明に保存し（アイドル状態のポーリング時も含む）、次のポーリングで返却し、反復処理を通じて保持し、実行が再開された際に復元します。 何が「新規」とみなされるかはプログラム側で決定します。KiroはペイロードやイベントIDを比較することはなく、新しい実行は`null`から開始されます。
- `payload` はオプションの文字列です。次のステップで構造化データが必要な場合は ``JSON.stringify`` を使用し、``new-activity`` および ``terminal-state`` の結果の両方にこれを指定してください。アイドル状態のペイロードはキャプチャされません。
- `targetId` は、監視対象のリソースに名前を付けるオプションの固定文字列です。Kiroは、実行ラベルが指定されていない場合にこれを使用して実行ラベルを導出しますが、イベントの重複排除には使用しません。

終了コードは、ポーリングの失敗が何を意味するかを決定します。有効な結果が得られた場合の終了コード 0 はポーリング結果となります。JSON の形式が不正、`outcome` が無効、または `cursor` が欠落している場合の終了コード 0 は、ウォッチノードの失敗を意味します。 終了コード 2 は無効な入力としてノードを失敗とみなします。また、終了コード 126 および 127 は、シェルがプログラムを実行できなかったか、プログラムを見つけられなかったためにノードを失敗とみなします。これは、その後のポーリングも成功しないことを意味します。 `commandTimeoutSec`による強制終了を含む、その他のゼロ以外の終了コードはアイドル状態のポーリングとみなされるため、一時的に異常状態になったプログラムでも、次のポーリングで再試行されます。 PowerShell はこれらの予約済みコードを保持しません。Windows では、これらが一般的な 0 以外の終了コードとして返され、ウォッチのポーリングが継続される可能性があるため、代わりに結果を通じてウォッチを終了させてください。説明付きのペイロードを伴う ``terminal-state`` を返し、終了コード 0 で終了します。

すべてのプロセス起動は、実行を開始したセッションの権限ポリシーを経由します。許可を求めるルールはプロンプトをそのセッションに送信し、拒否されるとウォッチノードは失敗します。ウォッチを一時停止またはキャンセルすると、開いているプロンプトが取り消されるため、遅れて回答しても効果はありません。 コマンドラインは、そのセッションに対する ``execute_bash`` コマンドが実行されるのと同じ方法で実行されます。つまり、サンドボックスがアクティブな場合はその内部で実行され、設定されたサンドボックスを準備できない場合はまったく実行されません。後者の場合、ノードは制限なしに実行されるのではなく、理由を明示して失敗します。 起動セッションが読み込まれていない実行は、そのセッションが読み込まれるまで待機し、詳細コード`ParentSessionUnavailable`で一時停止し、セッションが読み込まれると自動的に続行されます。削除された起動セッションは、ノードを失敗させます。

標準出力には、呼び出す CLI からの出力を含め、ログ、バナー、進行状況メッセージを出力せず、診断情報は標準エラーに出力してください。また、認証情報はどちらにも含めないでください。 Kiroはストリーム、カーソル、ペイロードに対してバイト制限やアイテム数制限を設けていないため、プログラム内でこれらを制限してください。ペイロードは実行と共に保存され、次のエージェントのプロンプトに表示される可能性があります。 実際のイベントストリームの場合は、少量のバッチと ID、または残りの部分に対するファイル参照を返し、配信済みまたは意図的に除外した項目を過ぎた分だけカーソルを前進させてください。配信は中断を挟んでも少なくとも 1 回行われるため、レスポンダーは重複を許容する必要があります。

以下の例ではネットワークは不要です。このスナップショットをワークスペース内の`mock-review.json`として保存してください。`revision`は、サマリーや状態が変更されるたびにインクリメントするカウンタです：

json

```json
{ "revision": 1, "state": "OPEN", "summary": "Please add a test." }
```

その隣に、ウォッチャーを「`watch-review.mjs`」として保存してください。これは、最初のポーリング時にスナップショットを報告し、リビジョンが変更されない間はアイドル状態を維持し、新しいアクティビティとしてより高いリビジョンを報告し、`OPEN` 以外の状態を終了として報告します：

js

```js
import { readFile } from 'node:fs/promises';
import { resolve } from 'node:path';

try {
  let input = '';
  for await (const chunk of process.stdin) input += chunk;
  const { cursor, config, workspacePath } = JSON.parse(input);
  const review = JSON.parse(
    await readFile(resolve(workspacePath, config.reviewFile), 'utf8')
  );
  const seen = cursor?.revision ?? 0;
  let result = { outcome: 'idle', cursor };
  if (review.state !== 'OPEN' || review.revision > seen) {
    result = {
      outcome: review.state === 'OPEN' ? 'new-activity' : 'terminal-state',
      cursor: { revision: review.revision },
      payload: JSON.stringify({ state: review.state, summary: review.summary })
    };
  }
  process.stdout.write(JSON.stringify(result) + '\n');
} catch {
  process.stderr.write('Invalid input or unreadable review file\n');
  process.exitCode = 2;
}
```

レシピに組み込む前に手動でテストしてください。上記の stdin オブジェクトを、ワークスペースの絶対パスを指定して `poll-input.json` として保存し、POSIX シェルで ``node watch-review.mjs < poll-input.json`` を実行するか、PowerShell で ``Get-Content -Raw poll-input.json | node watch-review.mjs`` を実行します。最初のポーリングでは、前述の ``new-activity`` という結果が出力されます。`{"revision":1}` をインプットの ``cursor`` にコピーして再度実行すると、プログラムは ``{"outcome":"idle","cursor":{"revision":1}}`` を出力します。 スナップショットをリビジョン 2 に変更し、同じ入力で再度実行すると、ペイロードに新しい要約が表示され、カーソルが進みます。実際のウォッチャーは、設定ミス（終了コード 2）と一時的なサービス障害（それ以外の非ゼロの終了コード）を区別する必要がありますが、このローカルな例ではその必要はありません。

ウォッチとそのレスポンダーを`repeat`内に配置し、`stopWhen`をウォッチではなくrepeatに指定します。repeatは本体の実行終了後に`stopWhen`をチェックするため、レスポンダーはターミナルペイロードに対しても実行されます：

json

```json
{
  "name": "mock-review-watch",
  "steps": [
    {
      "type": "repeat",
      "id": "review-loop",
      "maxIterations": 5,
      "onMaxIterations": "pause",
      "stopWhen": "review.terminal",
      "steps": [
        {
          "type": "watch",
          "id": "review",
          "handler": "command",
          "config": {
            "command": "node watch-review.mjs",
            "reviewFile": "mock-review.json",
            "pollIntervalSec": 10,
            "commandTimeoutSec": 5
          }
        },
        {
          "type": "step",
          "id": "respond-to-review",
          "agent": "wf-coder",
          "prompt": "Summarize this mock review without changing files. If MERGED or CLOSED, report that it is finished.\n\n{{review.output}}"
        }
      ]
    }
  ]
}
```

スナップショットの状態を`MERGED`に設定し、リビジョンをインクリメントして、終端の結果を処理し、ループが停止するのを確認します。

## 停止条件を定義する

上記のノード型ツリー内のゲート行は、`stopCondition`オブジェクトです。`stopCondition`をリピート内で使用するか、ステップの`completion`として使用します。オブジェクトに複数のフィールドが含まれている場合、いずれか1つでも一致すればループが停止するか、ステップが完了します。

| フィールド | 以下の場合に一致します |
| --- | --- |
| `containsText` | 最新のキャプチャされた出力に指定されたテキストが含まれている場合 |
| `completionSignal` | 最新のステップシグナルが「`success`」、「`need_input`」（`send_message`の深刻度`warning`として送信される）、または「`error`」である場合 |
| `fileCheck` | `jsonPath` にある JSON 値は、`value` と深さ同値です |

許可されたすべてのワークスペースのルート外にある `fileCheck` パスは、ノードの検証に失敗します。

`value` が配列の場合、Kiro はそれを「いずれか」のリストとして扱います。リテラル配列を別の配列で囲んでください：

json

```json
{
  "fileCheck": {
    "path": "result.json",
    "jsonPath": "labels",
    "value": [["ready", "reviewed"]]
  }
}
```

repeatでは、`stopCondition`の代わりに`stopWhen`を使用できます:

json

```json
{
  "stopWhen": "wait-for-pr.terminal"
}
```

json

```json
{
  "stopWhen": "{{aggregate.output}} contains VERDICT: APPROVED"
}
```

同じリピート内で両方の形式を設定しないでください。

## モデル、プロバイダー、およびステップごとの工数を選択します

各ステップでは、以下の順序でモデルと工数を決定します:

1. ステップのオーバーライド。
2. ワークフローのデフォルト。
3. 実行の作成時に取得された親セッションの設定。
4. ステップエージェントのデフォルト値。

継承するには、`modelId: "auto"`を使用するか、`modelId`を省略してください。工数値は、選択されたモデルによって異なります。 サポートされていない工数値は、ステップ セッションの作成時にそのモデルのデフォルト値に調整されます。不明なモデルは、警告のみが表示されて検証に合格しますが、フォールバックがないため、ステップの最初のモデル呼び出しで失敗します。そのため、推測されたモデル ID では、実行の途中で実行が失敗します。

各ステップが実行する役割の設定を選択してください：

- 要件定義、設計、困難な診断、または合成については、期待される品質の向上が追加の時間とリソースの使用を正当化する場合、より厳密な推論設定を使用してください。
- 機械的なセットアップ、特定の箇所に焦点を当てた編集、または独立して検証されるチェックについては、利用可能な低レイテンシ構成を使用してください。
- 判断の多様性が重要である場合は、独立したレビューブランチごとに、利用可能な異なるモデルまたはプロバイダーの設定を割り当ててください。
- 評価基準と成功基準を明確に定義してください。各ブランチ間の意見の不一致は、実験の証拠であり、ワークフローの失敗ではありません。

ワークフローの形状とモデルの選択は、組み合わせてテストできます。同じタスクセットを代替の`plan → execute → verify`グラフで実行し、品質、経過時間、推定使用量を成果物として記録した上で、宣言された評価基準と比較してください。ある広範なプロンプトで良好なパフォーマンスを示すモデルでも、作業が計画、実行、批評、修正の各ステップに分解されると、異なる挙動を示す場合があります。

プロバイダーの自動選択、フォールバック、またはパフォーマンスの最適化を前提としないでください。プロバイダー、モデル、およびリソースの利用可能性は、アカウントやクライアントによって異なります。リリース前にすべての`modelId`を検証し、現在の公開オプションについては[「利用可能なモデル」を](https://kiro.dev/docs/models/available-models/)参照してください。[「ワークフローの例」には、](https://kiro.dev/docs/workflows/patterns/#experiment-with-orchestration)比較の構成例が示されています。

## デプロイ前の検証

完全な JSON または YAML レシピを保存した後、`validate_workflow` を実行して、そのファイルを検証してから起動してください。このツールは、レシピが違反しているロード時の制約を報告します。これには以下が含まれます：

- スキーマエラーや無効な列挙型値；
- 重複するノードID;
- 50を超える静的ステップ、または8レベルを超えるネスト;
- `stopWhen`式の構文エラー；
- 構造化テンプレート内の無効な「happen-before」関係;
- ワークスペースの外にあることが証明できるファイルチェックパス;
- ワークフロー対応エージェントが必要な場所で、組み込みのサブエージェントが使用されている場合。

検証に合格したとしても、実行が開始できるとは限りません。スタンドアロンのバリデータでは、未知のカスタムエージェント名を拒否したり、実行時のウォッチハンドラの可用性や設定を検証したりすることはできません。Kiroは、実行を作成する際にこれらのチェックを行います。

## 作成チェックリスト

- すべてのノードに、一意で説明的な ID を割り当ててください。
- すべてのファイルの受け渡しは、許可されたワークスペースのルート内で行うこと。
- 実行開始前に、宣言されたすべての入力を用意してください。
- すべてのリピートに有限の`maxIterations`を設定し、上限の挙動を慎重に選択してください。
- 並列ブランチは互いに独立した状態に保ってください。
- ファイルはアーティファクトとして引き渡し、短いテキストはキャプチャされた出力として引き渡してください。
- 最終的な定義を検証し、長いタスクでそれを使用する前に、まず少量の入力で実行テストを行ってください。
