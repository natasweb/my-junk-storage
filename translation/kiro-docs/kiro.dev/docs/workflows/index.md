1回のエージェントセッションでは処理しきれないほど大規模な作業もあります。たとえば、要件定義、設計、実装、独立したレビュー、検証を必要とする機能などです。 また、見守っているよりも任せたほうがよい作業もあります。例えば、自分が他の作業を続けている間に完了すべき調査などです。ワークフローは、計画に基づいてエージェントのチームにこれら両方の作業を割り当てます。これは、すべてのステップを逐一確認することなく、その作業を完了させたい開発者やチームリーダーのためのものです。

このモデルは、どのエージェントがどの順序で作業を行うかを定義し、Kiroランタイムがその計画を実行するため、各ステップはリマインダーなしで時間通りに実行されます。 ワークフローは、エージェントのステップ、シーケンス、ループ、並列分岐からなるグラフであり、人間もエージェントも読み書きできる形式で構成されています。各ステップは新しいコンテキストを持つ独自のセッションで実行されるため、例えばレビュー担当者は、コーダーの思考プロセスを引き継ぐことなく作業を評価できます。

ワークフローはバックグラウンドで実行されます。委任された作業が進行している間も、メインの会話でKiroを使い続けることができ、各ステップのセッションは実行中に一時停止、再開、方向転換が可能であり、実行後にはフォローアップの質問のために再確認することもできます。 些細な調査であっても委任することで、ツールの出力結果や詳細な推論がメインの会話に混入するのを防ぎ、目の前の作業に必要なコンテキストを保持できます。

Kiroは、手元のタスクに合わせてワークフローを生成します。ワークフローを「レシピ」として保存して再利用したり、独自に作成したりすることもできます。

## エージェントから始める

最初にレシピを作成する必要はありません。親チャットで成果物を説明し、どの程度の構造化やレビューを希望するかを伝えます。V3セッションでは、Kiroはどのステップも実行する前に、承認を求めるために提案されたプランを表示します。開始前にそのステップやエージェントを確認することができます。 Kiro CLI 2.33.1以降では、「ワークフロー」を有効にしても、それだけでワークフローが開始されることはなくなりました。ワークフローは、明示的に実行を指示した場合にのみ実行されます。

Kiro CLI V3では、`/workflow run`ピッカーからレシピを選択すると、計画のプレビューが表示された確認フォームが開きます。Kiroがプロンプトに基づいてワークフローを作成する場合にも、同様の承認ステップが表示されます。

実行を開始する3つのプロンプト：

このリポジトリでの認証の仕組みを調査し、変更を行う前にリスクを報告してください。バックグラウンドで作業を行い、引用元を明記した要約を私に提出してください。

レート制限機能を新しいワークツリーで実装してください：要件定義、設計レビュー、計画策定、2名の独立したレビューアによる実装、および要件に対する最終検証を含めてください。

動作を変更せずにビルドを成功させてください。失敗を再現し、原因を1つずつ修正し、同じチェックを再実行してください。10回試行したら一時停止し、私に確認してください。

また、プロンプトやステアリングファイルを通じて、カスタムエージェント、優先モデル、各ステップごとの思考労力を指定したり、Kiroが作業をどのように分割するかを指示したりすることも可能です。Kiroには、自社チームが実際に使用している3つのレシピが同梱されています：`investigate`は読み取り専用の調査用、`feature-pipeline`は段階的な機能提供用、`publish-pr`はプルリクエストの作成とレビューフィードバックの処理用です。 いずれかのレシピを指定し、入力データを渡してください。KiroはJSON形式でレシピを生成しますが、YAMLもサポートされています。

Kiro CLI 2.33以降では、ワークフローが計画の承認を求める際、承認画面に簡潔なステップツリーが表示されます。各ステップにはエージェントに加え、計画で設定されたモデルと工数が表示されます。**Tabキー**を押すとツリー内を移動し、**Enterキー**でステップの詳細を表示または非表示にし、もう一度**Tabキー**を押すと選択肢画面に戻ります。 Kiro CLI 2.34以降では、承認画面に提案された変更を直接入力して、ワークフローが開始される前に計画を修正できます。 回答するまで何も実行されません。`/tools trust-all`が有効な場合、Kiroはワークフロー計画に対して「1回限りの許可」オプションで応答し、ルールは保存しません。確認するには、チャットからワークフローを開始し、承認を待ちます。実行が始まる前にステップの一覧が表示されます。

Kiro CLI 2.33以降では、組織が「自動モデル」を無効にしている場合でも、ワークフローは失敗することなく開始されます。

ワークフローは複数のエージェントを調整し、レビューを繰り返すため、単一のセッションよりも多くのトークンを消費します。これがトレードオフです。構造化や独立した判断が有益な作業にはそれに見合ったコストをかけ、小規模なタスクはチャット内で行うようにしてください。プランにおけるモデルの使用量の計算方法については、[「課金」を](https://kiro.dev/docs/billing/)参照してください。

## 有効にする

ワークフローは、すべてのクライアントでオプトイン方式となっています。レシピは、Kiro IDE、Kiro CLI、Kiro Web で同じファイルですが、ワークフローの有効化方法、レシピの取得元、および利用可能な制御機能は、クライアントによって異なります。

1. プロジェクトの「**ワークスペース設定」**を開きます。
2. **「ワークフロー」**を選択します。
3. ワークフローを有効にします。
4. 新しいチャットセッションを開始します。

バックエンドの設定は `kiroAgent.workflows.enabled` です。これはグローバルスイッチであり、オフの場合、Kiro は新しいワークフローを開始しませんが、既存のワークフローは実行され、レシピは引き続き利用可能です。変更は新しいセッションに適用されます。**「ワークフロー」**が表示されない場合は、お使いのアカウントではまだ利用できない状態です。

Kiro IDE 1.4.26 以降では、対象となる各トップレベルのチャットにも、「**ワークフローを使用」**コントロールがあります。これは、「**ワークフロー」**セクションの下部、親チャットの上、「**ワークフローに関するフィードバックを共有」**の隣に表示されます。 グローバル設定はワークフローが利用可能かどうかを決定し、「**ワークフローを使用」は、**そのセッション内でKiroがどの程度積極的にワークフローを自動開始するかを決定します。選択肢は以下の通りです：

- 「**要求があった場合のみ**」：アクティブなセッション内のタスクを処理し、ユーザーがワークフローを要求した場合にのみワークフローを開始します。これは、ローカルセッションで別のオプションを選択するまでの初期デフォルト設定です。その後、新しいチャットは記憶された選択設定で開始されます。
- **大規模なタスクのみ**：「**大規模なタスクのみ」**：複数ステップのタスクや、より多くのコンテキストを必要とするタスクに対して、自動的にワークフローを使用します。
- **「可能な限り**」：コードの読み込み、実装、テスト、レビューなど、ほとんどのタスクをワークフローに振り分けようとします。

各タスクの委任を自分で決定したい場合は「**依頼があった場合のみ**」を、「多段階の作業をバックグラウンドで実行しつつ、小規模なタスクはチャット内で処理したい」場合は**「大規模なタスクのみ」を**、「セッションの作業の大部分をワークフローとして実行し、追加のトークン使用を受け入れる」場合は**「可能な限り」**を選択することをお勧めします。

この設定は、Kiroの動作そのものではなく、判断の仕方を変更するものです。どの選択肢を選んでも実行が拒否されることはなく、実行中のワークフローは引き続き管理可能です。ローカルセッションでの直近の選択内容は、新しいチャットセッションでも引き継がれます。 クラウドセッションで行った選択は、そのセッションにのみ適用され、ローカルのデフォルト設定は変更されません。この設定は、ワークフローが有効になっている最上位のチャットでのみ表示されます。「**ワークフローステップ」**タブには表示されず、この設定が存在する以前に作成されたセッションにも表示されません。

確認するには、新しいチャットを開始し、その上の「**ワークフロー」**を開き、「**ワークフローを使用**」が、他のオプションを選択していない場合は「**求められた場合のみ**」、またはローカルセッションで最後に選択した内容になっていることを確認してください。

Kiroが提案されたワークフローステップの承認を求めた場合、IDEはそれらを権限カードに表示し、そこで**「許可」**または「**拒否」**を選択したり、フィードバックを送信したりできます。保存された権限決定は、カードを表示せずに後の提案を処理できます。「[Kiro IDEでの提案されたステップの確認」](https://kiro.dev/docs/workflows/manage/#review-proposed-steps-in-kiro-ide)を参照してください。

## ワークフローの構成

内部的には、ワークフローはグラフとして構成されています。エージェントステップ、シーケンス、ループ、並列分岐が、ユーザーと Kiro の双方が読み書き可能な形式で表現されています。ほとんどのレシピは、以下の 5 つの概念を通じて理解できます。

| 概念 | 意味 |
| --- | --- |
| **ステップ** | 1つのエージェントが、特定のコンテキストに焦点を当てた独自のセッション内で実行されます。ステップは他のステップのセッションを読み取ることはできず、明示的なハンドオフを通じてのみ、それ以前の結果を受け取ります |
| **ハンドオフ** | キャプチャされた出力または宣言されたアーティファクトが、後続のステップにエビデンスを渡す |
| **分岐と合流** | 独立したエージェントが同じ作業を評価し、その後、ポリシーがその結果を統合する |
| **ループ** | 一連のステップが、証拠が条件に一致するか、安全上限に達するまで繰り返される |
| **待機** | 実行中は、外部システムやプルリクエスト、あるいはスクリプトで確認可能なあらゆる項目を監視しますが、変化がない間はモデルのターンを消費しません |

親チャットと各ステップは双方向で接続された状態を維持します。ステップは、進行状況、質問、または結果を伝える`send_message`シグナルを外部へ報告します。実行中または一時停止中のステップはいつでも制御可能です。「[ステップが入力を必要とする際の対応](https://kiro.dev/docs/workflows/manage/#respond-when-a-step-needs-input)」を参照してください。

## バックグラウンドでの委任とサブエージェント

ワークフローでは、再利用可能なレシピや単一エージェントによるバックグラウンド委任のために`run_workflow`が追加されます。1つのカスタムエージェントをバックグラウンドで実行するには、メインエージェントが`run_workflow(agent://<name>)`を起動できます。

単一エージェントのワークフローは、通常の分離された委任と同様に動作しますが、バックグラウンドで実行されます。つまり、親チャットは利用可能な状態を維持し、実行状況を確認でき、処理中に進行状況が返されることもあります。Kiro CLI 2.34以降では、メインチャットがワークフローを開始するタイミングを[**ワークフローの使用設定で**](https://kiro.dev/docs/cli/chat/settings/#settings-features)制御できます。

| 状況 | 委譲の動作 |
| --- | --- |
| ワークフローが無効なメインセッション | Kiroはアクティブなセッション内の処理を処理し、直接サブエージェントを使用できます |
| **要求があった場合のみ**（デフォルト） | Kiroは、リクエストがあった場合にのみワークフローを開始します |
| **大規模なタスクの場合のみ** | Kiroは、複数のステップからなる作業や、より多くのコンテキストを必要とする作業に対してワークフローを開始できます |
| **可能な限り** | Kiroは、コードの読み込み、実装、テスト、およびレビューの大部分をワークフロー経由で行うよう努めます |
| ワークフロー内で実行されるエージェント | そのエージェントは、設定で許可されている場合、[サブエージェント](https://kiro.dev/docs/custom-agents/subagents/)を使用することも可能です |
| 再利用可能な多段階プロセス | ランタイムは、明示的なステップ、ハンドオフ、ループ、待機、およびリカバリを管理します |

ネストされたサブエージェントは、ワークフローステップが自身のタスクを分割するのに役立ちます。これらは親ワークフローのノードではなく、そのステップに代わってシグナルを送信したり、一時停止、完了、修正を行ったりすることはできません。

## クライアントのサポート

ワークフローは、Kiro IDE、Kiro CLI、および Kiro Web クラウドセッションで利用可能です。有効化、レシピへのアクセス、起動エントリポイント、および制御機能は、クライアントごとに異なります。

| 表示 | 開始 | 検査と操作 | 現在の操作 |
| --- | --- | --- | --- |
| IDE | 親チャットでKiroに尋ねるか、`/workflow-run`を使用して保存済みのレシピを選択し、その入力内容を完了させてください | 親チャットの上部にある**ワークフロー**。ステップを選択すると、そのステップ専用の「**ワークフローステップ」**タブが開きます | 一時停止、再開、停止 |
| CLI | `/workflow run` | ワークフロー履歴および全画面モニター | 一時停止、再開、停止、失敗/中止したジョブの再実行 |
| Web | クラウドセッションでKiroに質問する | **ワークフロー**、**概要**、**ファイル**、および**成果物**；ステップを選択してメッセージを送信 | 一時停止、再開、停止；ターミナル実行に再試行可能な失敗ノードがある場合の再試行 |

IDE 内で、Kiro は、リポジトリファイルを変更するワークフローに対し、実行開始時にチェックアウトされたブランチを使用するよう指示します。ワークフローがワークツリーを使用している場合、Kiro はそのブランチからワークツリーを作成し、終了時に同じブランチにリベースするよう指示します。

モバイルでの利用については、ここでは記載されていません。

## 調査から始める

`investigate`の例では、ソースファイルを変更せずにプロジェクトを読み込み、1つの引用レポートを出力します。具体的な成果を伴うメインチャットから始めましょう：

ワークフローを使用して、APIリクエストのタイムアウトがどこで設定されているかを調査します。優先順位のルールを説明し、関連するファイルやシンボルを引用し、プロジェクトを変更せず、レポートを`.kiro/reports/`として保存します。

Kiroは実行をバックグラウンドで開始し、親の会話を表示したままにしておくことができます。クライアント画面から実行の進捗を確認します：

親チャットの上部にある**「ワークフロー」**を開き、実行を展開して、`investigate` を選択します。Kiroは、ステップのセッション、エージェント、モデル、工数、アクティビティ、および**「このステップのエージェントへのメッセージ」**フィールドを含む専用の**ワークフローステップタ**ブを開きます。実行が継続している間、親チャットの横にこのタブを表示させておき、両方のコンテキストを追跡できるようにします。

## レシピの検索または作成

レシピは、ワークスペース（`.kiro/workflows/`）、ユーザー設定、アカウント用に同期されたレシピ、またはKiroにバンドルされているセットから取得できます。名前が重複する場合は、上位ティアの有効なレシピが優先されます。サポートされているファイル、優先順位ルール、およびWebインポートについては、[「ワークフローの作成」](https://kiro.dev/docs/workflows/authoring/)を参照してください。

バンドルされたレシピは有用な構成例を示しています。これらは実行可能な例であり、必須の方法論や、すべてのクライアントバージョンで保証される機能セットではありません。レシピを実行する前に内容を確認してください。副作用は、そのプロンプトと、選択されたエージェントのツールおよび権限の両方に依存します。

最初にレシピを手作業で記述する必要はありません。期待される結果と、必要な構造やレビューの程度を記述してください。Kiroは、そのタスクに合わせたワークフローを作成できます。再利用の価値があるようになったら、レビュー済みの定義を`.kiro/workflows/`に保存してください。

## セキュリティと信頼

ワークフローは、ユーザーが他の作業を行っている間も継続して実行されるバックグラウンドセッション内で、ユーザーに代わってエージェントを実行します。各ステップのセッションは、確認、一時停止、再開、または制御を行うためにいつでも利用可能です。 レシピで指定されたエージェントに応じて、そのステップではファイルの編集、シェルコマンドやテストの実行、コミット、プルリクエストの作成や対応を行うことができます。また、`command`による監視では、指定したプログラムがポーリングごとに1回実行されます。 エージェント定義では、`tools`および`excludedTools`の設定を通じて、ステップがアクセスできるツールが選択されます。そのため、レシピを実行する前に、そのレシピと指定されているエージェントを確認してください。ワークフロー自体によってエージェントが読み取り専用になることはありません。

ツールの可視性は権限とは別物です。すべてのステップセッションは、他のセッションと同様に権限チェックと承認プロンプトを経ます。実行を開始したセッションのユーザー、管理、ワークスペース、プリセット、およびセッションルールが、エージェント自身のルールとともに各ステップに適用され、適用されるルールの中で最も制限の厳しいものが優先されます。 エージェント自身の`allow`ルールは、実行を起動したセッションが許可していない権限を付与することはありません。[「サブエージェントの権限」](https://kiro.dev/docs/custom-agents/subagents/#sub-agent-permissions)を参照してください。`command`ウォッチは、実行を起動したセッションの権限ポリシーを通じてプログラムを実行します。許可を求めるルールは、そのセッションにプロンプトを送信し、拒否された場合はウォッチノードが失敗します。 ブランチのプッシュやプルリクエストへのコメントといったリモートアクションでは、ユーザー自身のリポジトリ認証情報が使用され、リポジトリのブランチ保護、必須チェック、承認ポリシーが、Kiroの権限プロンプトと併せて引き続き適用されます。 バンドルされている「公開して応答する」パターンでは、承認済みのプルリクエストが緑色で表示されますが、マージは行われません。[「公開して応答する」](https://kiro.dev/docs/workflows/patterns/#publish-and-respond)を参照してください。ワークフローがその計画の承認を求めた場合、Kiroは計画を表示し、ユーザーが回答するまで何も実行されません。`/tools trust-all`が有効になっている場合、Kiroは「許可」という1回限りのオプションでのみ回答し、ルールは保存されません。 信頼されていないワークスペースでは、Kiroはワークスペースの`.kiro/workflows/`ディレクトリからワークフローファイルをロードしません。ただし、ホーム、クラウド、バンドル済み、および生成されたワークフローは引き続き利用可能です。「[ワークスペースの信頼」](https://kiro.dev/docs/permissions/#workspace-trust)を参照してください。

ワークフローの範囲を狭めるには、そのステップで使用されるカスタムエージェントに`tools`と`excludedTools`を設定し、すべての繰り返しに有限の`maxIterations`を設定し、ウォッチに`idleTimeoutSec`を設定します。実行を停止するには、クライアントで**「停止」**を使用します。 `.kiro/workflows/`または`~/.kiro/workflows/`からレシピファイルを削除すると、そのローカルレシピの提供は停止されますが、同じ名前で優先順位が低いレシピがその代わりとなる可能性があります。すべてのワークフローを停止するには、[「有効にする」](https://kiro.dev/docs/workflows/#turn-it-on)の項で説明されている設定を無効にしてください。 レシピを実際に使用する前にその適用範囲を確認するには、レシピで指定されているエージェント定義を読み、まず少量の入力データで実行してみてください。
