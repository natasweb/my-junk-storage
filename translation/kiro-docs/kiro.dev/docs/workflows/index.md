ある作業は、1回のエージェントセッションでは処理しきれないほど大規模なものもあります。たとえば、要件定義、設計、実装、独立したレビュー、検証を必要とする機能などです。また、見守っているよりもむしろ他者に任せたい作業もあります。たとえば、自分が他の作業を続けている間に完了すべき調査などです。ワークフローは、計画に基づいて、エージェントのチームにこれら両方の作業を提供します。

このモデルは、どのエージェントがどの順序で作業を行うかを定義し、Kiroランタイムがその計画を実行するため、各ステップはリマインダーなしで時間通りに実行されます。 ワークフローは、エージェントのステップ、シーケンス、ループ、並列分岐からなるグラフであり、人間もエージェントも読み書きできる形式で構成されています。各ステップは、新しいコンテキストを持つ独自のセッションで実行されるため、例えばレビュー担当者は、コーダーの思考プロセスを引き継ぐことなく作業を評価できます。

ワークフローはバックグラウンドで実行されます。委任された作業が進行している間も、メインの会話でKiroを使い続けることができ、各ステップのセッションは実行中に一時停止、再開、方向修正が可能であり、実行後にフォローアップの質問をして再確認することもできます。 些細な調査であっても委任することで、ツールの出力結果や詳細な推論がメインの会話に混入するのを防ぎ、目の前の作業に必要なコンテキストを保持できます。

Kiroは、手元のタスクに合わせてワークフローを生成します。ワークフローを「レシピ」として保存して再利用したり、独自のワークフローを作成したりすることもできます。

レート制限機能を新しいワークツリーで実装してください：要件定義、設計レビュー、計画、2名の独立したレビューアによる実装、および要件に対する最終検証を含めてください。

動作を変更せずにビルドを成功させてください。失敗を再現し、原因を1つずつ修正し、同じチェックを再実行してください。10回試行したら一時停止し、私に確認してください。

また、プロンプトやステアリングファイルを通じて、カスタムエージェント、優先モデル、各ステップごとの思考労力を指定したり、Kiroによる作業の割り振り方法を制御したりすることも可能です。Kiroには、自社チームが実際に使用している3つのレシピが同梱されています：読み取り専用の調査用「`investigate`」、段階的な機能提供用「`feature-pipeline`」、プルリクエストの作成とレビューフィードバックの処理用「`publish-pr`」です。 いずれか1つを指定し、入力情報を渡してください。KiroはJSON形式でレシピを生成しますが、YAMLもサポートされています。

ワークフローは複数のエージェントを調整し、レビューを繰り返すため、単一のセッションよりも多くのトークンを消費します。これがトレードオフです。構造化や独立した判断が有効な作業にはより多くのリソースを割り当て、小規模なタスクはチャットで処理するようにしましょう。モデルの使用量がプランにどのように計上されるかについては、「[課金」](https://kiro.dev/docs/billing/)をご覧ください。

## 有効にする

ワークフローは、すべてのクライアントでオプトイン方式となっています。レシピは、Kiro IDE、Kiro CLI、Kiro Webで同じファイルですが、ワークフローの有効化方法、レシピの取得元、および利用可能な制御機能はクライアントによって異なります。

1. プロジェクトの「**ワークスペース設定」**を開きます。
2. **「ワークフロー」**を選択します。
3. ワークフローを有効にします。
4. 新しいチャットセッションを開始します。

バックエンドの設定は「`kiroAgent.workflows.enabled`」です。「**ワークフロー」**が表示されない場合は、お使いのアカウントではまだ利用できません。

## ワークフローの構成方法

内部的には、ワークフローはグラフとして構成されています。エージェントのステップ、シーケンス、ループ、並列分岐が、ユーザーとKiroの両方が読み書きできる形式で表現されています。以下の5つの概念を理解すれば、ほとんどのレシピを把握できます：

| 概念 | 意味 |
| --- | --- |
| **ステップ** | 1つのエージェントが、特定のコンテキストに焦点を当てた独自のセッション内で実行されます。ステップは他のステップのセッションを読み取ることはできず、明示的なハンドオフを通じてのみ、それ以前の結果を受け取ります |
| **ハンドオフ** | キャプチャされた出力または宣言されたアーティファクトが、後続のステップにエビデンスを渡す |
| **分岐と合流** | 独立したエージェントが同じ作業を評価し、その後、ポリシーがその成果を統合する |
| **ループ** | 一連のステップが、証拠が条件に一致するか、安全上限に達するまで繰り返される |
| **待機** | 実行中は、外部システムやプルリクエスト、あるいはスクリプトで確認可能なあらゆる項目を監視しますが、変化がない間はモデルのターンを消費しません |

親チャットと各ステップは双方向で接続された状態を維持します。ステップは、進行状況、質問、または結果を伝える「`send_message`」シグナルを外部へ送信します。実行中または一時停止中のステップはいつでも制御可能です。「[ステップが入力を必要とする際の応答](https://kiro.dev/docs/workflows/manage/#respond-when-a-step-needs-input)」を参照してください。

## バックグラウンドでの委任とサブエージェント

ワークフローでは、再利用可能なレシピや単一エージェントによるバックグラウンド委任を実現するために、`run_workflow`が追加されています。1つのカスタムエージェントをバックグラウンドで実行するには、メインエージェントが`run_workflow(agent://<name>)`を起動します。

シングルエージェントのワークフローは、通常の隔離された委任と同様に動作しますが、バックグラウンドで実行されます。つまり、親チャットは利用可能な状態を維持し、実行状況を確認でき、処理中に進行状況が返されることもあります。 CLI V3では、デフォルトで有効になっている「[**Workflows: sub-agent**](https://kiro.dev/docs/cli/chat/settings/#settings-features)」[**ツール**設定](https://kiro.dev/docs/cli/chat/settings/#settings-features)により、Workflowsと並行して`invoke_sub_agent`への直接委任が利用可能です。これを無効にすると、メインチャットの委任は`run_workflow`経由でのみルーティングされます。Workflowsが有効な場合、その他のクライアントは引き続きメインセッションの委任をWorkflows経由でルーティングします。

| 状況 | 委譲の動作 |
| --- | --- |
| ワークフローが無効なメインセッション | メインエージェントは、`invoke_sub_agent` を使用して、委任された特定の業務を行うことができます |
| ワークフローが有効で、「**ワークフロー：サブエージェントツール」**がオンになっているCLI V3（デフォルト） | メインエージェントは、`invoke_sub_agent` または `run_workflow` を使用できます |
| **ワークフロー**の**「サブエージェント」ツール**が無効なCLI V3、またはワークフローが有効な別のクライアント | メインエージェントは `run_workflow` を使用し、1つのカスタムエージェントについては `agent://<name>` も使用します |
| ワークフロー内で実行されているエージェント | そのエージェントは、設定で許可されている場合、引き続き[サブエージェント](https://kiro.dev/docs/custom-agents/subagents/)を使用できます |
| 再利用可能な多段階プロセス | ランタイムは、明示的なステップ、ハンドオフ、ループ、待機、およびリカバリを管理します |

ネストされたサブエージェントは、ワークフローステップが自身のタスクを分割するのに役立ちます。これらは親ワークフローのノードではなく、そのステップに代わってシグナルを送信したり、一時停止、完了、修正を行ったりすることはできません。

## クライアントのサポート

ワークフローは、Kiro IDE、Kiro CLI、および Kiro Web クラウドセッションで利用可能です。有効化、レシピへのアクセス、起動エントリポイント、および制御方法はクライアントごとに異なります。

| 表示 | 開始 | 検査と操作 | 現在の操作 |
| --- | --- | --- | --- |
| IDE | 親チャットでキロに尋ねる | 親チャットの上部にある**ワークフロー**。ステップを選択すると、そのステップ専用の「**ワークフローステップ」**タブが開きます | 一時停止、再開、停止 |
| CLI | `/workflow run` | ワークフロー履歴と全画面モニター | 一時停止、再開、停止、失敗／中止したジョブの再実行 |
| Web | クラウドセッションでKiroに質問する | **ワークフロー**、**概要**、**ファイル**、および**成果物**；ステップを選択してメッセージを送信 | 一時停止、再開、停止；ターミナル実行に再試行可能な失敗ノードがある場合の再試行 |

モバイルでの利用可能性については、ここでは記載されていません。

## レシピの検索または作成

レシピは、ワークスペース（`.kiro/workflows/`）、ユーザー設定、アカウント用に同期されたレシピ、またはKiroにバンドルされているセットから取得できます。名前が重複する場合、上位ティアの有効なレシピが優先されます。サポートされているファイル、優先順位ルール、およびWebインポートについては、[「ワークフローの作成」](https://kiro.dev/docs/workflows/authoring/)を参照してください。

バンドルされたレシピは有用な構成例を示しています。これらは実行可能な例であり、必須の方法論や、すべてのクライアントバージョンで保証される機能セットではありません。レシピを実行する前に内容を確認してください。副作用は、そのプロンプトと、選択されたエージェントのツールおよび権限の両方に依存します。

最初に手動でレシピを作成する必要はありません。期待される成果と、必要な構造やレビューの程度を記述してください。Kiroは、そのタスクに合わせたワークフローを作成できます。再利用の価値があるようになったら、レビュー済みの定義を`.kiro/workflows/`に保存してください。
