「仕様の正しさ」は、ある根本的な問いへの答えとなります。それは、「実装は実際に仕様通りに動作しているか？」という問いです。AIがコードを生成する場合、それが自分の意図と一致しているかどうかを、どのように確認すればよいのでしょうか？

## 概念

今日のテストのほとんどは*例ベースです*。各テストでは、特定の入力を持つ具体的なケースを設定し、1つの期待される結果を確認します。すべてのケースを手作業で記述するため、テストカバレッジはあなた（またはAI）がたまたま思いついた例に限定されてしまいます。 プロパティベーステスト（PBT）は、このアプローチを逆転させます。例を列挙する代わりに、常に成立しなければならない一般的なルールを定義し、ツールがそのルールに違反しようとする何百、何千ものランダムな入力を生成します。

この同じ考え方は、*ファジング*や*生成型テスト*と呼ばれることもあります。これらの用語は概ね同義です――ファジングはセキュリティやクラッシュ検出から発展したものであり、一方、プロパティベーステストはきめ細かな論理的正しさを重視しますが――いずれの場合も、多くの入力を自動的に生成し、あるプロパティが成立するかどうかを検証します。

これは、AIにおける正しさの捉え方における根本的な転換に向けた一歩であり、個々の例をチェックすることから、入力空間全体にわたる普遍的なプロパティを検証することへと移行するものです。従来のユニットテストは特定の例しかチェックせず、それを記述する者（人間であれAIであれ）は、自身のバイアスに制限されてしまいます。 Kiroは、自然言語による仕様を実行可能なプロパティに自動的に変換し、そこからテストケースを生成することで、AIエージェントと人間の開発者の双方がより信頼性の高いソフトウェアを構築できるよう支援するフィードバックループを構築します。このアプローチは、従来のテストでは見逃されていたバグを発見するだけでなく、要件とそれを検証するテストとの間に、明確で追跡可能な関連性を維持します。

### プロパティとは何か？

プロパティとは、システムがどのように振る舞うべきかに関する普遍的な記述です。プロパティは、関与する具体的なデータにかかわらず、システムにおいて常に真であるべき不変条件や契約を表現します。

> 特定の前提条件が満たされる任意の入力セットに対して、ある期待される挙動が成立します。

Kiroの仕様策定の世界では、これはEARSの要件と非常にうまく対応しています：

> 「認証済みのユーザーとアクティブなリスティングであれば、そのユーザーはそのリスティングを閲覧できる。」これは、すべての有効なシナリオにおいて成立しなければならない、システムの挙動に関する一般的なルールを捉えたものです。

### プロパティベースのテストの仕組み

自動車販売アプリを例に考えてみましょう：

- **従来のテスト**：ユーザーが車#5をお気に入りに追加すると、車#5がリストに表示される
- **プロパティベースのテスト**：任意のユーザーと任意の車について、ユーザーがその車を「お気に入り」に追加した際、システムはその車をユーザーのリストに表示しなければならない

PBT（プロパティベーステスト）は、ユーザーAが車#1を、ユーザーBが車#500をお気に入りに追加する場合、名前に特殊文字を含むユーザー、さまざまなステータスの車など、数百もの組み合わせを自動的にテストし、エッジケースを捕捉して、実装が意図通りに動作していることを検証します。

このプロセス全体を通じて、PBTは「**シュリンキング」**という手法を用いて反例を見つけ出します。これは、まるでレッドチームがコードを破壊しようとしているかのようです。ランダムな入力が障害を引き起こした場合、その入力はしばしば大規模でノイズの多いもの（200文字のユーザー名、1,000台の車からなるリストなど）です。 シュリンキングは、その入力を、障害を再現できる*最小*の入力（多くの場合、単一の空文字列や2要素のリスト）に自動的に縮小します。これにより、根本原因が隠れてしまうことなく、一目瞭然になります。違反が見つかった場合、Kiroは実装を自動的に更新したり、仕様、実装、あるいはテスト自体を修正するための選択肢を提示したりすることができます。

PBTは形式検証ではありませんが、手動では決して記述することのないシナリオにわたって正しさの証拠を提供し、実装が定義通りに動作しているかどうかを示します。

### 長所と限界

プロパティベーステストは、以下の理由から時間を節約し、AIが生成したコードに対する信頼性を高めます。

- 1つのプロパティから多くのテストケースが自動的に生成されるため、自分やAIが手作業で記述しようと考えた例に限定されることはありません。
- プロパティは具体的な例よりも高レベルで永続性が高いため、テストの保守性が向上し、実装の変更に対する耐性も高まります。
- ランダム化された入力により、空の値、境界条件、特殊な文字など、意図的にテストすることのないケースも検証されます。
- システムをより徹底的に検証することで、本番環境に到達する前に稀なバグを発見できます。
- テストを実行する前に、仕様が保証すべきプロパティを定義することで、要件が明確になり、論理的な検討が容易になります。

プロパティベーステストには、次のような制限もあります。

- これは正しさの証拠を提供するものであり、証明ではありません。形式検証ではないため、テストに合格しても信頼性は高まりますが、バグがないことを保証するものではありません。
- 有用なプロパティを特定・定義するには労力が必要です。弱すぎるプロパティや、誤った不変条件を定めたプロパティでは、実際の挙動が依然として誤っているにもかかわらず、テストに合格してしまう可能性があります。
- すべての要件がプロパティに明確にマッピングされるわけではありません。外部サービスや非決定論的な挙動に大きく依存する要件については、モック化が必要になる場合や、例ベースのテストでより適切にカバーできる場合があります。

## 仕様書を用いたプロパティベースのテスト

Kiroは、要件定義から実装の検証に至るまでの仕様書ワークフロー全体に、プロパティベースのテストを統合しています。

### ワークフロー

Kiroは、EARS形式の要件（例：「THE System SHALL allow authenticated users to view active car listings」）からプロパティを抽出し、論理的にテスト可能なものを特定します。そして、実行を選択すると、数百から数千ものランダムなテストケースを生成します。

### 設計フェーズ

設計フェーズでは、Kiroは要件からプロパティを抽出し、テストケースを生成します。これはワークフローの最初のステップであり、Kiroが要件を分析し、テスト可能なプロパティを特定します。

![Extract properties](https://kiro.dev/images/correctness1.png?h=ed62af53)

プロパティにカーソルを合わせると、元の要件や関連するタスクとの関連性が表示されます。

![Extract properties](https://kiro.dev/images/correctness2.png?h=30e6cf95)

### タスクの実行

実行フェーズでは、Kiroは生成されたPBTケースを実装に対して実行します。注：PBTはデフォルトではオプションであるため、まずはコアとなる実装に集中することができます。プロパティテストが実行されると、生成されたコードへの参照を確認できます。

![Run property tests](https://kiro.dev/images/correctness3.png?h=947e1f17)

プロパティテストが失敗した場合、Kiroは具体的な失敗シナリオを特定し、レビューのために表示します。

画像を読み込み中...![Property test failure notification](https://kiro.dev/images/correctness5.png?h=6f3237ea)

その後、Kiroとチャットして失敗の原因を把握し、実装の更新、テストの調整、あるいは要件自体の精緻化など、適切な修正策を決定できます。

画像を読み込み中...![Analyzing property test failures with Kiro](https://kiro.dev/images/correctness4.png?h=51bfcaf7)
