「クイック・スペック」は、1回の処理で要件、設計、タスクを自動生成するセッションモードです。各フェーズを承認してから次のフェーズに進むのではなく、最初に確認のための質問に回答することで、すぐに実行可能なタスクリストを作成できます。

## Quick Spec の活用シーン

Quick Specが最適なのは、次のような場合です：

- **機能が十分に理解されており**、Kiroの出力結果を信頼でき、要件や設計の反復作業が不要な場合
- レビューよりもスピードが重視される**ラピッドプロトタイピング**

未知の領域を模索している場合、要件の反復が必要である場合、またはレビューのゲートがチームにとって真に付加価値をもたらす場合は、標準の「Feature Specs」を使用してください。

## 仕組み

1. 新しいセッションを開始する際、**「Let's build」**画面のワークフローオプションから**「Quick Spec」**を選択します。セッションの途中で切り替えるには、チャット入力画面の下部バーにあるエージェント名をクリックし、エージェントピッカーから**「Quick Spec」**を選択します。
2. Kiroは最初に、スコープ、制約、エッジケース、および出力に影響を与えるその他の事項について、一連の確認質問を行います。
3. その回答をもとに、Kiroは「`requirements.md`」、「`design.md`」、「`tasks.md`」を順に自動生成します。各フェーズ間に承認ゲートは存在しません。
4. タスク一覧画面が表示され、レビューや実装を開始する準備が整います。

明確化のための質問が、重要なインタラクションのポイントとなります。各成果物を個別に確認・承認する代わりに、初期段階で必要な情報を提供することで、Kiroが十分なコンテキストを把握し、高品質な仕様書を自律的に生成できるようになります。

## 成果物

Quick Specは、標準的なSpecセッションと同じ成果物を生成し、`.kiro/specs/`に保存します：

- `requirements.md` - EARS表記によるユーザーストーリーと受け入れ基準
- `design.md` - 技術アーキテクチャおよび実装アプローチ
- `tasks.md` - 個別の、追跡可能な実装タスク

標準のSpecセッションと同様に、これらはいずれも事後に確認・編集が可能です。

## よくある質問

### Quick SpecとVibeモードの違いは何ですか？

Vibeモードは対話型で構造化されておらず、`.kiro/specs/`に成果物は保存されません。Quick Specでは、フェーズ間の承認ゲートがないものの、完全な仕様書成果物（要件、設計、タスク）が生成されます。

### Quick Spec から標準の機能仕様書に切り替えることはできますか？

明示的なモード切り替え機能はありませんが、成果物の形式は標準の機能仕様書と同じです。そのため、任意の仕様書ワークフローを使用して作業を続行したり、成果物を改良したり、タスクを再生成したり、`#spec`のチャットで参照したりすることができます。

### 自動生成された要件に重要な項目が抜けていた場合はどうすればよいですか？

`requirements.md`を直接編集するか、仕様チャットセッションでKiroに依頼して、特定の要件を追加または修正してもらってください。その後、「**ファイルの同期」**を使用してタスクを再生成してください。

### 複雑な機能には Quick Spec を使うべきでしょうか？

ご自身の判断にお任せします。要件の品質が極めて重要な機能（コンプライアンスに敏感な分野、リスクの高いシステム、不慣れな領域など）については、明確なレビューゲートを設けた標準的な機能仕様書の方が適している場合がほとんどです。一方、これまで何度もバリエーションを構築してきた機能については、Quick Spec を使用すれば、品質をほとんど損なうことなく、より迅速に開発できます。
