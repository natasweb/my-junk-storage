「デザインファースト」のワークフローは、技術設計やシステムアーキテクチャから始まり、そこから実現可能な要件を導き出します。

## 使用すべき場面

このワークフローは、次のような場合に最適です：

- **迅速なプロトタイピング** — 使用する技術スタックが明確で、何が可能かを模索したい場合
- **技術的な制約** — システムが厳格な非機能要件（レイテンシ、スループット、稼働率、コンプライアンス）を満たす必要がある場合
- **既存の設計** - アーキテクチャ図や設計文書があり、それらをKiroに移植したい場合
- **実現可能性の検討** — 特定の設計において、どの要件が達成可能かを把握したい場合
- **明確な方針** - 特定のアーキテクチャ上の好みや制約がある場合

## ワークフローの手順

### 1. 機能仕様書の作成

Kiroパネルまたはコマンドパレットから、新しい機能仕様書を作成します。プロンプトが表示されたら、「**Design-First」**ワークフローを選択します。

### 2. 詳細レベルの選択

指定したいアーキテクチャの詳細レベルを選択します：

#### ハイレベル設計

以下の内容を含む完全なアーキテクチャ：

- システムアーキテクチャ図
- コンポーネントの説明と相互作用
- 技術的アプローチとパターン
- 非機能要件（パフォーマンス、スケーラビリティ、セキュリティ）

**適している用途：**複雑なシステム、チームでの共同作業、徹底したドキュメント作成

#### 低レベル設計

実装の詳細に焦点を当てたもの：

- アルゴリズムの擬似コード
- インターフェースの定義と契約
- 主要なデータ構造
- 非機能要件

**適している用途：**迅速なプロトタイピング、迅速な実現可能性の確認、単独開発

### 3. 設計フェーズ

Kiroは、ユーザーの指示と選択した詳細レベルに基づいて、`design.md`ドキュメントを生成します。

**内容：**

- システムコンポーネントとその役割
- データフローと相互作用
- 技術スタックとフレームワーク
- API契約とインターフェース
- 非機能要件

**あなたの役割：**

- アーキテクチャの正確性を確認する
- フィードバックを提供し、設計の改良を繰り返す
- 必要に応じて代替案を検討する
- アーキテクチャが要件を満たしているかを確認する

**ヒント：**読みやすさを高めるため、設計文書はデフォルトでプレビューモードで開きます。「編集」をクリックして変更を加えてください。

### 4. 要件定義フェーズ

アーキテクチャを確認すると、Kiroは技術設計の制約内で実現可能な要件を導き出します。

**生成されるもの：**

- アーキテクチャの機能に整合したユーザーストーリー
- EARS形式のシステム動作
- 設計の範囲に限定された機能要件
- エッジケースおよびエラー処理

**主な利点：**検証済みのアーキテクチャから導き出されるため、要件が技術的に実現可能であることが保証されます。

**あなたの役割：**

- 要件の完全性を確認する
- 不足しているユーザー向けの動作を追加する
- 要件が自身の想定と一致しているかを確認する

### 5. タスクフェーズ

「要件ファースト」ワークフローと同様 — Kiroが実行可能な実装タスクを生成します。

### 6. 実装

タスクを個別に実行するか、すべてのタスクを一括実行して機能を実装します。

## ベストプラクティス

### 明確な技術的制約から始める

以下の点を明確に定義する：

- 必要な技術やサービス
- パフォーマンス要件（レイテンシ、スループット）
- スケーラビリティの要件
- コンプライアンスまたはセキュリティ要件
- 既存システムとの連携ポイント

**プロンプトの例：**

```
Create an MCP server for querying our Redshift data lake. Must use FastAPI 
and mcp-python. Target: <100ms query latency for 95th percentile. 
No UI components needed - pure API server.
```

### 要件定義の前にアーキテクチャを反復的に検討する

「デザインファースト」の強みは、技術的な設計を徹底的に検討することにあります。時間をかけて以下のことを行ってください：

- さまざまなアーキテクチャ手法を試す
- トレードオフを評価する（レイテンシ対コスト、複雑さ対保守性）
- 非機能要件が達成可能かどうかを検証する
- 要件を確定する前に、設計を適切に整える

### チームプロジェクトでは高レベル設計を活用する

実装に複数の人が関わる場合は、ドキュメントの充実と共通認識の確立のために、高レベル設計を採用する。

### 迅速な検証には低レベル設計を活用する

アイデアの実現可能性を素早く確認したい場合は、低レベル設計を用いることで、実装の詳細を含めてより迅速に検証を行うことができます。

### 既存の設計図をアップロードする

draw.io、Lucidchart、または手書きのスケッチによるアーキテクチャ図をお持ちの場合は：

1. PNG形式でエクスポートするか、写真をアップロードしてください
2. 初期のプロンプトに含める
3. Kiroがビジュアルデザインをアーキテクチャ文書に組み込みます

## 一般的なパターン

### パターン1：外部デザインの移植

**シナリオ：**別のツールで作成されたデザインドキュメントや会議のメモがある場合。

**手順：**

1. デザイン内容をコピーするか、図をアップロードする
2. 「Design-First」ワークフローを選択する
3. 「ハイレベル設計」を選択する
4. Kiroに設計をformalizeしてdesign.mdに変換させる
5. 形式化された設計から要件を導出する

### パターン2：技術的な実現可能性の検討

**シナリオ：**特定の制約条件下で、ある機能が実現可能かどうかを知りたい場合。

**アプローチ：**

1. 技術的な制約と大まかなアーキテクチャを記述する
2. 「Design-First」ワークフローを選択する
3. 反復を迅速化するために「低レベル設計」を選択する
4. 生成された要件を確認し、実現可能なものを特定する
5. 要件が期待通りでない場合は、アーキテクチャを反復修正する

### パターン3：既知のスタックを用いたプロトタイピング

**シナリオ：**顧客が具体的なサービス（Lambda、S3、DynamoDB）を指定しており、迅速にプロトタイプを作成する必要がある。

**アプローチ：**

1. 技術スタックと大まかなフローを記述する
2. 「デザインファースト」ワークフローを選択する
3. 指定されたサービスを用いてアーキテクチャを生成する
4. システムが何ができるかを示す要件を導出する
5. プロトタイプを構築するためのタスクを実行する

### パターン4：厳格な非機能要件への対応

**シナリオ：**システムは、特定のレイテンシ、スループット、またはコンプライアンス要件を満たす必要がある。

**アプローチ：**

1. 初期のプロンプトで非機能要件を定義する
2. 「Design-First」ワークフローを選択する
3. 「高レベル設計」を選択し、コンプライアンスへの取り組みを文書化する
4. アーキテクチャがすべての制約を満たしていることを検証する
5. 制約条件の範囲内で達成可能な要件を導出する

## トラブルシューティング

### 要件が期待と一致しない

生成された要件が希望する内容と一致しない場合：

1. 戻ってアーキテクチャの設計を見直し、反復を行う
2. 意図する機能について、より詳細な情報を追加する
3. 非機能要件を明確化する
4. 更新されたアーキテクチャに基づいて要件を再生成する

### アーキテクチャが抽象的すぎる

アーキテクチャに具体性が欠けている場合：

1. プロンプトに技術的な詳細をさらに追加する
2. 具体的なフレームワーク、ライブラリ、またはサービスを指定する
3. パフォーマンス数値や制約条件を含める
4. より詳細な内容が必要な場合は「High Level Design」を選択してください

### 要件確定後に設計を変更する必要がある場合

要件が確定した後に設計を変更する必要がある場合：

1. design.md ドキュメントを編集してください
2. Kiroに依頼し、更新されたアーキテクチャに基づいて要件の妥当性を検証してもらう
3. 必要に応じて要件を再生成してください
4. これは想定内のことです。反復はプロセスの一部です

## プロンプトの例

### 高レベル設計

```
Design a real-time notification system using AWS services. Must support:
- 100k concurrent WebSocket connections
- <50ms message delivery latency
- Message persistence for offline users
- Integration with existing user authentication service

Use API Gateway WebSocket, Lambda, DynamoDB, and SQS. Include 
architecture diagram showing component interactions and data flow.
```

### 低レベル設計

```
Build a rate limiter middleware for our Express API. Requirements:
- Token bucket algorithm
- Per-user and per-IP limits
- Redis for distributed state
- Configurable limits per endpoint

Show pseudocode for the core algorithm and interface definitions.
```

## 「設計ファースト」のメリット

1. **実現可能な要件を生み出す** — 要件は検証済みの技術設計から導き出される
2. **調整に伴うフラストレーションを回避** — 設計を検討する際に要件を更新する必要がない
3. **時間と労力の節約** - 要件と設計間の反復回数が減少する
4. **技術的な選択肢の検討** — 決定を下す前に、さまざまな技術的アプローチを試すことができる
5. **制約条件を早期に検証できる** - 非機能要件が達成可能であることを確実にできる
