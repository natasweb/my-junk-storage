「要件ファースト」のワークフローは、機能仕様書作成における従来のアプローチであり、システムがどのような動作を行うべきかをまず定義し、その上で構築方法を決定するものです。

## 使用すべき場面

このワークフローは、次のような場合に最適です：

- **明確なユーザーストーリー** — Kiroがユーザーストーリーを作成するために利用できる、明確に定義された動作がある場合
- **柔軟なアーキテクチャ** — 要件に合わせて技術設計を適応させることができる
- **グリーンフィールドプロジェクト** — 既存の技術的制約がなく、一から始める場合

## ワークフローの手順

### 1. 機能仕様書の作成

Kiroパネルまたはコマンドパレットから、新しい機能仕様書を作成します。プロンプトが表示されたら、「**要件ファースト」**ワークフローを選択します。

### 2. 要件定義フェーズ

Kiroは、入力内容に基づいて「`requirements.md`」ドキュメントを生成します。

**内容：**

- 明確な受け入れ基準を備えたユーザーストーリー
- EARS形式のシステム動作（WHEN...THE SYSTEM SHALL...）
- 機能要件
- エッジケースとエラー処理

**あなたの役割：**

- 要件の完全性を確認する
- ユーザーストーリーと受け入れ基準を反復的に改善する
- 不足しているシナリオやエッジケースを追加する
- 要件がニーズを満たしているかを確認する

**要件の例：**

markdown

```markdown
## User Authentication

### User Registration

WHEN a user submits valid registration data
THE SYSTEM SHALL create a new user account

WHEN a user submits an email that already exists
THE SYSTEM SHALL display "Email already registered" error

WHEN a user submits invalid email format
THE SYSTEM SHALL display email validation error
```

### 3. 設計フェーズ

要件を確認すると、Kiroはそれらを実装する方法を記述した`design.md`ドキュメントを生成します。

**生成される内容：**

- システムアーキテクチャとコンポーネント
- 相互作用を示すシーケンス図
- データモデルとインターフェース
- 技術スタックの推奨事項
- エラー処理のアプローチ
- テスト戦略

**あなたの役割：**

- 技術的なアプローチのレビュー
- アーキテクチャ上の決定事項を反復的に検討する
- 技術選定の妥当性を検証する
- 設計の実現可能性を確認する

[](/videos/specs-design.mp4?h=cf23ad47)

### 4. タスクフェーズ

Kiroは、実行可能な実装タスクを含む`tasks.md`ファイルを生成します。

**生成される内容：**

- 個別の、進捗管理可能なタスク
- 明確な説明と期待される成果
- タスク間の依存関係
- オプションのタスクと必須のタスク

**あなたの役割：**

- タスクの内訳を確認する
- 必要に応じてタスクの優先順位を調整する
- 任意のタスクにマークを付ける
- 実装を開始する

[](/videos/spec-task.mp4?h=66bfe3fb)

### 5. 実装

タスクを個別に実行するか、すべてのタスクを実行して機能を実装します。

## ベストプラクティス

### 明確なユーザーストーリーから始める

以下の点を明確にしましょう：

- ユーザーが誰か
- ユーザーが何を達成したいのか
- なぜこの機能が必要なのか
- 成功基準

**プロンプトの例：**

```
Build a user authentication system. Users should be able to register with 
email/password, login securely, reset forgotten passwords, and logout. 
The system must prevent brute force attacks and validate email formats.
```

### 設計の前に要件を反復的に検討する

「要件ファースト」の真価は、「どのように」に踏み込む前に「何を」を正しく定義することにあります。以下の作業に時間を割いてください：

- すべてのユーザーシナリオが網羅されていることを検証する
- 受け入れ基準がテスト可能であることを確認する
- 要件についてステークホルダーの賛同を得る
- エッジケースが適切に扱われているか確認する

### 明確化のためにEARS形式を使用する

EARS形式（WHEN...THE SYSTEM SHALL...）で記述された要件は、以下の特徴を持つ：

- 曖昧さがなく、テスト可能
- テストケースへの変換が容易
- 実装を通じてトレーサビリティが確保される
- 技術系および非技術系のステークホルダー双方にとって明確である

### 実現可能性のための設計レビュー

タスクに着手する前に、以下を確認してください：

- 設計がすべての要件を満たしていること
- 技術の選定が適切であること
- 非機能要件が満たされていること
- アプローチが保守可能であること

## 一般的なパターン

### パターン 1: 製品機能の開発

**シナリオ：**プロダクトマネージャーが新機能のユーザーストーリーを提供する。

**アプローチ：**

1. ユーザーストーリーを初期プロンプトにコピーする
2. 「要件ファースト」ワークフローを選択する
3. KiroにEARS形式で要件を形式化させる
4. PMと要件を確認し、反復改善を行う
5. 設計を生成し、エンジニアリングチームと検証を行う
6. 実装のためのタスクを実行する

### パターン2：顧客主導の機能

**シナリオ：**顧客から特定の機能が要求される。

**アプローチ：**

1. 初期のプロンプトで顧客のニーズを記述する
2. 「要件ファースト」ワークフローを選択する
3. 顧客の意図を反映した要件を生成する
4. 顧客と要件の妥当性を確認する
5. 要件に最適化された設計を生成する
6. 実装および納品

### パターン3：グリーンフィールド・アプリケーション

**シナリオ：**新しいアプリケーションをゼロから立ち上げる。

**アプローチ：**

1. 中核となるユーザージャーニーと機能を定義する
2. 「要件ファースト」のワークフローを選択する
3. 包括的な要件を策定する
4. 拡張性と保守性の観点から設計を検証する
5. MVPを構築するためのタスクを実行する

## トラブルシューティング

### 設計が要件を満たしていない

生成された設計が要件を完全に満たしていない場合：

1. 要件の明確性と完全性を確認する
2. より具体的な受け入れ基準を追加する
3. 更新された要件に基づいて設計を再生成する
4. 設計が要件と整合するまで反復を行う

### 要件が曖昧すぎる

要件に具体性が欠けている場合：

1. 最初のプロンプトに詳細を追加する
2. 具体的なユーザーシナリオやエッジケースを含める
3. 明確な成功基準を定義する
4. 正確さを高めるためにEARS形式を使用する

### 設計後に要件を変更する必要がある場合

設計生成後に要件を変更する必要がある場合：

1. requirements.md ドキュメントを編集してください
2. design.md ファイル内の [**Refine]** をクリックする
3. Kiroは新しい要件に合わせて設計とタスクを更新します
4. これは想定内の動作です。反復はプロセスの一部です
