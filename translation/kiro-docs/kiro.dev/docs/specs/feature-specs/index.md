「Feature Specs」は、新機能の構築に向けた体系的なアプローチを提供し、要件収集、技術設計、実装計画の各段階を順を追って案内します。明確なユーザー要件があるか、あるいは技術設計の構想があるかなど、開始時点の状況に応じて、開発プロセスに合わせた2つのワークフローのバリエーションから選択できます。

## 主なメリット

**体系的なアプローチ** - 明確なフェーズが、アイデアから実装までを導きます

**柔軟性** - 開始時点の状況に合わせてワークフローを選択可能

**ドキュメント化** - 要件書や設計書の自動生成

**進捗管理** - 個別の実装タスクにわたる進捗状況を監視

**コラボレーション** - 製品部門とエンジニアリング部門の連携を図るための成果物の共有

## 機能仕様書の活用シーン

**最適なケース：**

- 構造化された計画が必要な複雑な機能
- 複数の実装タスクを伴う機能
- チームでの協業のためにドキュメントが必要なプロジェクト
- 要件や設計の反復が必要な機能

**適さないケース：**

- バグ修正（代わりに「バグ修正仕様書」を使用してください）
- 明確な目標のない探索的コーディング

## ワークフローのバリエーション

機能仕様書では、さまざまな開発シナリオに対応するため、2つのワークフローのバリエーションをサポートしています。開始時点やプロジェクトの制約に最も適したワークフローを選択してください。

### 要件ファースト

作成したいシステムの挙動を要件として定義することから始め、そこから技術設計と実装タスクを生成します。

**使用すべき場面：**

- 構築したいシステムの動作が明確な場合
- アーキテクチャに柔軟性があり、ニーズに合わせて設計できる
- 顧客のフィードバックに基づいて製品機能を構築する場合
- 技術的な制約のないグリーンフィールドプロジェクトを開始する場合
- プロダクト主導型の組織で業務を行う場合

**フロー：**要件 → 設計 → タスク

### デザインファースト

まず技術設計（アーキテクチャまたは低レベル設計）から始め、そこから実現可能な要件と実装タスクを導き出す。

**適用すべき場面：**

- 頭の中にアーキテクチャ（高レベル設計）の構想がある場合
- 擬似コードやアルゴリズムを通じて、実装動作から始めたい場合（低レベル設計）
- システムが厳格な非機能要件（レイテンシ、スループット、コンプライアンス）を満たす必要がある場合
- 他のツールからKiroへの設計文書の移行
- スコープを確定する前に技術的な実現可能性を検討する場合

**フロー：**設計 → 要件 → タスク

### 簡単な比較

|  | 要件ファースト | 設計ファースト |
| --- | --- | --- |
| **開始点** | 要件として定義されたシステムの挙動 | 技術設計、アーキテクチャ、または擬似コード |
| **生成** | 要件から設計を生成する | 設計から要件を導出 |
| **最適用途** | プロダクト主導型開発 | 技術的な制約がある、または設計主導型のプロジェクト |
| **保証されること** | 期待される動作が明確に定義される | 技術的な実現可能性 |
| **柔軟性** | 実装の適応性 | 要件を適応させることができる |

## EARS表記法を用いた要件

`requirements.md`ファイルでは、構造化され、検証可能な要件を定義するために、EARS（Easy Approach to Requirements Syntax）表記法を使用しています。各要件は次のパターンに従います：

```
WHEN [condition/event]
THE SYSTEM SHALL [expected behavior]
```

例：

```
WHEN a user submits a form with invalid data
THE SYSTEM SHALL display validation errors next to the relevant fields
```

この構造化されたアプローチには、いくつかの利点があります：

- **明瞭性**：要件は曖昧さがなく、理解しやすい
- **テスト可能性**：各要件を直接テストケースに変換できます
- **トレーサビリティ**：個々の要件を、実装を通じて追跡できる
- **網羅性**：この形式により、あらゆる条件や挙動を徹底的に検討するよう促される

## 設計前の要件分析

要件から設計に移行する前に、Kiroに要件の分析を依頼し、論理的な矛盾、曖昧さ、制約の衝突、および欠落がないかを確認することができます。要件が生成された後、チャットオプションまたはエディタの「続行」ドロップダウンから「**要件の分析」**を選択してください。

[「要件の分析」の詳細はこちら →](https://kiro.dev/docs/specs/analyze-requirements/)

`design.md`ファイルには、技術アーキテクチャ、シーケンス図、および実装上の考慮事項が記載されます。このファイルには、コンポーネントやそれらの相互作用を含め、システムがどのように動作するかという全体像がまとめられています。

## はじめに

機能仕様書（Feature Specs）の作成は、他の仕様書と同様に開始します。各画面ごとの手順については、[「はじめに」を](https://kiro.dev/docs/specs/#getting-started)参照してください。Kiroが意図を確認してきたら、**「機能（Feature）」**を選択し、ワークフローとして「**要件ファースト（Requirements-First）**」または**「設計ファースト（Design-First）**」のいずれかを選びます。各フェーズ間の承認プロセスが不要な、十分に理解されている機能については、代わりに**[「クイック仕様（Quick Spec）」](https://kiro.dev/docs/specs/quick-spec/)**を選択してください。

また、Kiroの設定でデフォルトのワークフローを設定しておけば、この選択手順をスキップすることもできます。
