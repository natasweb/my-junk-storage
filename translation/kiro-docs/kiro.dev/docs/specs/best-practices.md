## 機能仕様

### どのワークフローを選べばよいですか？

「Feature Specs」では、「要件ファースト」と「設計ファースト」の2つのワークフローをサポートしています。

**次のような場合は「要件ファースト」を選択してください：**

- 構築したいシステムの動作が分かっている場合
- アーキテクチャに柔軟性があり、ニーズに合わせて設計できる場合
- 顧客のフィードバックに基づいて製品機能を構築する場合
- 技術的な制約がない状態で開始する場合

**「設計ファースト」を選択すべき場合：**

- 既存の技術設計やアーキテクチャがある場合
- システムが厳格な非機能要件（レイテンシ、スループット、コンプライアンス）を満たす必要がある場合
- 特定の技術スタックを用いたプロトタイピングを行う場合
- スコープを確定する前に技術的な実現可能性を検証する場合

[ワークフローの詳細はこちら →](https://kiro.dev/docs/specs/feature-specs/)

### 仕様書の作成を開始した後でも、ワークフローを切り替えることはできますか？

いいえ、仕様書を作成する際にワークフローを選択する必要があります。アプローチを変更する必要がある場合は、希望するワークフローで新しい機能仕様書を作成してください。必要に応じて、以前の仕様書から関連する内容をコピーすることができます。

### 同じプロジェクトで両方のワークフローを使用できますか？

はい！複数の仕様書を作成できます。例えば：

1. 「Design-First」を使用して技術的な実現可能性を検証する
2. 完全な機能開発のために「要件ファースト」の仕様書を作成する

### 既存の設計やアーキテクチャをインポートするにはどうすればよいですか？

既存のアーキテクチャ図や設計文書がある場合は：

1. **「デザインファースト」ワークフローを使用する場合**：

   - 新しい機能仕様書を作成し、「Design-First」を選択します
   - アーキテクチャ図（PNG、JPG）をアップロードするか、設計内容を貼り付けます
   - Kiroが設計内容を「design.md」として形式化します
   - アーキテクチャから要件を導出します
2. **画像を使用する場合**：draw.ioやLucidchartなどのツールから図をエクスポートするか、ホワイトボードのスケッチを写真に撮り、初期プロンプトに含めます。
3. **MCP 統合の使用**：お使いのデザインツールに [MCP サーバー](https://kiro.dev/docs/mcp/)がある場合は、直接接続してデザインをインポートできます。

### 既存の要件をインポートするにはどうすればよいですか？

要件や設計が別のシステム（JIRA、Confluence、Word文書など）にすでに存在する場合、次の2つの方法があります：

1. **MCP 連携の利用**：要件管理ツールに [MCP](https://kiro.dev/docs/mcp/) サーバーがある場合は、直接接続して要件を仕様セッションにインポートできます。Kiro はローカルおよびリモートの MCP サーバーの両方をサポートしています。
2. **手動でのインポート**：既存の要件（例：`foo-prfaq.md`）をリポジトリ内の新しいファイルにコピーし、仕様チャットセッションを開いて「`#foo-prfaq.md Generate a spec from it`」と入力します。Kiroが要件を読み取り、要件仕様と設計仕様を生成します。

### 機能仕様書（Feature Specs）をどのように反復改善すればよいですか？

Kiroの機能仕様書は継続的な改良を想定して設計されており、プロジェクトの進展に合わせて更新や機能強化を行うことができます。この反復的なアプローチにより、仕様書は変化する要件や技術設計と常に同期した状態が保たれ、開発のための信頼できる基盤が提供されます。

**要件ファーストの仕様書の場合：**

1. **要件の更新**：`requirements.md`ファイルを直接編集するか、仕様策定セッションを開始して、Kiroに新しい要件や設計要素を追加するよう指示します。
2. **設計の更新**：仕様の`design.md`ファイルに移動し、**「Refine」**を選択します。この操作により、変更された要件を反映して、設計ドキュメントと関連するタスクリストの両方が更新されます。
3. **ファイルの同期**：`tasks.md`ファイルに移動し、**「ファイルの同期」**を選択します。これにより、新しい要件に対応する新しいタスクが作成されます。

**「Design-First」仕様の場合：**

1. **設計の更新**：`design.md`ファイルを直接修正するか、仕様策定セッションでKiroに更新を依頼してください。
2. **要件の更新**：アーキテクチャの変更後、Kiroに要件の検証と再生成を依頼し、要件が依然として実現可能であることを確認してください。
3. **ファイルの同期**：`tasks.md` ファイルに移動し、「**ファイルの同期」**を選択して変更を反映させます。

## バグ修正仕様書

### 効果的なバグの説明文を書くにはどうすればよいですか？

明確なバグの説明は、Kiroが正確な根本原因分析を行うのに役立ちます。以下の内容を含めてください：

1. **再現手順** - バグが発生する正確な条件を記述してください
2. **現在の動作** — システムが現在どのように動作しているか（不具合）
3. **期待される動作** - システムが本来行うべき動作
4. **制約条件** - 変更してはならないコードや動作

**プロンプトの例：**

```
When a user submits a form with special characters in the name field 
(e.g., O'Brien), the API returns a 500 error. It should accept the 
input and save it correctly. The validation logic for email and 
password fields should not be affected.
```

### Bugfix Specs を使用して回帰バグを防ぐにはどうすればよいですか？

バグ修正仕様書では、修正内容とともに「変更されない動作」を明示的に定義します。分析フェーズにおいて、引き続き機能し続けなければならないことを文書化します：

- **WHEN** [条件] **THEN** システムは [既存の動作] **を継続しなければならない**

Kiroは、修正内容と既存の動作の維持の両方を検証するプロパティベースのテストを生成するため、修正によって他の部分が破損しないという確信を得ることができます。

### バグ修正仕様とクイックフィックスは、それぞれどのような場合に使用すべきですか？

次のような場合にバグ修正仕様を使用してください：

- バグが重要なコードパスにある場合
- 以前の修正試行により回帰バグが発生した場合
- 根本原因がすぐには明らかでない場合
- コンプライアンス対応やチームの知識共有のためにドキュメントが必要な場合

タイプミス、単純なロジックエラー、あるいは内容を十分に把握している1行の変更といった単純な問題については、チャットでの迅速な修正で問題ありません。

### バグ修正仕様書を機能仕様書に変換することはできますか？

直接はできません。根本原因の分析の結果、修正に大幅な新機能が必要であることが判明した場合は、その新しい作業用に別の機能仕様書を作成し、バグ修正仕様書は元の不具合に焦点を当てたままにしておきます。

## 全般

### 仕様書をチームと共有するにはどうすればよいですか？

仕様書はバージョン管理されるように設計されているため、チーム内で簡単に共有できます。仕様書は、それらが記述するコードと一緒に、プロジェクトのリポジトリに直接保存してください。これにより、すべてのプロジェクト成果物が一箇所にまとめられ、要件と実装の関連性が維持されます。

### 複数のチーム間で仕様書を共有できますか？

はい、Gitサブモジュールやパッケージ参照を活用することで、複数のチーム間で仕様書を共有できます。チーム間で共有される仕様書を管理するためのベストプラクティスを以下に示します：

1. **一元化された仕様リポジトリを作成する** - 複数のプロジェクトが参照できる、共有仕様専用のリポジトリを確立します。
2. **Gitサブモジュールまたはパッケージ参照を使用する** - 開発環境に応じて、Gitサブモジュール、パッケージ参照、またはシンボリックリンクを使用して、中央の仕様を個々のプロジェクトにリンクします。
3. **リポジトリをまたぐワークフローの導入** - 複数のプロジェクトに影響を与える共有仕様の提案、レビュー、更新に関するプロセスを確立します。

プロジェクト横断的な仕様管理に関して具体的なニーズがある場合は、[GitHub](https://github.com/kirodotdev)の[イシュートラッカー](https://github.com/kirodotdev)に要件を共有してください。そうすることで、皆様のワークフローをサポートする機能の優先順位付けに役立てることができます。

### vibe セッションから仕様セッションを開始することはできますか？

はい。vibeでの会話中に「`Generate spec`」と発声してください。すると、Kiroが仕様セッションを開始するかどうかを尋ねてきます。「はい」と答えると、vibeセッションの文脈に基づいて要件の生成が開始されます。

### 仕様書内のすべてのタスクを一括で実行できますか？

はい。「`tasks.md`」ファイル内のすべてのタスクは、「**すべてのタスク**を実行」ボタンをクリックすることで実行できます。Kiroはタスク間の依存関係を分析し、独立したタスクを並行して実行するため、実行速度が大幅に向上します。依存関係のあるタスクは順番を待ちます。この機能では、「必須」とマークされた未完了のタスクのみが実行されます。[タスクの並行実行について詳しくはこちら →](https://kiro.dev/docs/specs/#running-tasks-in-parallel)

### タスクは並列で実行できますか？

はい。「**すべてのタスクを実行**」をクリックすると、Kiroはタスク間の依存関係グラフを構築し、互いに独立したタスクをグループ（ウェーブ）にまとめ、並行して実行します。設定は不要です。[詳細はこちら →](https://kiro.dev/docs/specs/#running-tasks-in-parallel)

### 「クイックスペック」と標準の「フィーチャースペック」は、それぞれどのような場合に使用すべきですか？

**次のような場合にクイック・スペックを使用してください：**

- Kiroの出力を信頼できる、十分に理解されている機能に取り組んでいる場合
- ラピッドプロトタイピングを行っており、レビューよりもスピードを重視する場合
- 標準的なフローで要件や設計を編集することがほとんどない場合
- 標準の仕様書作成フローが煩雑に感じられ、ついVibeモードをデフォルトで使用していた場合

**標準の機能仕様書を使用すべき場面：**

- 未知の領域を模索している場合
- 要件や設計に反復作業が必要な場合
- コンプライアンスが重視される分野で作業しており、レビューゲートが真の価値をもたらす場合
- チームにとって、明確な承認チェックポイントの設置が有益な場合

どちらも同じ成果物（`requirements.md`、`design.md`、`tasks.md`）を生成します。違いは、次の成果物が生成される前に、それぞれをレビューするかどうかという点にあります。[Quick Specの詳細はこちら →](https://kiro.dev/docs/specs/quick-spec/)

### 設計に移行する前に、いつ要件を分析すべきですか？

Kiroが要件を生成した後、「**要件の分析」**を選択することで、論理的な不整合、曖昧さ、矛盾する制約、および欠落を検出する詳細な分析を実行できます。これは特に次のような場合に有用です：

- 相互作用が重要な、要件数の多い複雑な機能
- 曖昧さが大きなコストにつながるドメイン特化型プロジェクト（金融サービス、医療、コンプライアンス）
- 手動によるレビューなしで要件が自動生成された「[Quick Spec」](https://kiro.dev/docs/specs/quick-spec/)セッション

この分析は、要件セット全体を網羅して推論を行うため、数分（数秒ではありません）かかります。小規模な仕様書や内容が十分に把握されている仕様書の場合は、この分析をスキップして、直接設計に進むこともできます。[詳細はこちら →](https://kiro.dev/docs/specs/analyze-requirements/)

### 一部のタスクがすでに実装済みの場合はどうすればよいですか？

既存のコードベースで作業する際、同僚やご自身が別のセッションで既にそのタスクを完了させていたため、仕様書に記載されているタスクの一部がすでに完了していることに気づく場合があります。この場合の対処法は以下の2つです：

**方法1：tasks.md内の「Sync Files」をクリックする**

- `tasks.md`ファイルを開く
- **「ファイルの同期」**をクリックします
- Kiroが自動的に完了したタスクにマークを付けます。

**方法 2：仕様書のチャットセッションで Kiro にスキャンを依頼する**

- 仕様確認セッションで、Kiroに「すでに完了しているタスクを確認してください」と尋ねてください
- Kiroがコードベースを分析し、実装済みの機能を特定します
- Kiroは完了したタスクを自動的にマークします

これにより、タスクの仕様が正確に保たれます。

### チャットで仕様書を参照するにはどうすればよいですか？

`#spec`コンテキストプロバイダーを使用すると、チャットでの会話中に仕様リストから任意の仕様を参照できます。`#spec`と入力してEnterキーを押すと、利用可能な仕様のリストが表示されますので、参照したいものを選択してください。Kiroは、応答が文書化された仕様に確実に沿うよう、すべての仕様ファイル（requirements.md、design.md、tasks.md）を自動的に会話コンテキストに含めます。

### チャットで #spec はいつ使用すべきですか？

`#spec` の使用は、コンテキストに応じた支援が必要な場合に特に役立ちます：

- **タスクの実装** — 設計上の決定に沿い、受け入れ基準を満たすコードを生成する
- **仕様の精緻化** — 新たな知見に基づいて、要件、設計、またはタスクの変更を依頼する場合
- **成果物の検証** — 実装内容が仕様の要件と一致しているかを確認する
- **質問をする際** — 機能のアーキテクチャや設計に関する回答を得る

**例：**

```
#spec:user-authentication implement task 2.3
#spec:user-authentication update the design file to include password reset flow
#spec:user-authentication does my current implementation meet the acceptance criteria for task 7.1?
#spec:user-authentication why did we choose JWT over session-based authentication?
```

### 1つのリポジトリに何個の仕様書を含めることができますか？

1つのリポジトリに、必要なだけ仕様を配置できます。コードベース全体を1つの仕様でカバーしようとするのではなく、プロジェクト内の各機能ごとに複数の仕様を作成することをお勧めします。

たとえば、eコマースアプリケーションでは、次のように仕様を整理することができます。

```
.kiro/specs/
├── user-authentication/       # Login, signup, password reset
├── product-catalog/           # Product listing, search, filtering
├── shopping-cart/             # Add to cart, quantity updates, checkout
├── payment-processing/        # Payment gateway integration, order confirmation
└── admin-dashboard/           # Product management, user analytics
```

このアプローチにより、以下のことが可能になります：

- 競合することなく、各機能を独立して開発できる
- 焦点を絞った、管理しやすい仕様書を維持できる
- 他の領域に影響を与えることなく、特定の機能を反復的に改善できる
- 異なる機能について、チームメンバーと同時に共同作業を行うことができる
