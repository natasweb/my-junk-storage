Kiroは、エージェントの動作をきめ細かく宣言的に制御できる、機能ベースの権限システムを採用しています。機能ごとに一致パターンと明示的な効果を定義することで、従来の二値的な信頼モデルに取って代わります。

| 機能 | IDE | CLI | Web | モバイル |
| --- | --- | --- | --- | --- |
| 権限のYAML設定 | ✓ | ✓ | 該当なし | — |
| 対話型承認プロンプト | ✓ | ✓ | 該当なし | — |
| グローバルおよびワークスペースのスコープ | ✓ | ✓ | 該当なし | — |
| 権限確認プロンプトの代わりに管理型クラウドサンドボックス | 該当なし | 該当なし | ✓ | — |

Web版では、`permissions.yaml`モデルおよび対話型承認は適用されません。エージェントはアクションごとにプロンプトを表示するのではなく、隔離された[クラウドサンドボックス](https://kiro.dev/docs/web/sandbox/)内で実行されるため、これらの行は「非対応」ではなく「N/A」とマークされています。

## 仕組み

権限システムは、3つの中核となる概念に基づいて構築されています：

| 概念 | 説明 |
| --- | --- |
| **機能** | `fs_read`、`fs_write`、`shell`、`web_fetch`、<img id="5"/>、`web_search`、`mcp`、`subagent`、`skill`、`power`、`context`、`diagnostics`、`sandbox_network`、`all`。メタ機能の詳細：`sandbox_network`（<img id="15"/>を除くすべての機能）、`builtin`（すべての組み込みツール）、`filesystem`（`fs_read` + `fs_write`） |
| **効果** | `deny`（常にブロック）、`ask`（確認を要求）、`allow`（黙って実行）、`evaluate`（Kiroがアクションを判断する。最も弱い効果で、`approve-for-me`プリセットによって追加され、信頼性分類器が利用可能な場合にのみ有効） |
| **優先順位** | deny > ask > allow > evaluate - スコープに関係なく、deny ルールが常に優先されます。`sandbox_network` ホストルールは例外です。[サンドボックスのネットワークルールを](https://kiro.dev/docs/permissions/#sandbox-network-rules)参照してください。 |

追加のルールプロパティ：

| プロパティ | 説明 |
| --- | --- |
| **一致パターン** | ルールの適用範囲を指定するGlobパターン（fsの場合はファイルパス、shellの場合はコマンドのプレフィックス、MCPの場合はサーバー／ツール名） |
| **除外** | 一致させてはならないオプションのグロブパターン — 「X 以外のすべてを許可」を有効にします |

### サンドボックスネットワークルール

`sandbox_network`機能は、[ローカルコマンドサンドボックス](https://kiro.dev/docs/sandbox/)がアクティブな場合にのみ適用されます。その`allow`および`deny`ルールは、サンドボックス化されたシェルコマンドが到達可能なホストを指定し、`fs_read`および`fs_write`ルールは、それらのコマンドが参照および書き込み可能なパスを制御します。これは`all`メタ機能からは除外されます。

ホストフィルタリングでは、拒否オーバーライドは使用されません。`sandbox_network`ルールは順序通りに適用され、ホストに一致した最初のルールが優先されるため、特定の`deny`は、同様に一致するより広範なワイルドカード`allow`よりも前に配置する必要があります。エージェントがツールアクションを実行できるかどうかは、引き続き拒否オーバーライドによって決定されます。ホストパターンおよびネットワークモードについては、[「ローカルコマンドサンドボックス」](https://kiro.dev/docs/sandbox/)を参照してください。

## ルールの定義

権限は、YAML ファイル内で 2 つのレベルで定義されます。

**ユーザースコープ**（`~/.kiro/settings/permissions.yaml`） - すべてのプロジェクトに適用されます。信頼できる操作を事前に承認するために使用します：

yaml

```yaml
rules:
  - capability: shell
    match: ["git *", "npm *", "npx *"]
    effect: allow

  - capability: fs_write
    match: ["src/**", "tests/**"]
    effect: allow

  - capability: fs_read
    effect: allow

  - capability: mcp
    match: ["my-server/*"]
    effect: allow
```

**ワークスペーススコープ**（`~/.kiro/workspace-roots/<hash>/permissions.yaml`） - 特定のプロジェクトにのみ適用されます。ルールを1つのコードベースに限定する場合に使用します：

yaml

```yaml
rules:
  - capability: fs_write
    match: ["*.env", "*.pem", "*.key"]
    effect: deny

  - capability: shell
    match: ["rm -rf *", "sudo *"]
    effect: deny
```

どちらのスコープも、すべてのエフェクト（`deny`、`ask`、`allow`、および`evaluate`）をサポートしています。

### 除外構文

ルールでは、「～を除くすべてを許可する」パターン用の`exclude`フィールドがサポートされています：

yaml

```yaml
rules:
  - capability: mcp
    match: ["my-server/*"]
    exclude: ["my-server/dangerous-tool"]
    effect: allow
```

### パターンマッチング

ルールではグロブパターンが使用されます。構文は機能の種類によって異なります：

**ファイルシステムパターン**（`fs_read`、`fs_write`）：

- `*`は、単一のパス構成要素内で一致します
- `**`は、パス区切り文字をまたいで一致します
- `{a,b}`による中括弧の展開および`[abc]`による文字クラスがサポートされています
- ワイルドカードを含まないパターンは、暗黙的に子要素に一致します：`~/temp` は `~/temp/child` に一致します

**シェル、Web、および MCP パターン:**

- `*` は任意の文字列に一致します
- `**`、`?`、および文字クラスはサポートされていません

yaml

```yaml
rules:
  # Allow npm commands except npm publish
  - capability: shell
    effect: allow
    match:
      - "npm *"
    exclude:
      - "npm publish*"

  # Deny reads to secrets at any depth
  - capability: fs_read
    effect: deny
    match:
      - "**/.env"
      - "**/.env.*"
      - "secrets/**"
      - "**/*.pem"
```

### シェルコマンドの解析

シェルコマンドは、パターンマッチングの前に解析されます。複合コマンド（`;`、`&&`、`||`、`|` を使用するもの）は分割され、各サブコマンドが個別に評価されます。これにより、`npm test *` に対するルールが誤って `npm test ; curl attacker.com` に一致してしまうことを防ぎます。

パーサーは、組み合わせられた短縮オプション内のフラグを評価するため、`grep -iP`のようなコマンドであっても、そのフラグのいずれかが承認を必要とする場合は、依然としてプロンプトが表示されます。別のプログラムを起動できるオプションは、決して読み取り専用として扱われることはありません。`tar --use-compress-program`や`tar --to-command`は、基となる`tar`コマンドが信頼されている場合でも、承認を必要とします。

Kiro IDE 1.4.51 以降および Kiro CLI V3 セッションでは、Kiro は、権限ルールとの照合に必要なほど十分に解析できない bash または PowerShell コマンドをブロックします。Kiro は、未検証のコマンドの承認をユーザーに求める代わりに、エージェントにコマンドの書き換えを依頼します。`cmd.exe` に対するコマンドについては、引き続き承認が求められます。 すべてのシェルコマンドについて確認を求めるルールであっても、シェル`deny`ルールが適用されない場合は、通常のプロンプトが表示されます。無条件の`allow`または`deny`ルールは、解析を行わずに判断します。有効なコマンドが数回の書き換え後もブロックされたままの場合、エージェントはコマンドを確認できなかったことをユーザーに通知します。

## スコープ

権限は複数のスコープにわたって評価されます。以下の表には、ユーザーが直接設定または遭遇するスコープが記載されていますが、これは権限エンジンが定義するすべてのスコープの網羅的な一覧ではありません。

| スコープ | 場所 | 許可される効果 |
| --- | --- | --- |
| Kiro | ハードコードされたセキュリティ不変条件（設定によって変更できません） | 拒否、確認 |
| 管理 | `managed-settings.json` 内の[エンタープライズ権限ポリシー](https://kiro.dev/docs/enterprise/governance/permissions/) | 拒否、確認 |
| ユーザー | `~/.kiro/settings/permissions.yaml` | 拒否、確認、許可、評価 |
| ワークスペース | `~/.kiro/workspace-roots/<hash>/permissions.yaml` | 拒否、確認、許可、評価 |
| エージェント | エージェントプロファイルに埋め込まれている（`permissions`フィールド） | 拒否、確認、許可、評価 |
| セッション | セッション中の同意決定に基づくインメモリルール | 拒否、確認、許可、評価 |

ルールは、「拒否優先」アルゴリズム（deny > ask > allow > evaluate）を使用して評価されます。 スコープ間の優先順位はありません。どのスコープに由来するかにかかわらず、最も制限の厳しい効果が優先されます。`evaluate`は、ユーザーまたはワークスペースの権限ファイル内で`policies:`の下にリストされている場合、`approve-for-me`プリセットによって追加される効果です。[「ポリシープリセット」を](https://kiro.dev/docs/permissions/#policy-presets)参照してください。`sandbox_network`ホストフィルタリングは例外です。これは、[「サンドボックスネットワークルール」](https://kiro.dev/docs/permissions/#sandbox-network-rules)で説明されているように、ルールが最初に一致したものが適用されます。

### サブエージェント

Kiroは、各サブエージェントのツール呼び出しについて、親セッションのポリシーおよびサブエージェント自身の`permissions`と照合します。より厳格な結果が優先されます：

- いずれかのポリシーの`deny`が、その呼び出しを拒否します。
- いずれかのポリシーの`ask`ルールが適用される場合、確認メッセージが表示されます。
- 親セッションのポリシーにその呼び出しに関するルールがない場合、サブエージェント自身のルールで許可されている場合でも、Kiroは確認を求めます。

サブエージェントのルールに言及されていない呼び出しは、親セッションのポリシーに従います。サブエージェントの`allow`ルールは、親セッションが許可する範囲を超える権限を付与することはありません。`subagent`機能ルールは、サブエージェントが確認メッセージなしで起動できるかどうかのみを制御します。「[サブエージェントの権限」](https://kiro.dev/docs/custom-agents/subagents/#sub-agent-permissions)を参照してください。

## ポリシープリセット

ポリシープリセットは、名前が付けられ、組み合わせ可能なルールのセットです。`approve-for-me`を除くすべてのプリセットは、`allow`ルールのみで構成されています。プリセットは2つの経路のいずれかを通じてセッションに適用され、その経路によって適用範囲が決まります：

- **クライアントによる要求。**Kiro独自のインターフェースや、エディタ統合、レビューボット、CIハネスなどの互換性のあるサードパーティ製統合を含む、あらゆるACPクライアントは、セッションを開く際に「許可のみ」のプリセットを要求できます。それらのルールはセッションスコープで初期化され、メモリ内でのみ保持されます。
- **権限ファイルにリストされている場合。**ユーザーまたはワークスペースの`permissions.yaml`内で`policies:`として指定されたプリセットは、そのファイルのスコープで展開され、ファイルとともに永続化されます。Kiro CLI 2.36以降では、`/permissions`の「**承認を代行」**オプションが`approve-for-me`を有効にする仕組みはこれに基づいています。つまり、プリセットをワークスペースの権限ファイルに書き込むのです。

`approve-for-me`は「allow-only」の例外です。これは、範囲が限定された`allow`ルールのセットの上に、各機能ごとに`evaluate`ルールを追加するものであり、Kiroの信頼分類器に依存しています。分類器が利用できない場合、このプリセットはルールを提供せず、セッションは引き続き確認を求め続けます。 Kiro CLI V3 セッションの `/permissions` の下にある「**Approve for me**」オプションで有効にします（このオプションが表示される場合）。[「Approve for me](https://kiro.dev/docs/cli/v3/permissions/#approve-for-me)」を参照してください。

### クライアントから要求されたプリセットの適用方法

ACP クライアントは、`session/new` または `session/load` リクエストの `_meta.kiro.policyPreset` フィールドでプリセットを要求します。複数のプリセットを組み合わせることができ、そのルールは和集合として統合されます。

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["edit-workspace", "dev-shell"]
    }
  }
}
```

クライアントから要求されたプリセットのルールは、クライアントがセッションを開いた際に、`permissions.yaml`で設定したルールとは別に、セッションに読み込まれます。これが、セッションのアクティブなルールに、自分が設定した覚えのないエントリが含まれることがある理由です。

未知のプリセット ID を要求すると、セッション要求は拒否されます。デフォルトポリシーへのサイレントなフォールバックは行われません。

### 利用可能なプリセット

| プリセット ID | 含まれるルール |
| --- | --- |
| `allow-all` | `sandbox_network`（`capability: all, effect: allow`に相当）を除くすべての機能 |
| `edit-workspace` | `./**` 内の `fs_read` および `fs_write` のみ |
| `read-workspace` | `./**` 内の `fs_read` のみ |
| `read-all` | 任意の場所にある `fs_read`、および `web_fetch` と `web_search` |
| `read-only-shell` | 読み取り専用シェルコマンド：システム情報に加え、`git`、`cargo`、`npm`、`docker`、`kubectl`、および`rustup`のクエリ |
| `dev-shell` | 読み取り専用のシェルコマンド（`read-only-shell`のセット）に加え、gitの書き込みコマンド；ビルドツール `cargo`、`npm`、`bun`、`yarn`；ワークスペース操作 `mkdir`、`touch`、`mv`、`cp`；検査コマンド `ls`、`cat`、`grep`、`echo` |
| `approve-for-me` | `edit-workspace`および`read-only-shell`のセットに加え、各機能に対する`evaluate`ルールが設定されているため、Kiroは「deny」、「ask」、または「allow」のいずれのルールにも該当しない各アクションを判定します。トラスト分類器が必要です。利用できない場合、このプリセットはルールを提供しません。 Kiro CLI 2.36以降では、V3セッションの`/permissions`で**「承認（approve for me）」**を選択すると、ワークスペース権限ファイルの`policies:`にこのプリセットが一覧表示されるため、そのルールはワークスペーススコープで適用されます。[「承認（Approve for me）」](https://kiro.dev/docs/cli/v3/permissions/#approve-for-me)を参照してください |

### セッションのプリセットの選択

「許可のみ」のプリセットは、セッションが実行することを意図している操作に関するプロンプトを削除し、それ以外のすべてについては承認を求めるというデフォルト設定を維持します。 セッションのタスクに最も適合する、範囲の狭いプロファイルを選択してください。`approve-for-me`はこの表には含まれていません。これは、Kiro CLI V3 セッションの `/permissions` で選択され、1 つのセッションに対して要求されるのではなく、ワークスペースの権限ファイルにリストされ、トラスト分類子が利用可能な場合にのみ有効になります。

| セッションプロファイル | プリセット | 得られるもの |
| --- | --- | --- |
| コードレビューまたは監査 | `read-workspace` | ワークスペースのファイルは、ユーザーに通知することなく読み込まれます。書き込みやシェルコマンドについては引き続き確認が行われるため、変更を行う前にセッションからプロンプトが表示されます。 |
| 調査および研究 | `read-all` | ディスク上の任意の場所にあるファイルの読み取りに加え、`web_fetch`および`web_search`も利用可能です。これにより、書き込みアクセスを必要とせずに、コードや外部ドキュメント全体にわたって問題を追跡するセッションが可能になります。 |
| 診断およびトリアージ | `read-workspace` + `read-only-shell` | エージェントはワークスペースのファイルを読み取り、Git、Docker、kubectl、およびその他のツールの状態を照会します。書き込みが許可されることは一切ないため、変更を行うたびに確認が行われます。 |
| 自律的なビルド・テストループ | `edit-workspace` + `dev-shell` | エージェントはワークスペースのファイルを編集し、gitの書き込みコマンドや標準的なビルドツールを実行し、アクションごとの確認プロンプトなしにワークスペース内でファイルを作成または移動します。ワークスペース外への書き込みやリストにないコマンドについては、依然として確認が行われます。 |
| 使い捨てサンドボックス | `allow-all` | すべての機能が許可されています。実行後に破棄されるコンテナなど、環境自体が境界となる場面で使用してください。 |

各プロファイルの要求方法は同じです。プリセット ID をセッションリクエストの `policyPreset` 配列に指定します。コードレビューボットは、次のようにしてセッションを開きます：

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["read-workspace"]
    }
  }
}
```

診断セッションでは、ワークスペースの読み取りと読み取り専用シェルクエリを組み合わせて使用します：

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["read-workspace", "read-only-shell"]
    }
  }
}
```

編集、ビルド、テストを行うCIハネスでは、書き込み可能な2つのプリセットを組み合わせて使用します：

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["edit-workspace", "dev-shell"]
    }
  }
}
```

`deny`以下のルールおよびKiroスコープの不変条件は、どのプロファイルがアクティブであっても適用されます。

### 組み込みおよびヘッドレスクライアントのプリセット

同じプロファイルが一般的な統合パターンに対応しています。Kiroを埋め込むエディタ統合では、通常`edit-workspace`を要求するため、ワークスペース内のファイル編集時にプロンプトが表示されません。コードレビューボットは`read-workspace`のみを要求します。エージェントをプログラムで駆動するCIや評価ハネスは、`edit-workspace`と`dev-shell`を組み合わせ、さらにパイプラインが絶対に触れてはならない項目に対して独自の`deny`ルールを追加します。

### 信頼不変条件

プリセットはセッションに許可される操作の範囲を拡張しますが、優先順位の高いルールを上書きすることはできません。上記の「スコープ」セクションで説明した「上書き拒否」アルゴリズムは、依然として完全に適用されます：

- Kiro-scopeによるハード拒否（`~/.kiro/settings/`、`.kiro/settings/`、`~/.kiro/workspace-roots/`、`.kiroignore`への書き込み、および「[デフォルトの動作](https://kiro.dev/docs/permissions/#default-behavior)」に記載されているその他の保存先）は、いかなるプリセットにかかわらず、そのアクションをブロックします。
- Kiroスコープの「ask」ルール（`.git/**`、`.vscode/**`、`**/*.code-workspace`、および`.kiro`と`~/.kiro`の下にある`agents`、`hooks`、`workflows`、`powers`ディレクトリ）は、プリセットによって広範な書き込みアクセスが許可されている場合でも、引き続き確認プロンプトを表示します。
- ユーザー、ワークスペース、または管理スコープで設定された `deny` ルールは、プリセット `allow` よりも優先されます。
- `sandbox_network` 機能は `all` メタ機能の一部ではないため、`allow-all` を含むどのプリセットも、サンドボックスのネットワークゲート設定を変更することはありません。

## デフォルトの動作

`permissions.yaml`が設定されていない場合、デフォルトのエージェントポリシーでは以下が許可されます：

- `fs_read``./**` での実行 — ワークスペース内の任意のファイルを通知なしに読み取り
- 一般的な Git の読み取り専用コマンドに対する `shell` — `git status`、`git log`、`git diff`、`git branch` など
- システム情報コマンドに対する `shell` — `pwd`、`whoami`、`uname` など
- ユーティリティツール（診断、ナレッジなど）

Kiroのスコープ（ハードコードされており、設定で変更不可）では以下が強制されます：

- **常に拒否される：**`~/.kiro/settings/`、`.kiro/settings/`、および`~/.kiro/workspace-roots/`への書き込み（エージェントが自身の権限ファイルを変更することを防止するため）、任意の階層にある`.kiroignore`への書き込み（エージェント自身の読み取り境界を定義するため）、インストール済みのPowerのMCP設定（`~/.kiro/powers/installed/<name>/mcp.json`）への書き込み、およびKiro自身の状態ストア（`~/.kiro/sandbox-state/`、`~/.kiro/web-session/`、`~/.kiro/cloud-cache/`、`~/.kiro/sandbox-curl/`）への書き込み
- **常に確認を求める：**`.git/**`、`.vscode/**`、`**/*.code-workspace`への書き込み、およびワークスペース`.kiro`と`~/.kiro`の両方の`agents`、`hooks`、`workflows`、`powers`ディレクトリへの書き込み。これらは信頼済みおよび信頼されていないワークスペースのいずれにおいても確認を求め、どのスコープの`allow`ルールもこの確認を無効にしません。ただし、「[ワークスペースの信頼](https://kiro.dev/docs/permissions/#workspace-trust)」で説明されている管理対象クラウドサンドボックス内での1つの例外を除きます。
- **ワークスペースが信頼されていない場合の確認:** `.kiro/steering`、`.kiro/skills`、`.kiro/extensions`、`.kiro/specs`ディレクトリ自体、およびKiroが宣言していない`.kiro`ディレクトリへの書き込みを行う際、保存されたルールで書き込みが許可されている場合でも確認が行われます。[「ワークスペースの信頼」](https://kiro.dev/docs/permissions/#workspace-trust)を参照してください。

それ以外の場合はすべて、承認を求めるプロンプトが表示されます。`permissions.yaml` を作成すると、これらのデフォルト設定に追加され、置き換えられることはありません。

## ワークスペースの信頼性

一部のエージェント入力は、開いているリポジトリ内に存在します。具体的には、`.kiro/agents/` 内のカスタムエージェントプロファイル、`.kiro/steering/` 内のステアリングファイル、ワークスペースの MCP サーバー設定、スキル、およびワークフローファイルです。クローンされたリポジトリがこれらを利用してエージェントの動作を変更する可能性があるため、Kiro は、ユーザーがワークスペースを信頼するまで、そのワークスペースを「信頼されていない」ものとして扱います。 この決定はワークスペースの外部に保存されるため、リポジトリは自身の信頼ステータスを変更することはできません。

ワークスペースを信頼するまで、Kiro は以下の処理を行います：

- そのワークスペースのカスタムエージェント、ステアリングファイル、MCPサーバー設定、およびスキルをロードしません。
- ワークスペースからのワークフローファイル（ホームディレクトリやクラウドレシピディレクトリからのリンクを介してアクセスされるファイルを含む）を読み込みません。ユーザー自身のホーム、クラウド、バンドル、および生成されたワークフローは引き続き利用可能です。
- 保存済みルールや広範なルールでコマンドが許可されている場合でも、バックグラウンドプロセスを含め、すべてのシェルコマンドの実行前に確認を求めます。プロンプトにはコマンド全体が表示されます。一致する`deny`ルールがある場合は、依然として拒否されます。
- 保存されたルールや`autoApprove`によって許可されている場合でも、すべてのMCPツール呼び出し、およびPowerの起動、コンテンツの読み取り、ツール呼び出しの前に確認を求めます。また、MCP認証やURLプロンプトの後に呼び出しが再試行された際にも再度確認を求めます。一致する`deny`ルールがある場合は、依然として拒否されます。
- `.kiro/steering`、`.kiro/skills`、`.kiro/extensions`、`.kiro/specs`ディレクトリ自体、またはKiroが宣言していない任意の`.kiro`ディレクトリへの書き込みを行う前には、ワークスペースおよび`~/.kiro`の両方で確認を求めます。これは`powers`、保存されたルールで書き込みが許可されている場合でも同様です。`agents``hooks``workflows`、
- `~/.kiro/memories/` 以下のメモリデータベースおよびエージェントのセッションストア（デフォルトでは `~/.kiro/sessions/`）への書き込みは、確認を求めずに拒否されます。これにより、信頼されていないセッションが他のセッションの状態を上書きすることを防ぎます。
- エージェントがメモリ、ナレッジベース、またはリモートラーニングを追加、変更、または削除することは許可されません。それらの読み取りは引き続き可能です。

ユーザー、管理、エージェント、およびセッションのルールは引き続き適用され、`~/.kiro/workspace-roots/` にあるワークスペースごとのストアも同様です。これはリポジトリの外にあるため、信頼関係に関係なく読み込まれます。

信頼設定の変更は、`.kiro` への書き込みの 1 つの階層にのみ影響し、他の階層には影響しません。この表は、ワークスペースの `.kiro` および `~/.kiro` の両方に適用されます。`.kiro/specs/` 以下のファイルについては、通常のルールが適用されます。

| `.kiro` 以下のパス | 信頼されていないワークスペース | 信頼されたワークスペース |
| --- | --- | --- |
| `steering`、`skills`、`extensions`、`specs` ディレクトリ自体、Kiro が宣言していないディレクトリ | 保存されたルールで書き込みが許可されている場合でも、確認を求めます | ルールに従う |
| `agents`, `hooks`, `powers`, `workflows` | 確認を求める | 確認を求めます。ただし、以下の`fs_write`の例外で説明されている場合は除きます |
| `settings` | 拒否 | 拒否 |

一致する`deny`ルールが、すべての行で優先されます。

1 つのルールにより、`.kiro` ディレクトリに対する「信頼できないもののみ」の確認要求が解除されます。それは、`match` の制限がなく、`exclude` もない、自身の `~/.kiro/settings/permissions.yaml` 内の `fs_write` `allow` ルールです。このルールは、「常に確認」のパスを削除したり、一致する `ask` や `deny` を上書きしたり、上記に挙げた信頼できないワークスペースの入力を読み込んだりすることはありません。 ただし、1つの環境ではこのルールが拡大適用されます。クラウドセッションが実行される管理対象のクラウドサンドボックス内の信頼済みワークスペースでは、同じ制限のないユーザーレベルの`fs_write` `allow`により、`.git/**`、`.vscode/**`、`**/*.code-workspace`、および`agents`、`hooks`、`workflows`、`powers`ディレクトリに対する「常に確認」プロンプトも解除されます。クラウドサンドボックスの外では、これらのパスについてはすべてのワークスペースで確認が求められます。

### Kiro CLI でのワークスペースの信頼設定

Kiro CLI 2.33 以降では、対話型 V3 セッションにおいて、フォルダ内で Kiro CLI を初めて起動した際、そのフォルダのフック、エージェント、MCP サーバー、ステアリング、ワークフロー、または言語サーバーの設定が読み込まれる前に、「**このワークスペースを信頼しますか？」**という画面が表示されます。 非対話型の実行（`--no-interactive`）および V1 および V2 セッションにはこの確認画面は表示されません。これらは以前と同様に、確認なしにワークスペースの設定を読み込みます。この画面は Kiro CLI 固有のものです。

1. プロジェクトフォルダ内で Kiro CLI を起動してください。画面にはフォルダパスが表示され、そのフォルダには、お使いのマシン上でコマンドを実行するフック、エージェント、MCP サーバー、およびワークフローが含まれている可能性があるという警告が表示されます。
2. **「信頼」**を選択してフォルダの設定を読み込み、セッションを開始するか、**「信頼しない」**を選択して終了します。「信頼しない」を選択すると、フォルダから何も読み込まずに Kiro CLI が終了し、`Not trusted: <folder>. Kiro exited without loading this folder.` が表示されます。
3. Kiroは、信頼された回答を`workspaceTrusted`として、`~/.kiro/workspace-roots/`配下のワークスペースごとの権限ファイルに保存するため、この画面はフォルダごとに1回表示されます。画面にはそのファイル名が正確に表示されます。

フォルダがホームディレクトリの場合、画面にはその`.kiro`の設定がユーザーレベルの設定であり、その回答は当該セッション中のみ有効であることが表示されます。ホームディレクトリに対する信頼設定は決して保存されないため、Kiroはそこで起動するたびに確認を行います。

Kiro CLI 2.34以降では、`--trust-workspace`を指定することで、現在のフォルダを1回のV3起動分だけ信頼対象にできます。このフラグはプロンプトをスキップし、`workspaceTrusted`を保存しないため、以前にそのフォルダに対する信頼を保存していない限り、その後の起動時に再度確認が行われます。

信頼を解除するには、指定された画面に示されているファイルから`workspaceTrusted`の行を削除してください。そのフォルダで次に起動すると、画面が再び表示されます。フォルダが信頼されていることを確認するには、そのフォルダ内でKiro CLIを再度起動してください。画面は表示されず、そのフォルダの設定が読み込まれた状態でセッションが開始されます。

## インターフェースごとの権限管理

### エージェントの自律性設定

`permissions.yaml`ルールに加え、IDEのエージェントの自律性は **[設定] → [エージェント] → [エージェントの自律性]**（設定キー：`kiroAgent.agentAutonomy`）で制御されます。2つのモードは以下の通りです：

- **オートパイロット** - エージェントは確認を求めずに許可された操作を実行します
- **監督モード** - エージェントは、いかなるアクションを実行する前にも確認を求めます

機能ベースの権限レイヤーは、自律モードによって実行の可否が決定された後に適用されます。これら2つのレイヤーを組み合わせることで、大まかな制御（オートパイロット対スーパーバイズド）に加え、特定の機能に対するきめ細かなルール（permissions.yaml）を設定できます。

### 対話型承認フロー

ツールが承認を必要とする場合、チャットにプロンプトが表示されます。現在の呼び出しに対しては、**「許可」**と**「拒否」**の選択肢が利用可能です。また、Kiroは、要求されたコマンドに適用可能な保存済みルールを導き出せる場合、永続的な選択肢も表示します：

| アクション | 効果 |
| --- | --- |
| **許可** | この特定の実行を1回承認する |
| **常に許可** | 永続的な許可ルールを作成する（パターン／スコープピッカーが開きます） |
| **拒否** | この特定の呼び出しを1回だけブロックする |
| **常に拒否する** | 永続的な拒否ルールを作成する |

Kiro が保存されたルールの有効性を確認できない場合、「**常に許可」**および「**常に拒否」**のオプションは非表示になり、その理由がプロンプトに説明されます。

**「常に許可」**または「**常に拒否」**を選択すると、次の 2 つの項目を設定します。

- **パターン** - ルールの照合範囲を選択します（例：任意の cd コマンドに対して `cd *`、または正確なコマンドパス）
- **適用先** - ルールを保存する場所を選択します：
  - **すべてのワークスペース** — ユーザースコープの `~/.kiro/settings/permissions.yaml` に保存
  - **このワークスペース** — `~/.kiro/workspace-roots/<hash>/permissions.yaml`に保存されます（ユーザー単位、リポジトリ外）。Kiro IDEでは、ウィンドウに複数のワークスペースフォルダがある場合、この選択肢は「**このワークスペースフォルダ（*フォルダ名*）**」と表示されるため、ルールがどのフォルダ用に保存されているかを確認できます。 このラベルはルールの適用方法には影響しません。シェルコマンドのルールは、引き続きセッション全体に適用されます。Kiro IDEでは、各ワークスペースフォルダ外のファイルやフォルダについては、この選択肢は非表示になります。
  - 「**このセッション**」 - セッションが終了するまでメモリ内に保持されます

パターンのドロップダウンには、特定の操作の一般化されたバージョンが候補として表示されます。たとえば、正確なコマンド `git add contents/docs/` はパターン `git add *` となり、正確なパス `.env.local` は `.env*` または `**/.env*` となります。この候補を編集して、より制限を厳しくしたり、より許容範囲を広げたりすることができます。

連鎖したコマンド（例：`cd /path && cargo build`）の場合、連鎖内の各サブコマンドは個別に表示され、承認を求められます。

## 権限設定の例

以下に、権限設定の一般的なパターンを示します：

| シナリオ | 設定 |
| --- | --- |
| ファイルの読み取りを許可 | `capability: fs_read`, `effect: allow` |
| プロジェクトディレクトリへの書き込みを許可する | `capability: fs_write`, `match: ["src/**", "tests/**"]`, `effect: allow` |
| 機密ファイルへのアクセスをブロックする | `capability: fs_write`, `match: ["*.env", "*.pem", "*.key"]`, `effect: deny` |
| 危険なコマンドをブロック | `capability: shell`, `match: ["rm -rf *", "sudo *"]`, `effect: deny` |
| 特定のMCPサーバーを許可 | `capability: mcp`, `match: ["my-server/*"]`, `effect: allow` |
| 本番環境でのシェル実行には承認を必須とする | `capability: shell`, `effect: ask` |
