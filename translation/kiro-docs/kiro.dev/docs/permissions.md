Kiroは、エージェントの動作をきめ細かく宣言的に制御できる、機能ベースの権限システムを採用しています。機能ごとに一致パターンと明示的な効果を定義することで、従来の二値的な信頼モデルに取って代わります。

| 機能 | IDE | CLI | Web | モバイル |
| --- | --- | --- | --- | --- |
| 権限のYAML設定 | ✓ | ✓ | 該当なし | — |
| 対話型承認プロンプト | ✓ | ✓ | 該当なし | — |
| グローバルおよびワークスペースのスコープ | ✓ | ✓ | 該当なし | — |
| アクションごとのプロンプトなしのサンドボックス実行 | — | — | ✓ | — |

Web版では、`permissions.yaml`モデルおよび対話型承認は適用されません。エージェントはアクションごとの確認を行う代わりに、隔離された[クラウドサンドボックス](https://kiro.dev/docs/web/sandbox/)内で実行されるため、これらの行は「非対応」ではなく「N/A」とマークされます。

## 仕組み

権限システムは、3つの中核となる概念に基づいて構築されています：

| 概念 | 説明 |
| --- | --- |
| **機能** | `fs_read`、`fs_write`、`shell`、`web_fetch`、`web_search`、`mcp`、`subagent`、`skill`、`power`、`context`、`diagnostics`、`sandbox_network`。メタ機能の詳細：`all`（すべて）、`builtin`（すべての組み込みツール）、`filesystem`（`fs_read` + `fs_write`） |
| **効果** | `deny` (常にブロック)、`ask` (プロンプトを表示)、`allow` (黙って処理を続行) |
| **優先順位** | deny > ask > allow - スコープにかかわらず、denyルールが常に優先される |

追加のルールプロパティ：

| プロパティ | 説明 |
| --- | --- |
| **一致パターン** | ルールの適用範囲を指定するグロブパターン（fsの場合はファイルパス、shellの場合はコマンドの接頭辞、MCPの場合はサーバー名またはツール名） |
| **除外** | 一致させてはならないオプションのグロブパターン — 「X 以外のすべてを許可」を有効にします |

## ルールの定義

権限は、YAML ファイル内で 2 つのレベルで定義されます：

**ユーザースコープ**（`~/.kiro/settings/permissions.yaml`） - すべてのプロジェクトに適用されます。信頼できる操作を事前に承認するために使用します：

yaml

```yaml
rules:
  - capability: shell
    match: ["git *", "npm *", "npx *"]
    effect: allow

  - capability: fs_write
    match: ["src/**", "tests/**"]
    effect: allow

  - capability: fs_read
    effect: allow

  - capability: mcp
    match: ["my-server/*"]
    effect: allow
```

**ワークスペーススコープ**（`~/.kiro/workspace-roots/<hash>/permissions.yaml`） - 特定のプロジェクトにのみ適用されます。ルールを1つのコードベースに限定する場合に使用します：

yaml

```yaml
rules:
  - capability: fs_write
    match: ["*.env", "*.pem", "*.key"]
    effect: deny

  - capability: shell
    match: ["rm -rf *", "sudo *"]
    effect: deny
```

どちらのスコープも、すべてのエフェクト（`deny`、`ask`、`allow`）をサポートしています。

### 除外構文

ルールでは、「～を除くすべてを許可する」パターン用の `exclude` フィールドをサポートしています：

yaml

```yaml
rules:
  - capability: mcp
    match: ["my-server/*"]
    exclude: ["my-server/dangerous-tool"]
    effect: allow
```

### パターンマッチング

ルールではグロブパターンが使用されます。構文は機能の種類によって異なります：

**ファイルシステムパターン**（`fs_read`、`fs_write`）：

- `*` 単一のパス構成要素内での一致
- `**` パス区切り文字をまたいで一致
- `{a,b}` 中括弧展開および`[abc]`の文字クラスがサポートされています
- ワイルドカードを含まないパターンは、暗黙的に子要素に一致します。`~/temp` は `~/temp/child` に一致します

**シェル、Web、および MCP パターン：**

- `*` 任意の文字列に一致する
- `**`、`?`、および文字クラスはサポートされていません

yaml

```yaml
rules:
  # Allow npm commands except npm publish
  - capability: shell
    effect: allow
    match:
      - "npm *"
    exclude:
      - "npm publish*"

  # Deny reads to secrets at any depth
  - capability: fs_read
    effect: deny
    match:
      - "**/.env"
      - "**/.env.*"
      - "secrets/**"
      - "**/*.pem"
```

### シェルコマンドの解析

シェルコマンドは、パターンマッチングの前に解析されます。複合コマンド（`;`、`&&`、`||`、`|` を使用するもの）は分割され、各サブコマンドが個別に評価されます。これにより、`npm test *` に対するルールが誤って `npm test ; curl attacker.com` に一致してしまうことを防ぎます。

## スコープ

権限は複数のスコープにわたって評価されます。

| スコープ | 場所 | 許可される効果 |
| --- | --- | --- |
| Kiro | ハードコードされたセキュリティ不変条件（設定によって変更できないもの） | 拒否、確認 |
| 管理 | `managed-settings.json` における[エンタープライズ権限ポリシー](https://kiro.dev/docs/enterprise/governance/permissions/) | 拒否、確認 |
| ユーザー | `~/.kiro/settings/permissions.yaml` | 拒否、確認、許可 |
| ワークスペース | `~/.kiro/workspace-roots/<hash>/permissions.yaml` | 拒否、確認、許可 |
| エージェント | エージェントプロファイルに組み込まれている（`permissions`フィールド） | 拒否、確認、許可 |
| セッション | セッション中の同意決定に基づくインメモリルール | 拒否、確認、許可 |

ルールは、「拒否が優先」というアルゴリズム（deny > ask > allow）を使用して評価されます。スコープ間の優先順位はなく、どのスコープに由来するかにかかわらず、最も制限の厳しい効果が優先されます。

## ポリシープリセット

ポリシープリセットは、名前が付けられ、組み合わせ可能なセッションスコープの`allow`ルールセットです。Kiro独自のインターフェースや、エディタ統合、レビューボット、CIハネスなどの互換性のあるサードパーティ製統合を含む、あらゆるACPクライアントがこれらを使用することで、個別のルールを一から記述することなく、明確に定義された機能プロファイルでセッションを開始できます。

### プリセットの適用方法

プリセットは、ACPクライアントが`session/new`または`session/load`リクエストの`_meta.kiro.policyPreset`フィールドを通じて要求します。複数のプリセットを組み合わせることができ、そのルールは和集合として統合されます。

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["edit-workspace", "dev-shell"]
    }
  }
}
```

プリセットのルールは、クライアントがセッションを開く際に、`permissions.yaml`で設定したルールとは別にセッションに読み込まれます。これが、セッションのアクティブなルールに、自身が作成したことのないエントリが含まれることがある理由です。

未知のプリセット ID をリクエストすると、セッションリクエストは拒否されます。デフォルトポリシーへのサイレントなフォールバックは行われません。

### 利用可能なプリセット

| プリセット ID | 許可される内容 |
| --- | --- |
| `allow-all` | `sandbox_network` を除くすべての機能（`capability: all, effect: allow` と同等） |
| `edit-workspace` | `fs_read` および、`./**`内でのみ有効な`fs_write` |
| `read-workspace` | `fs_read` `./**`内のみ |
| `read-all` | `fs_read` どこでも、さらに`web_fetch`および`web_search` |
| `read-only-shell` | 読み取り専用のシェルコマンド：システム情報に加え、`git`、`cargo`、`npm`、`docker`、`kubectl`、および `rustup` へのクエリ |
| `dev-shell` | 読み取り専用のシェルコマンド（`read-only-shell`のセット）に加え、git writeコマンド；ビルドツール `cargo`、`npm`、`bun`、`yarn`；ワークスペース操作 `mkdir`、`touch`、`mv`、`cp`；インスペクションコマンド `ls`、`cat`、`grep`、`echo` |

### セッションのプリセットの選択

プリセットは「許可のみ」のプロファイルです。セッションで実行すべき操作に関するプロンプトを非表示にし、それ以外の操作については承認を求めるデフォルト設定を維持します。セッションの目的に最も合致する、範囲が最も狭いプロファイルを選択してください。

| セッションプロファイル | プリセット | 得られるもの |
| --- | --- | --- |
| コードレビューまたは監査 | `read-workspace` | ワークスペースのファイルは確認なしに読み込まれます。書き込みやシェルコマンドについては引き続き確認が行われるため、変更を行う前にセッションからプロンプトが表示されます。 |
| 調査および研究 | `read-all` | ディスク上の任意の場所からのファイル読み取りに加え、`web_fetch`および`web_search`も利用可能です。これにより、書き込みアクセスを必要とせずに、コードや外部ドキュメント全体にわたって問題を追跡するセッションが可能になります。 |
| 診断およびトリアージ | `read-workspace` + `read-only-shell` | エージェントはワークスペースのファイルを読み取り、Git、Docker、kubectl、およびその他のツールの状態を照会します。書き込みが許可されることは一切ないため、変更を行うたびに確認が行われます。 |
| 自律的なビルド・テストループ | `edit-workspace` + `dev-shell` | エージェントは、ワークスペースのファイルを編集し、git write コマンドや標準的なビルドツールを実行し、アクションごとに確認を求められずにワークスペース内のファイルを作成または移動します。ワークスペース外への書き込みやリストにないコマンドについては、依然として確認が求められます。 |
| 使い捨てサンドボックス | `allow-all` | すべての機能が許可されています。実行後に破棄されるコンテナなど、環境自体が境界となる場面で使用してください。 |

各プロファイルの要求方法は同じです。プリセット ID をセッションリクエストの ``policyPreset`` 配列に指定します。コードレビューボットは、次のようにしてセッションを開きます：

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["read-workspace"]
    }
  }
}
```

診断セッションでは、ワークスペースの読み取りと読み取り専用シェルクエリを組み合わせて使用します：

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["read-workspace", "read-only-shell"]
    }
  }
}
```

編集、ビルド、テストを行うCIハネスでは、書き込み可能な2つのプリセットを組み合わせて使用します：

json

```json
{
  "_meta": {
    "kiro": {
      "policyPreset": ["edit-workspace", "dev-shell"]
    }
  }
}
```

`deny` どのプロファイルがアクティブであっても、以下のルールおよびKiroスコープの不変条件は引き続き適用されます。

### 組み込みおよびヘッドレスクライアントのプリセット

同じプロファイルが一般的な統合パターンに対応しています。Kiroを組み込むエディタ統合では、通常`edit-workspace`を要求するため、ワークスペース内のファイル編集時にプロンプトが表示されません。コードレビューボットは`read-workspace`のみを要求します。エージェントをプログラムで駆動するCIや評価ハネスは、`edit-workspace`と`dev-shell`を組み合わせ、さらにパイプラインが絶対に触れてはならない項目に対して独自の`deny`ルールを追加します。

### 信頼不変条件

プリセットはセッションに許可される動作の範囲を拡張しますが、優先順位の高いルールを上書きすることはできません。上記の「スコープ」セクションで説明した「拒否の上書き」アルゴリズムは、依然として完全に適用されます：

- Kiro-scopeによるハード拒否（`~/.kiro/settings/`、`.kiro/settings/`、`~/.kiro/workspace-roots/`、および「[デフォルトの動作」](https://kiro.dev/docs/permissions/#default-behavior)に記載されているその他のストアへの書き込み）は、いかなるプリセットにかかわらず、そのアクションをブロックします。
- Kiroスコープの「ask」ルール（`.git/**`、`.vscode/**`、`**/*.code-workspace`、`.kiroignore`、および`.kiro`および`~/.kiro`配下の`agents`、`hooks`、`workflows`、`powers`ディレクトリ）は、プリセットで広範な書き込みアクセスが許可されている場合でも、確認プロンプトを表示します。
- ユーザー、ワークスペース、または管理スコープで設定された「`deny`」ルールは、プリセットの「`allow`」よりも優先されます。
- `sandbox_network`機能は`all`メタ機能の一部ではないため、`allow-all`を含むどのプリセットも、サンドボックスのネットワークゲート設定を変更することはありません。

サブエージェントは、deny-wins 交差ルールにより、親セッションのルールセット全体を継承します。親セッションのすべての allow、deny、および ask が適用されるため、いずれかの側でより制限の厳しいルールが常に優先されます。

## デフォルトの動作

`permissions.yaml`が設定されていない場合、デフォルトのエージェントポリシーでは以下が許可されます：

- `fs_read` `./**` では、ワークスペース内の任意のファイルを通知なしで読み込み可能
- `shell` 一般的な Git の読み取り専用コマンド（`git status`、`git log`、`git diff`、`git branch` など）
- `shell` システム情報コマンド用 - `pwd`、`whoami`、`uname` など
- ユーティリティツール（診断、ナレッジなど）

Kiroのスコープ（ハードコードされており、設定で変更不可）では以下が強制されます：

- **常に拒否される：**`~/.kiro/settings/`、`.kiro/settings/`、および `~/.kiro/workspace-roots/` への書き込み（エージェントが自身の権限ファイルを変更できないようにするため）、インストール済みの Power の MCP 設定（`~/.kiro/powers/installed/<name>/mcp.json`）への書き込み、および Kiro 自身の状態ストア（`~/.kiro/sandbox-state/`、`~/.kiro/web-session/`、`~/.kiro/cloud-cache/`、`~/.kiro/sandbox-curl/`）への書き込み
- **常に確認を求める：**`.git/**`、`.vscode/**`、`**/*.code-workspace`、`.kiroignore`、およびワークスペース `.kiro` と `~/.kiro` の両方の `agents`、`hooks`、`workflows`、`powers` ディレクトリに書き込みを行います。これらは信頼済みおよび信頼されていないワークスペースのいずれでも確認を求め、どのスコープの `allow` ルールでもこのプロンプトを削除することはできません。
- **ワークスペースが「信頼されていない」状態の間に確認を求めます：**`.kiro/steering`、`.kiro/skills`、`.kiro/extensions`、および Kiro が宣言していない `.kiro` ディレクトリへの書き込みが行われます。「[ワークスペースの信頼」](https://kiro.dev/docs/permissions/#workspace-trust)を参照してください。

それ以外の場合はすべて、承認を求めるプロンプトが表示されます。`permissions.yaml` を作成すると、これらのデフォルト設定に追加され、置き換えられることはありません。

## ワークスペースの信頼

一部のエージェント入力は、開いたリポジトリ内に存在します。具体的には、`.kiro/agents/` 内のカスタムエージェントプロファイル、`.kiro/steering/` 内のステアリングファイル、ワークスペースの MCP サーバー設定、スキル、およびワークフローファイルです。クローンされたリポジトリがこれらを利用してエージェントの動作を変更する可能性があるため、Kiro は、ユーザーがワークスペースを信頼するまで、そのワークスペースを「信頼されていない」ものとして扱います。 この決定はワークスペースの外部に保存されるため、リポジトリは自身の信頼ステータスを変更することはできません。

ワークスペースを信頼するまで、Kiroは以下の処理を行います：

- そのワークスペースのカスタムエージェント、ステアリングファイル、MCPサーバー設定、およびスキルをロードしません。
- ワークスペースからのワークフローファイル（ホームディレクトリやクラウドレシピディレクトリからのリンクを介してアクセスされるファイルを含む）を読み込みません。ユーザー自身のホーム、クラウド、バンドル、および生成されたワークフローは引き続き利用可能です。
- 保存済みルールや広範なルールによってコマンドが許可されている場合でも、バックグラウンドプロセスを含め、すべてのシェルコマンドが実行される前に確認を求めます。プロンプトにはコマンド全体が表示されます。一致する`deny`ルールがある場合は、依然として拒否されます。
- 保存済みルールや`autoApprove`によって許可されている場合でも、すべてのMCPツール呼び出し、およびPowerの起動、コンテンツの読み取り、ツール呼び出しの前に確認を求めます。また、MCP認証やURLプロンプトの後に呼び出しが再試行された際にも再度確認を求めます。一致する`deny`ルールがある場合は、依然として拒否されます。
- `.kiro/steering`、`.kiro/skills`、`.kiro/extensions`、またはKiroが宣言していない任意の`.kiro`ディレクトリへの書き込み前に、ワークスペースおよび`~/.kiro`の両方で確認を求めます。`agents`、`hooks`、`workflows`、および`powers`ディレクトリへの書き込みについては、すべてのワークスペースで確認を求めます。
- `~/.kiro/memories/` 配下のメモリデータベースおよびエージェントのセッションストア（デフォルトでは `~/.kiro/sessions/`）への書き込みは、確認を求めずに拒否されます。これにより、信頼できないセッションが他のセッションの状態を上書きすることを防ぎます。
- エージェントがメモリ、ナレッジベース、またはリモートラーニングを追加、変更、または削除することは許可されません。ただし、それらの読み取りは引き続き可能です。

ユーザー、管理、エージェント、およびセッションに関するルールは引き続き適用されます。また、`~/.kiro/workspace-roots/` 配下のワークスペースごとのストアも同様です。これはリポジトリの外に存在するため、信頼関係に関係なく読み込まれます。

`.kiro` ディレクトリに対する「信頼されていないセッションのみ」という要求を解除するルールが 1 つあります。それは、`match` の制限や `exclude` を設定していない、自身の `~/.kiro/settings/permissions.yaml` にある `fs_write` `allow` ルールです。このルールは、常に確認を要求するパスを削除したり、一致する `ask` や `deny` を上書きしたり、上記の信頼されていないワークスペースの入力を読み込んだりすることはありません。

## インターフェースごとの権限管理

### エージェントの自律性設定

`permissions.yaml`ルールに加え、IDEのエージェントの自律性は [**設定] → [エージェント] → [エージェントの自律性**]（設定キー：`kiroAgent.agentAutonomy`）で制御されます。2つのモードは以下の通りです：

- **オートパイロット** - エージェントは確認を求めずに許可された操作を実行します
- **監督モード** - エージェントは、いかなるアクションを実行する前にも確認を求めます

機能ベースの権限レイヤーは、自律モードによって処理の可否が決定された後に適用されます。これら2つのレイヤーを組み合わせることで、大まかな制御（オートパイロットとスーパーバイズド）に加え、特定の機能に対するきめ細かなルール（permissions.yaml）を設定できます。

### 対話型承認フロー

ツールが承認を必要とする場合、チャットにプロンプトが表示されます。現在の呼び出しに対しては、**「許可」**と**「拒否」**の選択肢が利用可能です。また、Kiroは、要求されたコマンドに適用可能な保存済みルールを導き出せる場合、永続的な選択肢も表示します：

| アクション | 効果 |
| --- | --- |
| **許可** | この特定の実行を1回承認する |
| **常に許可** | 永続的な許可ルールを作成（パターン／スコープピッカーが開きます） |
| **拒否** | この特定の呼び出しを1回だけブロックする |
| **常に拒否する** | 永続的な拒否ルールを作成する |

Kiro が保存されたルールの有効性を確認できない場合、「**常に許可」**および「**常に拒否」**のオプションは非表示になり、その理由がプロンプトに説明されます。

**「常に許可」**を選択すると、次の 2 つの項目を設定します。

- **パターン** - ルールの照合範囲を選択します（例：任意の cd コマンドに対しては ``cd *``、または正確なコマンドパスなど）
- **適用先** - ルールを保存する場所を選択します：
  - **すべてのワークスペース** — ユーザースコープの ``~/.kiro/settings/permissions.yaml`` に保存されます
  - **このワークスペース** — `~/.kiro/workspace-roots/<hash>/permissions.yaml` に保存されます（ユーザー単位、リポジトリ外）
  - **このセッション** — セッションが終了するまでメモリ内に保持されます

「パターン」ドロップダウンには、特定の操作の一般化されたバージョンが候補として表示されます。たとえば、正確なコマンド「`git add contents/docs/`」はパターン「`git add *`」となり、正確なパス「`.env.local`」は「`.env*`」または「`**/.env*`」となります。この候補を編集して、制限を厳しくしたり、緩和したりすることができます。

連鎖したコマンド（例：`cd /path && cargo build`）の場合、連鎖内の各サブコマンドが個別に承認を求める形で提示されます。

## 権限設定の例

以下に、権限設定の一般的なパターンを示します：

| シナリオ | 設定 |
| --- | --- |
| ファイルの読み取りを許可 | `capability: fs_read`, `effect: allow` |
| プロジェクトディレクトリへの書き込みを許可する | `capability: fs_write`, `match: ["src/**", "tests/**"]`, `effect: allow` |
| 機密ファイルへのアクセスをブロックする | `capability: fs_write`, `match: ["*.env", "*.pem", "*.key"]`, `effect: deny` |
| 危険なコマンドをブロック | `capability: shell`, `match: ["rm -rf *", "sudo *"]`, `effect: deny` |
| 特定のMCPサーバーを許可 | `capability: mcp`, `match: ["my-server/*"]`, `effect: allow` |
| 本番環境ではシェルを信頼しない | `capability: shell`、`effect: ask`（またはCLIで`/tools untrust shell`を使用） |
