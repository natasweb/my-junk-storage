Kiroは単一のエージェントであり、仕事をする場所ならどこでも利用可能です。ノートパソコンを閉じても、セッションはクラウド上で引き続き実行されます。 スマートフォンから状況を確認し、翌朝にはIDEで作業を再開できます。IDE、CLI、Web、モバイルアプリは、すべて同じ**統合エージェント・ハーネス**と通信するための異なる手段に過ぎません。したがって、ステアリングルールを設定したり、カスタムエージェントを作成したり、MCPサーバーを接続したりする際は、特定のアプリではなく、Kiroそのものを設定していることになります。

この一つの考え方が、他のすべてを整理しています。機能はKiroレベルに存在し、「**機能（Features）**」で一度だけ文書化され、各「インターフェース」セクションでは、そのインターフェースが追加する機能のみを扱います。このページでは、各要素がどのように組み合わさっているかを解説します。アーキテクチャの背景にある技術的なストーリーについては、Kiroブログの[「One agent, every surface」](https://kiro.dev/blog/one-agent/)をご覧ください。

## 1つのハーネス、多数のサーフェス

その中心にあるのが、統一されたエージェント・ハーネスです。これは、エージェントの実行に関わるすべて（会話のオーケストレーション、ツールの実行、コンテキストの管理、権限の評価、LLMプロバイダーとの通信）を処理します。すべてのKiroサーフェス（IDE、CLI、Web、モバイル）は、この同じハーネスのフロントエンドです。

このハーネスは、各アプリにコンパイルされたライブラリではなく、独立したプロセスです。コードベースと並行して実行され、エージェント側のすべてを管理し、クライアント側はそれとのやり取り方法を決定します。独立したプロセスであるため、同じハーネスをノートパソコン上でもクラウドのサンドボックス内でも起動でき、どちらでも全く同じように動作します。

ハーネスが共有されているため、機能は利用可能な場所を問わず同じように動作します。権限ルールは、CLIでもIDEでも同じ操作を拒否します。ステアリングファイルは、すべてのインターフェースでエージェントの挙動を同じように制御します。コンパクションは同じ情報を保持します。 各インターフェースの違いは、エージェントを操作する方法にあり、エージェントが実行できる機能そのものにはありません。ある機能がまだ特定のインターフェースに実装されていない場合、その機能ページの利用可能状況表にその旨が明記されています。

### 境界となるのはプロトコルです

クライアントは、オープンな[エージェントクライアントプロトコル](https://kiro.dev/docs/acp/)（ACP）を通じてハーネスと通信します。 これにはKiro独自のインターフェースも含まれます。IDE、CLI、Web、モバイルアプリはすべてACPを使用しており、ライブステアリング、仕様ワークフロー、リッチな権限プロンプト、コンテキスト使用状況の追跡といった機能のために、Kiro固有のメソッド（仕様の`_kiro/`名前空間下）で拡張されています。 ローカルクライアントは stdio 経由で接続し、Web およびモバイルは WebSocket 経由でサンドボックス化されたハーネスに接続します。どちらのトランスポートでも、同じバイナリ、同じツール、同じ動作が実現されます。

## ターン（ターン）の仕組み

どのインターフェースからプロンプトを送信しても、ハーネスは同じループを実行します：

1. **コンテキストが構築されます。**ハーネスは、プロンプト、これまでの会話履歴、[ステアリング](https://kiro.dev/docs/steering/)ファイル、および添付されたすべての情報を収集します。ここで[プロンプト送信フックが](https://kiro.dev/docs/hooks/types/#prompt-submit)実行され、独自のコンテキストを注入することができます。
2. **モデルが計画を立てます。**リクエストは[選択したモデルに](https://kiro.dev/docs/models/)送信されるか、Autoがタスクに最適なモデルへルーティングし、テキスト、ツール呼び出し、またはその両方が返されます。
3. **すべてのツール呼び出しがチェックされます。**ツールが実行される前に、[権限ルール](https://kiro.dev/docs/permissions/)（「deny」は「ask」より優先され、「ask」は「allow」より優先される）が評価され、有効になっている場合は[kiroignore](https://kiro.dev/docs/kiroignore/)パターンも評価されます。[「Pre Tool Use」フックは、](https://kiro.dev/docs/hooks/types/#pre-tool-use)呼び出しを許可またはブロックすることができます。
4. **ツールが実行されます。**[組み込みツールは](https://kiro.dev/docs/tools/)、ファイルの読み取りや編集、シェルコマンドの実行、Web検索を行います。[MCPサーバー](https://kiro.dev/docs/mcp/)や[Powers](https://kiro.dev/docs/powers/)によってツールセットが拡張され、[サブエージェントが](https://kiro.dev/docs/custom-agents/subagents/)委任された作業を引き受けます。[「ツール使用後」フックは](https://kiro.dev/docs/hooks/types/#post-tool-use)結果に応じて反応します。
5. **結果がフィードバックされます。**ツールの出力はモデルに戻され、タスクが完了するまでこのループが繰り返されます。ターンが完了すると、[エージェント停止フックが](https://kiro.dev/docs/hooks/types/#agent-stop)トリガーされます。
6. **コンテキストは管理された状態を維持します。**会話がモデルのコンテキスト制限に近づくと、[コンパクション機能によって](https://kiro.dev/docs/compaction/)古い履歴が要約され、セッションが継続されます。

このループこそが、「機能」セクションが現在の構成になっている理由です。各機能はループの段階であり、単一のアプリに後付けされたものではありません。一度記述した権限ルールは、あらゆる場所でのステップ3を制御します。ステアリングファイルは、あらゆる場所でのステップ1を形作ります。これこそが「単一のハーネス」という表現が持つ実用的な意味です。

## エージェントの実行環境

ループ自体はどこでも同じですが、実行されるコンピュータは環境によって異なります：

- **IDEとCLIでは、**デフォルトでユーザー自身のマシン上でハネスが実行されます。ツールはローカルファイルシステム上で動作し、シェルコマンドはユーザーのシェルで実行され、ビルドにはローカルにインストールされたツールチェーンと認証情報が使用されます。また、これら両方の環境から、Webが使用するのと同じ管理されたサンドボックス内で実行される[クラウドセッション](https://kiro.dev/docs/cloud-sessions/)を作成・接続することも可能です。
- **Webとモバイルは、**管理された[クラウドサンドボックス](https://kiro.dev/docs/web/sandbox/)内で同じハーネスを実行します。Kiroは接続されたリポジトリを隔離された環境にクローンし、そこで作業を行い、変更をプルリクエストまたはマージリクエストとして送信します。ユーザーの本機では何も実行されず、ノートパソコンを閉じた後もセッションは継続して実行されます。 Mobileも同様のクラウドセッションを利用するため、ブラウザで作業を開始し、スマートフォンからチェックインを行うことができます。

クラウドセッションは特定のアプリではなく、あなたのアカウントに紐づいているため、ある端末で開始した作業を別の端末で引き継ぐことができます。各端末でのクラウドセッションの作成方法および接続方法については、「[クラウドセッション」](https://kiro.dev/docs/cloud-sessions/)を参照してください。

同じループ、同じルール、同じ設定形式です。違いは、作業が行われる場所と、結果がどのようにユーザーに届くかという点だけです。

## 各デバイスによる付加価値

各デバイスのセクションでは、エージェントに関する体験、つまりエージェントの起動方法、動作の確認方法、および制御を維持する方法について解説しています。また、デバイスは単なる薄いラッパーでもありません。 クライアントは、プラットフォームの方が処理を効率的に行える場合、ハーネスの組み込み機能の代わりに独自のツールを提供できます。例えば、IDEはファイル操作にエディタ独自のAPIを使用し、その上にエディタ固有のコード解析機能を追加しています。

| インターフェース | 追加される機能 |
| --- | --- |
| [IDE](https://kiro.dev/docs/ide/) | エディタの統合：インライン差分表示、チェックポイント UI、仕様ペイン、ドッキング可能なチャット、および #Problems コンテキストを介したエージェントとのエディタ診断情報の共有 |
| [CLI](https://kiro.dev/docs/cli/) | ターミナルネイティブのワークフロー：TUI、スクリプトやCI向けのヘッドレスモード、オートコンプリート、シェルからのセッション管理 |
| [Web](https://kiro.dev/docs/web/) | ブラウザ上のセットアップ不要のエージェント：サンドボックス化された実行、リポジトリへの接続、プルリクエストベースのデリバリー、スケジュールに基づく自動化 |
| [モバイル](https://kiro.dev/docs/mobile/) | 外出先でもKiro：スマートフォンからセッションを開始・操作 |

「概要」セクションを読んでいて、「でも、その機能自体はどのように動作するのだろう？」と疑問に思った場合は、その答えは一つ上の階層にある「機能」セクションに記載されています。

## 設定はいつでも持ち運べます

設定も同様の共有モデルに従います。一度定義した内容は、Harnessが実行される場所ならどこでも適用されます：

| スコープ | 場所 | 移動先 |
| --- | --- | --- |
| プロジェクト | `.kiro/` リポジトリ内 | リポジトリ。チームメンバーや、それを開くすべてのインターフェースは、同じステアリング、仕様、エージェント、フック、およびMCPサーバーを受け取ります |
| ユーザー | `~/.kiro/` あなたのマシン上の | あなた。すべてのローカルプロジェクトにまたがる個人用エージェント、スキル、ステアリング、および設定 |
| クラウド | ローカルの`~/.kiro/`環境。[クラウド設定](https://kiro.dev/docs/web/cloud-configuration/)とアカウント間で同期されます | あなた。すべてのクラウドセッションにおける、個人用のステアリング、エージェント、フック、スキル、Powers、MCPサーバー、およびワークフロー。ステアリング、エージェント、スキル、Powers、フックは、新しいローカルセッションにも適用可能です |
| ワークスペースの信頼 | `~/.kiro/workspace-roots/<hash>/` | お使いのマシン限定。プロジェクトごとの権限ルールはリポジトリ外に保存されるため、クローンされたリポジトリが自らに信頼を付与することは決してありません |

これが、Kiro WebおよびMobileが設定なしでプロジェクトのエージェントやステアリングを自動的に読み込める理由です。これらは、IDEやCLIがローカルで使用するのと同じ、リポジトリ内の`.kiro/`ディレクトリを読み取ります。詳細については、「[設定スコープ」](https://kiro.dev/docs/configuration/)を参照してください。

## 実用上の意味

- **一度学べば、どこでも使える。**CLI用に作成した`permissions.yaml`は、IDEが参照するファイルと同じです。プロジェクトに追加した機能は、そのプロジェクトを開くすべての環境（インターフェース）で動作します。
- **一貫したアップグレード。**Harnessの改善点は一箇所に集約され、クライアントプロトコルに影響しない変更は、アプリの更新を必要とせずにすべてのインターフェースに反映されます。「`~/.kiro/hooks/`」のグローバルフックやコンパクション機能の改善も、この方法で提供され、すべてのインターフェースに同時に反映されました。
- **チーム全体での一貫性。**リポジトリに `.kiro/` をコミットすることで、IDE、ターミナル、ブラウザのいずれを使用する場合でも、全員が同じエージェントの挙動を利用できるようになります。
